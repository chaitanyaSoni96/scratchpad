# P5.7 Supply-Chain and Lifecycle Review

The task: *"Verify downloaded binaries need no arbitrary script execution
beyond the visible installer, checksums are published, and uninstall is
non-destructive."*

## Verdict

**FAIL AT ENTRY, then PASS after remediation.**

Two of the three questions passed on their own terms. The third did not, and
it did not fail at the margin: **the release archive could not install
itself.** Every documented install command — including the installer's default
verb — failed from an extracted archive, for two independent reasons. Nothing
in CI noticed, because the 94-assertion installer job that Phase 5 recorded as
its evidence runs `install.ps1` out of a git checkout, which is not the layout
a user downloads.

That is the same shape as the other controls this branch has caught: owned,
green, and pointed at the wrong artefact. A green check on the wrong input is
worse than no check, because it is believed. The Phase 5 exit evidence claims
a "clean-VM install/update/uninstall transcript"; what existed was a
clean-VM install from a *source tree*.

All findings below are fixed, and the fix is now enforced by a new gating CI
job that installs from the archive rather than the checkout. **P5.7 can be
ticked**, but the gate's own wording should be read as satisfied by the
remediation, not by what was there when the review started.

The one thing I want on the record for P6.8: the pre-beta manual check already
owed for standard-user Scheduled Task registration should now also cover the
downloaded-archive path end to end on a real machine, because CI cannot
reproduce Mark-of-the-Web (see S8, unverified).

## Findings

Ranked by severity. Every finding is marked **confirmed-by-execution** (I ran
something and read the result) or **confirmed-by-reading** (I traced the code
or config and did not execute it). Where a finding is partly each, it says so.

### S1 — HIGH — The release archive could not install itself

**confirmed-by-execution** (locally at entry; end-to-end in CI after the fix)

Two independent defects, either of which alone breaks the download path.

**S1a — payload resolution assumed the git-checkout layout.** `install.ps1`
computed `$RepoDir = Split-Path -Parent $PSScriptRoot` and resolved every
payload against it: `$RepoDir\bin\<name>.exe` and `$RepoDir\skill\SKILL.md`.
That is right for `<repo>\scripts\install.ps1`. In a release, `install.ps1`
sits at the **archive root**, so for an archive extracted to
`C:\Users\me\Downloads\scratchpad_v0.1.0_windows_amd64\`, `$RepoDir` is
`C:\Users\me\Downloads` — the parent of the extracted folder. `cli` died with:

```
scratchpad.exe not found at C:\Users\me\Downloads\bin\scratchpad.exe
  -- build it first: go build -o bin/ ./cmd/...
```

telling a user who downloaded a binary release to go build it from source.

**S1b — `skill/SKILL.md` was never in the archive.** I built the archives with
`make release-windows` and read the manifest. Contents were: `scratchpad.exe`,
`scratchpad-web.exe`, `install.ps1`, `README.md`, `LICENSE`, and three files
under `docs/`. No `skill/`. So `install.ps1 skill` had no source to copy —
and neither did `all`, **the default verb**, nor `install`. A user following
the beta release notes verbatim (`.\install.ps1 install`) hits this on the
first command.

**Fixed** in `0fb8b8b`: `Resolve-Payload` tries the release-archive layout
first and the git-checkout layout second, and error messages now name both
paths searched; `mkrelease.go` adds `skill/SKILL.md` to the archive.
`install.ps1` remains pure ASCII, which PowerShell 5.1 support depends on
(re-checked after the edit).

**Proven** by the new `windows-archive-install` CI job, on both engines: it
packages the archives, extracts one into a scratch directory, and installs
from it. The extraction parent is asserted to contain neither `bin\` nor
`skill\`, so a pass cannot come from the checkout-layout fallback firing.

#### The red run at `212f597`: harness bug, not an incomplete fix

That job went red on its first execution, with `FAIL cli installed
scratchpad.exe into -BinDir` at the head of a five-failure cascade. The
comfortable reading is "my harness was wrong"; the uncomfortable one is "the
`Resolve-Payload` fix is incomplete and the installer still cannot find its
payload in an extracted archive". I was asked to say which, explicitly, so:

**It was the harness, and the log proves it directly rather than by
inference.** The first invocation, running `install.ps1` out of
`D:\a\_temp\archive-2a83abd...\pkg`:

```
--> pwsh install.ps1
      cli: installed scratchpad.exe at C:\Users\runneradmin\AppData\Local\scratchpad\bin\scratchpad.exe
      skill: installed at C:\Users\runneradmin\.claude\skills\scratchpad\SKILL.md
      skill: installed at C:\Users\runneradmin\.pi\agent\skills\scratchpad\SKILL.md
```

The installer **found and copied both payloads out of the extracted archive**.
`Resolve-Payload` did exactly its job. Note the `-->` line: nothing follows
`install.ps1`. My helper's parameter was named `$Args`, which collides with a
PowerShell automatic variable, so the array bound empty and *every* invocation
ran a bare `install.ps1` — default verb `all`, default `-BinDir`. The
assertion then looked for the exe in the `-BinDir` it had failed to pass. The
whole cascade follows from that one line: nothing was in `$bin` to upgrade or
restore, and "uninstall removed the ~\.claude skill copy" failed because the
invocation labelled `uninstall` had in fact just run `all` and *installed* it.

The accident made it a stronger proof than the test I wrote. A bare
`install.ps1` is the **default verb `all`** — precisely the verb that had no
source whatsoever before this task, because `SKILL.md` was not in the archive
(S1b). It succeeded, from an extracted archive, with no `bin\` or `skill\`
anywhere near it. Both halves of S1 are closed by that transcript alone.

Two assertions in that run nevertheless *passed vacuously*, which is the part
worth keeping: "uninstall removed the binary" passed because the binary had
never been in `$bin`, and "the installed scratchpad.exe runs" passed because
`& $exe list` on a non-existent path is a PowerShell error, not a native exit
code, so `$LASTEXITCODE` still held the previous call's `0`. `3f42059` fixes
both by poisoning `$LASTEXITCODE` with a sentinel before every launch, so a
command that never ran cannot read as success.

**The minimum-assertion-count guard is what turned this into a legible
failure** rather than a partial green. `only 19 assertions ran - the block did
not execute its checks` is the same anti-vacuity idea as the symlink job's
zero-skip assertion and its "no `--- PASS/FAIL/SKIP:` lines" check: assert on
the *number of checks that ran*, not only on their outcomes, so a harness that
silently stops checking cannot pass. Both blocks in the new job carry one, and
any future assertion block on this branch should.

### S2 — HIGH — The installer verification job only ever tested the checkout layout

**confirmed-by-reading**, corroborated by S1 being live while it was green

`windows-installer` builds with `go build -o bin/ ./cmd/...` into the checkout
and runs `scripts/verify-install.ps1`, which drives `scripts/install.ps1`
in place. Both layouts' payload paths happen to coincide there. The job
recorded `94 passed, 0 failed` per engine (run `32994820274`) — genuinely
useful evidence about verbs, idempotence, the Scheduled Task, the exe-lock
retry and data-root survival, and completely silent about whether the thing
users download works.

This is the finding that matters more than S1. S1 is a bug; S2 is why a bug of
that size survived a phase whose stated gate was "clean Windows VM can install,
run, update, and uninstall".

**Fixed** in `212f597`/`3f42059`: new gating job `windows-archive-install`
(matrix `pwsh` × `powershell`) covering package → extract → `cli` → run the
installed exe → `skill` → `all` over an existing install → `uninstall` →
second `uninstall` → reinstall, plus the data-root marker and checksum blocks.
Both assertion blocks fail on a **minimum assertion count**, so "0 failures"
can never mean "0 checks ran". The `release` job now `needs` it.

*Cost, since it was asked for:* two additional `windows-2025` legs at roughly
five minutes each — the same runner class `windows-installer` already uses, and
about 15% on top of the branch's current Windows CI time. Both engines are kept
because engine parity is exactly what `docs/windows.md` claims. I considered
folding this into `verify-install.ps1` instead; I kept it separate because that
file is another task's, and because a job that must *not* see the checkout
layout is clearer as its own job with its own scratch directory.

### S3 — MED-HIGH — A tag name could inject shell into the `contents: write` release job

**confirmed-by-execution**

`git check-ref-format` permits `;`, `$`, `` ` ``, `|` and `&` in a tag name — I
checked each. `RELEASE_TAG` (`github.ref_name`) flows into
`make release-windows VERSION="$RELEASE_TAG"`, and the recipe expands
`$(VERSION)` **unquoted** into `/bin/sh`:

```make
go run scripts/mkrelease.go -dist $(DIST) -version $(VERSION) $(RELEASE_FLAGS)
```

I reproduced it against a copy of that recipe: `VERSION` set to
`v1.0;<command>;` executed `<command>`. In CI that runs inside the `release`
job — the only job holding `contents: write` and a `GH_TOKEN`. So pushing a
tag, a right that is often delegated more widely than repository write, became
arbitrary code execution with a token that can create and modify releases.

The workflow's existing env-indirection discipline (`RELEASE_TAG: ${{ ... }}`
then `"$RELEASE_TAG"` in the shell) correctly prevents *expression* injection
at the `${{ }}` layer. This is a layer below that, in make's own re-expansion.

**Fixed** in `212f597`: the `release` job rejects any tag not matching
`^v[0-9][0-9A-Za-z.+-]*$` before a shell sees it, and `windows-artifacts`
validates its `git describe` output the same way (that job derives `VERSION`
from tags too, so it is reachable from an ordinary branch push, though with a
read-only token). Both regexes were tested against the payloads above and
against real version shapes (`v1.0.0`, `v0.1.0-beta.1`, `v1.0.0+win`,
`v1.0.0-3-g0fb8b8b`, `0fb8b8b-dirty`, `dev`).

**The recommended second half was taken, after this review was written.** I
left the Makefile alone — it was shared with the concurrent P6.6 task — and
recorded quoting `-version "$(VERSION)"` as a one-line follow-up, since the CI
guard makes the injection unreachable from CI but a developer running
`make release-windows` by hand on a malicious tag was still exposed. The
coordinator closed it in `607a131` once P6.6 released the file, and did so
with a **negative control**: reverting the
quotes made `VERSION='v9.9;echo INJECTED>/tmp/pwn-proof;'` create the file,
and applying them made the metacharacters arrive at `mkrelease` as a literal
archive name that fails cleanly. That control is what makes it evidence rather
than an assertion — without it the commit could not have distinguished "the
fix works" from "the test never fired". The vector is now closed at both
layers.

### S4 — MED — Every CI action was a floating tag (finding F8, deferred here from P0.5)

**confirmed-by-reading**, remediation **confirmed-by-execution**

All 23 `uses:` were `actions/checkout@v4`, `actions/setup-go@v5`,
`actions/upload-artifact@v4`. A major tag is a mutable pointer controlled by
the action's publisher. Whoever controls that repository — or steals a
maintainer token, which is how both the `tj-actions/changed-files` and
`reviewdog` compromises worked — retargets the tag and immediately executes
code in every job of every workflow that follows it. Several jobs here run with
the repository checkout on disk, and one holds `contents: write`.

**Decision: pin.** The argument against pinning is that it freezes security
patches in the actions themselves. That argument is weaker here than usual:
these are three first-party GitHub actions performing checkout and toolchain
setup, their patch cadence is low, and the trailing-comment form keeps the
in-use version legible and makes Dependabot/Renovate able to bump them
automatically if either is ever enabled. Against that, an unpinned tag is a
live path from a third-party account to this project's release assets. Pinning
wins.

**Fixed** in `212f597`. All 23 are full commit SHAs with the release in a
trailing comment, resolved once from the API rather than recalled:

| Action | Pin | Version |
|---|---|---|
| `actions/checkout` | `11d5960a326750d5838078e36cf38b85af677262` | v4.4.0 |
| `actions/setup-go` | `40f1582b2485089dde7abd97c1529aa768e1baff` | v5.6.0 |
| `actions/upload-artifact` | `ea165f8d65b6e75b540449e92b4886f43607fa02` | v4.6.2 |

Each is the commit the corresponding major tag pointed at, so **no behaviour
changed** — this is a semantics-preserving pin, not an upgrade. (Majors v7/v7/v7
exist; deliberately not adopted in a review task.) The workflow header records
the one-line `gh api` command for bumping a pin. Verified after the edit that
no `@vN`, `@main` or `@master` reference remains.

### S5 — MED — `sha256sum -c` cannot detect an archive that no checksum line covers

**confirmed-by-execution**

Both packaging jobs verified checksums with `sha256sum -c SHA256SUMS.txt`, and
then uploaded `dist/*.zip` by glob. `-c` checks that every file the sums file
*names* matches; it says nothing about a `.zip` in `dist/` that no line covers.
`make release-windows` does not clean `dist/` first, so a stale archive from an
earlier version, or from a different build, would be published with no checksum
line at all — a user verifying "against SHA256SUMS.txt" would find no line for
it and have nothing to compare.

Demonstrated: I copied an archive under a second name into a `dist` replica.
`sha256sum -c` passed clean; the reverse-direction loop caught it immediately.

Hosted runners get a fresh checkout, so this was latent rather than live. It
becomes live on a self-hosted runner, on a re-run in a reused workspace, or for
anyone packaging locally before uploading.

**Fixed** in `212f597`: both jobs now assert coverage in both directions.

### S6 — MED — The release job would replace assets under an already-published release

**confirmed-by-reading**

```bash
if gh release view "$RELEASE_TAG" >/dev/null 2>&1; then
  gh release upload "$RELEASE_TAG" dist/*.zip dist/SHA256SUMS.txt --clobber
```

The design intent is a **draft** release that a human reviews and publishes.
But `gh release view` succeeds for a published release too, so re-running the
job on an existing tag — a manual re-run, a tag deleted and re-pushed —
silently swapped the assets of a live release, with new checksums, under
users who had already been told to trust the old ones. No human sees the new
build in that path.

**Fixed** in `212f597`: the job refuses to touch anything that is not still a
draft.

### S7 — MED — The documented install and verification commands named things that do not exist

**confirmed-by-execution** (the archive manifest) / **confirmed-by-reading** (the docs)

The task asked whether "the instruction in the notes matches what a user would
really find". It did not, in three places:

- `docs/windows.md` and `beta-release-notes.md` both said to run
  `.\scripts\install.ps1`. A release archive has no `scripts\` directory. Even
  after S1 is fixed, that command is a file-not-found.
- Both told users to hash `.\scratchpad-windows-amd64.zip`. No file by that
  name is ever produced; `mkrelease.go` names archives
  `scratchpad_<version>_windows_<arch>.zip`. This is the checksum instruction
  itself: a user copy-pasting the *documented verification step* gets "file not
  found", which is strictly worse than no instruction, because it teaches them
  the verification is broken and to skip it.
- `docs/windows.md` said "Every operation is idempotent — re-running is how you
  upgrade", without saying which verb upgrades what (see S10).

**Fixed** in `0fb8b8b` (paths and the archive-name pattern in `docs/windows.md`,
plus the install snippet in `beta-release-notes.md`) and in the coordinator's
`2a0a4f2` (the `beta-release-notes.md` "Verifying a download" section, which
P6.6's archive-cell work turned up independently — the same class of defect
found the same way, by checking the shipped artefact instead of the code that
describes it).

### S8 — MED — Nothing warned users about the execution-policy / Mark-of-the-Web wall

**confirmed-by-reading. The remediation is NOT verified — see below.**

The installer is an unsigned `.ps1`. Extracted from a downloaded zip it
normally carries the Mark of the Web, and Windows PowerShell 5.1's default
client execution policy is `Restricted`. The first thing many users will see
is *"cannot be loaded"* or *"running scripts is disabled on this system"* — a
security stop, with no guidance anywhere in the docs set.

That gap is a supply-chain problem, not a usability one. A user who hits an
unexplained block goes looking for a workaround, and the workarounds the
internet offers are `Set-ExecutionPolicy Unrestricted` machine-wide or
`irm <url> | iex`. Documenting the narrow fix is how you stop that.

**Fixed** in `0fb8b8b`: `docs/windows.md` now gives
`Get-ChildItem -Recurse -File | Unblock-File` plus a per-invocation
`-ExecutionPolicy Bypass`, states explicitly that nothing else needs to run,
that the installer downloads nothing, that there is no remote bootstrap
command, and that any instruction to pipe a URL into PowerShell should be
treated as suspect. `beta-release-notes.md` carries a pointer to it.

**Unverified, deliberately:** CI does not exercise the MOTW path. Hosted
runners execute steps with a permissive policy, and a job that manufactures a
`Zone.Identifier` stream would be testing my construction of the mark rather
than the real download. I pass `-ExecutionPolicy Bypass` in the archive job for
determinism, which means **CI proves the installer works once you are allowed
to run it, not that the documented unblock sequence is what a real download
needs.** That belongs in the pre-beta manual check.

### S9 — MED — Vendored third-party JavaScript has no recorded provenance

**partly confirmed-by-execution, partly UNVERIFIED**

`internal/web/assets/` contains three third-party files that are `go:embed`ded
into `scratchpad-web.exe` and served to every browser that opens the site:
`htmx.min.js`, `idiomorph-ext.min.js`, `sse.js`. None of them records an
upstream URL, a version, or a hash anywhere in the repository. Go module
dependencies are in good shape by contrast — three direct modules, a six-line
`go.sum`, and `go mod tidy -diff` gating drift in `linux-test` — but these
minified blobs sit entirely outside that.

The consequence is that nobody can answer "does published advisory X apply to
us?" without reverse-engineering a minified file, and a modified copy would be
invisible to review.

What I could verify:

- **`htmx.min.js` is byte-identical to upstream `htmx.org@2.0.10`.** I
  recovered the version string from the file, fetched that exact release, and
  the SHA-256 matched
  (`71ea67185bfa8c98c39d31717c6fce5d852370fcdfd129db4543774d3145c0de`).
  Confirmed authentic today.
- **`idiomorph-ext.min.js` and `sse.js` — UNVERIFIED.** Neither carries a
  version string. I tried a dozen plausible upstream releases of `idiomorph`
  and `htmx-ext-sse` and matched none (nearest by size was
  `htmx-ext-sse@2.2.3/dist/sse.min.js`, 2834 bytes against our 2853). That is
  **not** evidence of tampering — it is far more likely I did not guess the
  right version or build variant — but I could not establish provenance and I
  am not going to record a pass I did not earn.

**Not fixed.** The remedy is to record the upstream URL, version and SHA-256
for all three next to the files, and to re-derive them at review time. That is
a pre-existing, platform-independent gap, out of scope for a Windows packaging
task, and it is the wrong thing for me to guess at — someone who knows which
build these came from should write it down.

### S10 — LOW — `all` does not upgrade `scratchpad-web.exe`

**confirmed-by-reading**

The dispatch table is explicit: `all` is `Install-Cli; Install-Skill;
Remove-ObsoleteMcp`. Only `install` and `startup` call `Register-Startup`,
which is the only path that stops the task and re-copies `scratchpad-web.exe`.
Since the docs said "re-running is how you upgrade" without qualification, a
user who installed with `install` and upgrades with `all` gets a new CLI, a new
skill, and **the old server binary still running** — a silent version skew
between the two halves of a system that share an on-disk format.

**Fixed (documentation)** in `0fb8b8b`: `docs/windows.md` and
`beta-release-notes.md` now name which verb replaces which binary. The
installer behaviour is unchanged; making `all` stop a running server would be
a behaviour change outside a review's remit, and is arguably wrong anyway.

### S11 — LOW — Uninstall deletes the skill directories recursively, contents and all

**confirmed-by-reading**

`Uninstall-All` does `Remove-Item -Recurse -Force` on
`~\.claude\skills\scratchpad` and `~\.pi\agent\skills\scratchpad`. The
installer only ever puts `SKILL.md` there, but anything a user added alongside
it — notes, extra skill resources — goes too, without confirmation and without
being restored by a reinstall.

This does not contradict the data-root claim, which is specifically about
`%USERPROFILE%\.scratchpad` / `SCRATCHPAD_ROOT`, and it mirrors what the Unix
installer does. Recording it because "uninstall is non-destructive" is the
question I was asked, and the honest answer is *non-destructive to the data
root, and to everything else except these two directories*. Not fixed;
removing only `SKILL.md` and then pruning the directory if empty would be a
strictly better behaviour if anyone wants it.

### S12 — LOW — A `v*` tag on any commit produces draft release assets

**confirmed-by-reading. Not fixed — decision left to the operator.**

The `release` job gates on `startsWith(github.ref, 'refs/tags/v')` and
`--verify-tag`, which together prove the ref is a tag that exists on the
remote. Neither proves the tagged commit is reachable from `main`. A tag on a
feature-branch head, or on any commit in the repository, builds and uploads
official-looking assets.

Three things bound this: the release is a **draft** that a human must publish;
the job rebuilds from the tagged commit rather than trusting a cross-job
artifact, so the assets do match the tag; and it now `needs` the full gating
matrix including the archive-install job, so a tag on a broken commit cannot
produce assets at all.

I did not add an ancestry check (`git merge-base --is-ancestor "$RELEASE_TAG"
origin/main`) because tagging a release-candidate before merge is a legitimate
workflow and I cannot tell from here whether this project uses one. It is a
one-line addition if the operator wants it.

The related structural gap remains the one P0.5 raised and nobody can close
from inside this chain: **`main` has no branch protection rule**, so every
"gating" job in this workflow is advisory at the repository level. Making the
Windows jobs required is still a no-op until a protection rule names them.

### S13 — INFO — What the installer actually executes

**confirmed-by-execution** (grep over the script; archive manifest from a real build)

The direct answer to "do downloaded binaries need any arbitrary script
execution beyond the visible installer?" is **no**:

- The archive contains exactly nine entries: two `.exe`s, `install.ps1`,
  `skill/SKILL.md`, `README.md`, `LICENSE`, and three files under `docs/`.
  `mkrelease.go` re-opens each archive after writing it and fails on any
  unexpected name, so the manifest is enforced, not merely intended.
- `install.ps1` contains **no** network primitive at all — no
  `Invoke-WebRequest`/`iwr`, `Invoke-RestMethod`/`irm`, `DownloadString`,
  `DownloadFile`, `Start-BitsTransfer`, `System.Net.*` — and no
  `Invoke-Expression`/`iex`. It reads files out of the folder it was unzipped
  into and writes them under `%LOCALAPPDATA%`, `%USERPROFILE%` and
  `HKCU\Environment`.
- Two things it does execute, named for completeness rather than as concerns:
  `Add-Type` compiles an inline `SendMessageTimeout` P/Invoke to broadcast
  `WM_SETTINGCHANGE` after a PATH edit (in-process, from the visible script,
  wrapped in try/catch); and `drop-mcp` — part of the default `all` — runs
  `claude mcp remove` **if** a `claude` command is already on the user's PATH,
  resolved through `Get-Command`. That is the user's own installed CLI, and
  delegating to it is the right call given the alternative is rewriting its
  config file, but it does mean the default verb can invoke a third-party
  binary found on PATH.
- No elevation is requested anywhere, and no machine-scope registry key or
  machine PATH is written.

## The three gate questions, answered

**1. No arbitrary script execution beyond the visible installer.** **PASS**,
confirmed-by-execution — see S13. Caveat S8: users may first have to clear the
download mark, which is now documented but not CI-verified.

**2. Checksums are published.** **PASS**, confirmed-by-execution.
`mkrelease.go` emits `SHA256SUMS.txt` in coreutils format covering every
archive it built; the packaging job re-verifies with `sha256sum -c` **and**,
now, in the reverse direction (S5); the tagged-release job uploads it as a
release asset alongside the zips. The new Windows job re-derives every hash
with `Get-FileHash` — verbatim the command `docs/windows.md` gives users — and
compares it to the file: **8/8 assertions passed on both engines**, so the
published verification instruction is executed, not asserted. Two limitations,
both now stated in the docs: the sums file is **unsigned**, so it proves
integrity of transfer and not authenticity of the release; and the binaries are
**unsigned**, so SmartScreen and Defender will warn. `docs/windows.md` now says
both, and says the warning is expected rather than a sign of tampering.

**3. Uninstall is non-destructive.** **PASS**, confirmed-by-reading with
execution corroboration.

I was asked to check whether the existing evidence covers the claim rather than
reproduce it, so: the marker-file evidence is sound but narrower than the claim.
A byte-identical marker proves that one file was not modified or deleted; it
does not by itself prove nothing else in the data root was touched. The claim
holds because of the code, and the code is clean — `Uninstall-All` has no path
that can reach `$DataRoot`. It touches exactly `$BinDir` (the two `.exe`s, then
the directory if empty), the *default* bin parent and only when `-BinDir` was
not overridden, the `HKCU\Environment` PATH value (format-preserving, and a
no-op when no entry of ours is present), and the two skill directories. That
`$DataRoot` is computed at all is only so the closing message can name the
directory it did not touch. Marker survival then corroborates the reading, on
two roots including an overridden `SCRATCHPAD_ROOT`, on both engines.

Two qualifications: S11 (the skill directories go recursively), and an
uninstall run with a different `-BinDir` than the install used will leave the
old binaries and PATH entry behind — inherent to a script with no install
manifest, worth knowing.

**Lifecycle, which the gate does not name but the task asked for.** Upgrade
over an existing install is exercised by the new job (`cli`, then `skill`, then
`all` over the top) and by the pre-existing job's idempotence pairs. The
`Invoke-WithRetry` exe-lock handling on both copy and remove is real and was
proven under a live server by run `32970247103`. The gap was S10, now
documented. On leftovers: the new job runs `uninstall`, then `uninstall` again,
then a full reinstall, and asserts the reinstall succeeds and restores the
binary — so nothing uninstall leaves behind trips a reinstall.

## What I could not verify

Stated plainly, because this branch has been bitten by controls that were
owned, marked verified, and never actually evaluated.

1. **Mark-of-the-Web and default execution policy** (S8). The documented
   `Unblock-File` + `-ExecutionPolicy Bypass` sequence is review-verified only.
   CI runs with a permissive policy and passes `Bypass` explicitly. Needs the
   pre-beta manual check on a real downloaded archive.
2. **Provenance of `idiomorph-ext.min.js` and `sse.js`** (S9). Not matched to
   any upstream release I tried. `htmx.min.js` *is* verified byte-identical to
   `htmx.org@2.0.10`.
3. **The tagged-release path has never been executed.** The `release` job is
   `v*`-tag-gated and no tag has been pushed on this branch. Everything about
   it in this review — the tag guard, the draft check, the both-directions
   checksum step, `-require-installer`, `--verify-tag` — is confirmed by
   reading the workflow plus local reproduction of the injection and the
   uncovered-archive case. **The job itself has not run.** The first `v*` tag
   is the first execution, and it should be treated as such: cut it as a
   throwaway pre-release tag first.
4. **Signing and SmartScreen behaviour in practice.** Out of scope by decision,
   and no unsigned-binary first-run experience has been observed on a real
   machine.
5. **`arm64` archives are built and checksummed but never installed anywhere.**
   The new job extracts and installs the amd64 archive only; arm64 gets PE-magic
   verification in `mkrelease` and a native build job, not an install. The
   `windows-11-arm` runner is build-only in this workflow.
6. **Whether S1 would have shipped.** It would have — that is the point — but I
   cannot say whether the owed pre-beta manual check would have caught it
   first, since that check was written as "run `install.ps1 install` from an
   unzipped release" and would indeed have hit it. The failure is that the
   automated control claimed the coverage the manual check actually held.
