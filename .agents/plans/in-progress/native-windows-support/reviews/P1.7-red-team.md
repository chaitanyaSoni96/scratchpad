# P1.7 Red Team

## Verdict

**ACCEPT WITH CONDITIONS.**

P1.8's actual question is "does a race-resistant Windows strategy exist, or must
the port degrade to validate-then-reopen?" The answer is **yes, and the evidence
supports it**. Seven Linux primitives have measured Windows twins; the two
questions that could have killed the project (`OBJ_DONT_REPARSE` on intermediate
components, handle-relative atomic rename) resolved in favour of a workable
design; the two that resolved against the obvious approach (`LockFileEx` on a
directory, `os.Root` following in-root symlinks) each have a replacement that
preserves rather than trades away the property. The strategic decision in §2, the
rejection of `os.Root` in §8.1, the rejection of the spec's fallback in §8.2, the
refuse-by-default tag allowlist in §5, and the junction acceptance in §6.6 are
all, in my judgement, correct. **Do not stop the project.**

But the ADR **cannot be handed to Phase 3 as the implementation contract in its
current state**, for one reason that dominates all the others:

> The ADR was committed in `47248c3` — the very commit whose message reads
> *"correct R3 after the runner invalidated it"* and which introduced the
> **strict** traversal primitives to fix a `SECURITY-FAIL` — and the ADR still
> specifies the pre-fix mechanism in every place that matters. §2's mechanism
> table, §3.2's API list, §4.0's fact F-a, §4.2, §4.9's R3 row, §5.1's Scope B,
> §6.2 and §11's P3.1/P3.2 rows all describe `OBJ_DONT_REPARSE` as the
> containment primitive. The spike measured that it is **inert for
> non-Microsoft reparse tags** (`A5.obj_dont_reparse_inert_for_unknown_tags`,
> YES), and `internal/winspike/winfs.go` says so in a 20-line comment before
> defining the replacement the ADR never mentions.

More generally: **the ADR cites zero evidence from P1.3 and P1.5.** Every
measurement ID in the document is from the `M*`, `P12`, `P14`, `R13`, `RR1`, `R4`
families — the P1.2/P1.4 runs 1–5. There is not one `A1`–`A12` citation and not
one `P13.*` citation, although those 177 additional measurements include every
direct attack simulation, produced two `SECURITY-FAIL` verdicts that changed the
design, and contain the only **NO** verdict in the corpus that lands on a
containment question (`A11.ancestor_swapped`). §8.4's retry bound is visibly the
pre-P1.3 guess rather than P1.3's measured policy, which is the fingerprint of
the omission.

The corrections are cheap — every one of them already exists as working code in
`internal/winspike/`. Nothing here justifies stopping or rescoping. Six items
must land in the ADR before P1.8 signs it; nine more are recorded with owners.

**Recommended P1.8 action:** accept the ADR's *decisions*, require F1–F6 as
revisions to the *document* before it moves to `status: accepted`, and re-run
P1.7 against the revised §2/§3.2/§4.3/§4.5/§6.7/§9 only.

*One note on timing that sharpens all of this.* While I was writing, commit
`9dfa2c5` landed the P1.3/P1.5 write-up into `spike-findings.md`, and it records
**both** of my blocking findings independently — §10.1 titled *"WARNING —
`A11.ancestor_swapped`: containment BROKE"*, and §10.3 recording the R3
self-correction and the strict primitives. The ADR was not updated. So the
question in front of P1.8 is narrower and more tractable than it first looks:
the project's own evidence base and its own code already agree with this review.
What is stale is one document, and it is the one Phase 3 will be implemented
from.

## The A11 question, answered directly

The brief singled this out, so it gets its own section.

### Does the ADR address `A11.ancestor_swapped`?

**No. The string "A11" does not appear anywhere in the ADR.** It is a **NO**
verdict in the authoritative green run:

```
WINSPIKE|A11.ancestor_swapped|NO|an ANCESTOR of the watch target was replaced
with a junction between the reparse-buffer read and the open-by-name … the
attacker's tree was reached = true. THIS IS A REAL WINDOW AND IT IS
PLATFORM-INDEPENDENT: storefs_linux.go:184 re-opens the readlink result as an
ABSOLUTE PATH with O_NOFOLLOW, which likewise protects only the final component.
```

`A11.ancestor_swapped` is not a `RequireProperty`, so it does not fail the job:
it is a measured negative result sitting inside a green run, in the one corner of
the design the ADR calls "the one place this design re-resolves a PATH STRING".

**Confirmed independently, mid-review.** Commit `9dfa2c5`
(*"docs(windows): record the P1.3/P1.5 spike findings"*) landed while I was
writing, and `spike-findings.md` now carries this as **§10.1, "WARNING —
`A11.ancestor_swapped`: containment BROKE"**, with the security matrix row
*"Browse / target replacement — **Partial, and it is the one that found a real
gap**"*. The spike author and I reached the same conclusion from opposite
directions. That removes any doubt about the finding and sharpens the defect:
**the evidence document now records a broken containment case that the design
document does not mention at all.** The ADR is the artefact P1.8 accepts, and it
is the one that is wrong.

### Does the containment proof survive it?

**The design survives. The proof, as written, does not.**

§4.3's stated bound is wrong in two places:

- §4.3: *"open the target absolutely with `FILE_FLAG_OPEN_REPARSE_POINT` and
  require a plain directory — **so a link-to-a-link cannot chain**."*
- §4.3 / RW3: *"A2 can substitute the target — with a link (**refused by the tag
  check on the reopen**) or with a different real directory (accepted)."*

Both sentences are true only of the **final** component. `FILE_FLAG_OPEN_REPARSE_POINT`
protects the final component and nothing else — which the spike measured
independently and which the ADR itself quotes as `M1.weak_flag_traverses` when
arguing *for* `OBJ_DONT_REPARSE` two pages earlier. A reparse point at an
**ancestor** position of the target path is followed, and the attacker's tree is
reached. So RW3's "High / Accepted, enumerated" disposition rests on a bound that
does not hold, and F-a (§4.0) does not cover the one open in the whole design
that is not handle-relative.

I verified the prototype rather than trusting the finding text:
`openAbsoluteDirNoFollow` (`internal/winspike/winfs.go`) is
`CreateFile(path, …, FILE_FLAG_BACKUP_SEMANTICS|FILE_FLAG_OPEN_REPARSE_POINT)`
followed by a tag check on the resulting handle. One call, whole path, final
component only.

### Is the Linux code exploitable today, and how bounded really?

`storefs_linux.go`'s `openBrowsableDir`:

```go
next, openErr = unix.Open(string(buf[:n]), unix.O_RDONLY|unix.O_DIRECTORY|unix.O_CLOEXEC|unix.O_NOFOLLOW, 0)
```

`O_NOFOLLOW` protects the final component only. So yes — **structurally
exploitable today on Linux**, and three details make it slightly worse than the
finding text says:

1. **It is not a race.** The finding stages it as a TOCTOU because the spike
   needed a deterministic hook, but the store never validates the watch target's
   ancestors *at all* — not at watch time, not at browse time. Any ancestor that
   becomes a symlink at any point after `watch` is followed on every subsequent
   browse, indefinitely. There is no window to lose.
2. **A1 can reach it, not only A2.** The threat model bounds this by "the
   attacker already needs write access above the user's watched folder". That is
   right for a plain filesystem attacker, but a watched **git repository** is the
   canonical case, and `git checkout` creates symlinks. A branch that replaces
   `docs/` with a symlink, in a repo whose `docs/.scratchpad` is watched, turns a
   `git switch` into a browse redirect. That is A1 territory (content in the
   watched source), not A2.
3. **The payoff is over the network.** The redirected tree is served by an
   unauthenticated HTTP endpoint. Under `LAN=1` it is readable by anything on the
   network.

The bound that *is* real: the attacker must arrange for the remaining path
suffix to exist under the redirect, and the result is a **read** disclosure — no
mutation reaches through this path, because every mutation walk is
`openRealDir`, which is handle-relative end to end and refuses reparse points at
every component. So: **High severity as a proof defect, Medium as a live
exposure, and genuinely platform-independent.**

### Two things the ADR must add beyond recording it

- **The reopen has no absoluteness requirement.** §4.3 refuses a substitute name
  beginning `\??\Volume{` and nothing else. `ReadLinkHandle` in the prototype
  **never reads the SYMLINK reparse buffer's `Flags` word** (offset 8 in the
  body), so a `SYMLINK_FLAG_RELATIVE` link's substitute name — e.g. `..\..\Users`
  — is returned verbatim, `stripNTPrefix` passes it through unchanged, and
  `CreateFile` resolves it **against the process working directory**. The store
  only ever creates absolute links, but Scope A forgives links the store did not
  create, by design. `readlinkAt` must reject a relative `SYMLINK` and require
  the stripped target to be absolute and drive-rooted, using the same validator
  §4.1 applies to `Root()`.
- **The structural fix is available and its cost should be stated.** Walking the
  target's components handle-by-handle with the strict primitive closes A11
  completely. It also refuses a target whose ancestor is a *legitimate* junction
  or volume mount point — a real compatibility cost on Windows (Dev Drive mounts,
  redirected `%USERPROFILE%`) that does not arise on Linux. The ADR should make
  that trade explicitly rather than leave the weaker behaviour as an unstated
  default.

**Required actions:** record `A11.ancestor_swapped` in the ADR (it is now in
`spike-findings.md` §10.1); correct §4.3's two false sentences and RW3's bound;
add the absolute/drive-rooted/non-relative requirement to `readlinkAt`; choose
and justify a disposition for the ancestor case. Owners: ADR §4.3 / §6.9 / RW3,
then **P3.4**.

## Findings, by severity

### BLOCKING — must be fixed in the ADR before P1.8 accepts it

#### F1. The ADR's containment primitive is the one the spike falsified. *(Critical)*

`A5.obj_dont_reparse_inert_for_unknown_tags` (**YES**, run 9), quoted in full:

> THREAT-MODEL CORRECTION: for a NON-MICROSOFT tag the WITH-flag and WITHOUT-flag
> opens return the SAME status (`STATUS_IO_REPARSE_TAG_NOT_HANDLED`, 0xC0000279),
> whereas for the junction they differ (refused vs traverses). OBJ_DONT_REPARSE
> therefore does NOTHING for an unknown tag: the open is refused because no filter
> driver claimed the tag, not because we asked not to reparse. On a machine that
> HAS the driver — Windows Containers (WCI\*), VFS-for-Git (PROJFS\*), a vendor
> filter — the same open would be SERVICED and the walk would traverse. **R3
> stated as 'OBJ_DONT_REPARSE on every component' is NECESSARY AND NOT
> SUFFICIENT.**

This is not a hypothetical. Run 7 (`32906333884`) recorded
`A5.unknown_tag_refused` as a **`SECURITY-FAIL`**, which is the harness's
"the runner contradicted a property the Windows backend must have" verdict. The
fix landed in `47248c3` as `openStrictAt` / `OpenRealDirAt` / `OpenRealFileAt`:
one `NtCreateFile` with `FILE_OPEN_REPARSE_POINT` (which bypasses reparse
processing for *every* tag, driver or no driver) plus `FILE_ATTRIBUTE_TAG_INFO`
read from **that same handle**, refusing anything tagged. One operation, one
check, one object — no check-then-use, no dependence on installed drivers. Six
REQUIRED properties now rest on it: `A5.strict_open`, `A5.unknown_tag_refused`,
`A5.strict_open_admits_real_dirs`, `A5.strict_walk`, and
`A3.nested_strict.{symlink,junction}_boundary/*`.

The ADR, added in the same commit, describes none of it. The word "strict" does
not appear anywhere in it. (`spike-findings.md` §10.3 now records the whole
correction, as of `9dfa2c5` — so, as with F2, the evidence document is right and
the design document is not.) §3.2 literally specifies the weak primitive:

```go
func openDirAt(parent int, name string) (int, error)  // FILE_OPEN|FILE_DIRECTORY_FILE|OBJ_DONT_REPARSE
```

and §11's P3.2 row says *"`openRealDir` over `openDirAt`+`mkdirClaim`"*. A Phase 3
author implementing §3.2 literally would ship the falsified primitive.

§5.2 **knows the fact** — it says *"On a machine that has the driver … the open
succeeds and the `IsDir() == true` classification is the entire defence"* — but
draws the wrong conclusion. For `openRealDir` and `openBrowsableDir`,
classification is never consulted: the walk's entire defence *is* the open
failing. §5.2's answer applies to listing and delete, not to traversal, and the
ADR never makes that distinction.

Exploitability is not established (I could not measure whether a driver-serviced
tag can be created unprivileged with an attacker-chosen redirect — see
*Could not verify*), but that is irrelevant to the decision: the fix is one extra
flag plus one `GetFileInformationByHandleEx` per open, it is already written and
measured, and it removes a dependency on which filter drivers happen to be
installed on the user's machine — Docker Desktop and VFS-for-Git being ordinary
developer software.

**Required.** Rewrite §2's mechanism table, §3.2's API list, §4.0's F-a, §4.2,
§4.9's R3 row, §5.1's Scope B, §6.2 and §11's P3.1/P3.2/P3.4 rows around the
strict open. State plainly that `OBJ_DONT_REPARSE` is retained as a cheap
intermediate-component filter for Microsoft tags and is **necessary and not
sufficient**. Cite `A5.*` and `A3.nested_strict.*`. Owners: ADR, then **P3.1,
P3.2, P3.4**.

#### F2. `A11.ancestor_swapped` — see the dedicated section above. *(High)*

#### F3. §4.5's recursive delete is weaker than the prototype's, on the RR1 critical path. *(High)*

§4.5 prescribes:

> `removeTreeAt` walks by handle: `readDirFD` for entries, `statAt` per entry for
> classification, recurse only into `IsDir` (attribute set **and** no tag)

That is classify-then-open. The prototype deliberately does not do it, and says
why in its own doc comment:

> The rule here replaces the classification with an operation: attempt the
> no-follow directory open FIRST; **its FAILURE is the classification**. Nothing
> is decided from a separately-observed attribute, so there is no check-then-use
> window at all … This is strictly stronger than classify-then-open, and **it is
> the shape Phase 3 should copy**.

`A6.swap_midwalk` is a REQUIRED property that exists precisely to exercise the
window the ADR's version reopens — an ordinary subdirectory swapped for a
junction *between the enumeration and the descent* — and `A6.negative_control`
demonstrates that the mechanical classify-then-recurse port **destroys the
external target tree** on the same fixture. RW1 is the ADR's own Critical risk
and its declared hard release gate. Specifying the weaker algorithm for it is the
single most consequential drafting error in the document after F1.

(Note that `RemoveTreeAt` uses `OpenRealDirAt` — the strict primitive — so F1 and
F3 are the same correction applied in two places.)

**Required.** Replace §4.5's algorithm with the operation-as-classification
shape; keep `statAt` for reporting only. Owner: ADR §4.5, then **P3.9**.

#### F4. The ADR does not incorporate P1.3 or P1.5 at all. *(High)*

Zero `A*` citations, zero `P13.*` citations. The evidence rule (§29–31) and §12
say *"192 measurements, five CI runs … 17 REQUIRED security properties"* — that
is run 5's state. The authoritative run 9 is **369 measurement lines, 91 distinct
`RequireProperty` ids**, after **two intervening runs that failed with
`SECURITY-FAIL`** (runs 7 and 8). "Zero `SECURITY-FAIL`" is true of run 9 and
materially incomplete as a summary of the corpus: two of them occurred, and one
of them (F1) changed the design.

The fingerprint is §8.4. It states the retry bound as *"10 attempts, exponential
backoff 1/2/4/…/64 ms, ~250 ms total"*. The prototype's `DefaultReplacePolicy`
and `P13.bound` say **10 attempts, 2 ms → 256 ms, 771 ms observed, 2 s
wall-clock ceiling** — the bound was widened in `47248c3` and the ADR quotes the
number from before. Anyone sizing an HTTP timeout off §8.4 would be off by 3×.

Other P1.3 evidence the ADR should be resting on and is not:

- **§4.8's durability paragraph is marked `[UNMEASURED]`.** `P13.flush_cost`
  (INFO) measured it: 811 µs/op without `FlushFileBuffers` vs 4.594 ms/op with,
  5.7×, with the explicit recommendation not to flush by default because Linux
  does not `fsync` either. The ADR's decision is right; its "no measurement
  exists" is wrong.
- **`P13.change_records` was withdrawn (NO), but its replacement is stronger than
  "code review is now the only guard."** `P13.continuous_existence` is a REQUIRED
  property: a concurrent reader polled the destination through 200 replaces and
  observed "does not exist" **0 times in 1902 polls**, while the deliberately
  wrong `removeThenRenameUNSAFE` was caught **1902 times out of 3441**. That is a
  black-box discriminator with a proven-failing negative control. Together with
  `P13.no_dest_removal` (the namespace-removal audit) it is a better guard than
  the change-record instrument would have been, and it belongs in R9's row.

**Required.** Re-base the evidence rule on run 9; record runs 6–9 and the two
`SECURITY-FAIL`s honestly; correct §8.4's numbers; replace §4.8's `[UNMEASURED]`
durability note with `P13.flush_cost`; cite `P13.continuous_existence` /
`P13.no_dest_removal` under R9. Owner: ADR §Evidence rule, §4.8, §8.4, §9, §12.

#### F5. The annotation rendezvous is materially weaker than Linux, and RW5's parity claim is false. *(High)*

RW5 says the residual is *"cross-process rendezvous lost if `.annotations` is
replaced between two processes' opens"* and justifies it: *"Linux has the same
shape of gap"*. It does not.

- **Linux** (`annotations.go:117-129`): `lockAnnotations` flocks
  `ann.storeRoot` — the **store root directory inode**. Losing the rendezvous
  requires replacing the *store root*, which needs write access to the root's
  parent.
- **ADR Windows** (§6.7): the rendezvous is `.annotations\.lock`, reached root →
  `.annotations` → `.lock`. Losing it requires replacing **either** `.annotations`
  **or** `.lock` — both of which live *inside* the store, one hop from where a
  same-user process is already writing. That is a strictly larger and much
  cheaper surface, and the store's own comment (`annotations.go:124-126`) names
  `.annotations` being renamed away as precisely the case the root inode was
  chosen to survive.

Worse, the ADR's supporting evidence does not support the claim. §6.7 argues the
property is *"preserved by the handle, not by the location"* and cites
`M7.namefollows` and `R13.rename`. Both measure **rename** survival. The hazard
is **deletion and re-creation**, which is unmeasured and which Windows makes
trivial — because **R15 requires `FILE_SHARE_DELETE` on every handle**. The
design's own mandatory share mode is what makes the rendezvous object deletable
out from under its holder, silently, with no error on either side. A handle
survives a rename; it does not survive a swap, and after a swap two processes
hold locks on two different objects and both believe they are excluded.

The ADR then rejects a root-level lock file on cosmetic grounds — *"adds a second
reserved name to the store's visible namespace"*. `Visible`'s reserved-name check
(`ignore.go:378`) is a single `if rel == "." && name == AnnotationsDir` line; a
second reserved name is a one-line change and is invisible to the user by
construction. A real security property was traded for a cosmetic one, with a
false parity claim doing the justifying.

For the rest of §6.7 I found no defect: `LOCKFILE_FAIL_IMMEDIATELY` + bounded
retry is the right answer to `M14.mandatory` (a *hung* holder must not be waited
on; a *crashed* one is released by the kernel on close), and mandatory-ness is
genuinely harmless here because the locked range belongs to a file nobody ever
reads. The ordering rule (root → `.annotations` → `.lock`, all pinned before any
lock is taken) does close RR6 between `Delete` and `SaveNotes` **in the normal
case** — which is the case that matters. The gap is the swap, not the ordering.

**Required.** Correct RW5's parity claim. Then either (a) re-validate the lock
object's `FILE_ID_INFO` after acquiring the lock by re-opening `.lock` relative to
the pinned `.annotations` handle and comparing, dropping and retrying on
mismatch under a bound; or (b) move the rendezvous to a root-level reserved lock
file so only one object, one hop from the pinned root, can be swapped. Keep
P3.12's racing test either way. Owners: ADR §6.7 / RW5, then **P3.7, P3.12**.

#### F6. R16's error-triage half is unowned, and it is a non-adversarial availability bug. *(Medium-High)*

§4.9 marks **R16 "yes | §6.8"**. §6.8 delivers the depth bound and the
identity-keyed visited set. R16's third clause — *"a `reconcile` failure is
triaged into 'retry' versus 'fatal' rather than being uniformly fatal"* — is not
in §6.8, is not in §11's P4.1/P4.2 row (which covers only the `M15.overflow`
mapping, RW12), and has no owner anywhere in the document.

Traced end to end, that clause is load-bearing on Windows in a way it is not on
Linux:

- `cmd/scratchpad-web/main.go:49`: `log.Fatalf("watcher stopped: %v", err)`.
- `watch.go:79`: `reconcile()` also runs at **startup**, and its error is fatal
  there too.
- `desiredDirs`' `walk` returns a hard error from `os.Open(dir)` for anything
  that is not `os.IsNotExist`.
- A non-Microsoft or unserviced reparse-tagged directory returns
  `STATUS_IO_REPARSE_TAG_NOT_HANDLED` → Win32 **1920**, which is not `NotExist`.

So a single such directory inside the store or a watched tree kills the web
process **and prevents it from starting again**. That is a boot loop, not the
"supervisor restarts it" framing RR9 is rated Medium on. And it needs no
attacker: an `APPEXECLINK` (observed live in `WindowsApps`, `M2.appexeclink`), a
OneDrive placeholder (`M2.cloud`, NOT MEASURED — Windows 11 puts Documents and
Desktop there by default), or a ProjFS entry in a watched repo are all ordinary
objects on ordinary machines. RW13 rates cloud placeholders Low-Medium and worries
about rehydration cost; nobody connected them to the fatal path.

**Required.** Assign reconcile error triage to P4.2 explicitly; correct §4.9's
R16 row to "partial, triage unowned" until it is; restate RR9/RW13's disposition
in terms of a persistent failure to start rather than a transient restart.
Owners: ADR §4.9 / §11 / RW13, then **P4.2**.

### Recorded with owners — not blocking P1.8

#### F7. §6.9's "three surviving path re-resolutions" is already incomplete by the ADR's own text. *(Medium)*

§6.9 exists so that *"P3.13's trace review can find zero **unlisted** ones."* As
written that criterion is unmeetable, because the ADR itself introduces more:

- **`statLinkTarget(path string)`** (§3.2, and binding via Pre-1) is path-based
  and is described self-contradictorily as *"convert `entryIsDir` … to a
  **no-follow** classification via `statLinkTarget`"* against §3.2's
  *"**bounded one-hop follow** for listings"*. Which it is decides whether
  `entryIsDir` can be redirected; the ADR does not say.
- **`annotate`'s `os.Lstat(a.Dir)`** survives §6.8 item 2 untouched. Item 2 says
  annotate takes "the *logical* store-relative path", but a store-relative path
  cannot be `Lstat`ed, and the ADR never says where `IsLink` then comes from
  (it should be `statAt(parentFD, name)`).
- **`WatchLinkFor(rel)`** (§6.8 item 3) is an *n*-`os.Lstat` path walk replacing
  one `EvalSymlinks`. It is the right change — `EvalSymlinks` does not resolve
  junctions (`M5.junction`), so the old test reports `Linked == false` for every
  junction-watched tree and the card offers **Delete** where it must offer
  **Unwatch** — but §6.8 presents the whole item as making the read path
  *"strictly more anchored"*, and this sub-item is not: it swaps one path-based
  test for another.
- **`Watches()`'s `hasHTML(sub)` and `os.Stat(sub)`** are not mentioned anywhere.

Also worth naming in Pre-1: `RR1.unknown_tag_isdir` (NO) shows a non-surrogate
tag makes `DirEntry.IsDir()` **true**, so `entryIsDir`'s *first* line
(`if e.IsDir() { return true }`) is unsafe and `IsLinkEntry`'s over-approximation
never gets a chance to save it. The ADR names the second trap in that function
and not the first.

**Owner:** ADR §6.9 / Pre-1, then **P3.6, P3.13**.

*(Pre-1's ordering argument itself is correct and valuable — I checked it against
the code. Fixing `IsLinkEntry` alone really does convert today's fail-closed skip
into a path-based `os.Stat` descent through the junction. Landing
`TestJunctionIsClassifiedAsLink` first so CI enforces the ordering is the right
call.)*

#### F8. The two-step link window: the interlock is fine to defer, but rule 3 is not true yet. *(Medium)*

On the brief's question — is it acceptable to ship an **UNMEASURED**
`FILE_DELETE_ON_CLOSE` interlock in the accepted design? **Yes**, and P1.8 should
not require it be measured first. The ADR frames it correctly: it is a belt on
top of rule 3, rule 3 is unconditional, and §6.6 already says *"If it does not
hold, rule 3 alone carries the case"* with P3.1 named as the owner. That is how
an unmeasured optimisation should be carried.

But **rule 3 does not currently work**, on three counts I verified in the code:

1. **The recovery instruction is false.** Rule 3's message is *"delete it in the
   web UI and retry"*. `internal/web/templates/list.tmpl`'s folder card renders a
   `delete` button **only** inside `{{with .Unwatch}}` — a plain directory with no
   watch link has no delete affordance at all. Widening `store.Delete` (RW19)
   does not create one. RW19 must state that the UI half is part of the change.
2. **The junction path does not self-heal.** §6.6 rule 1 says *"On
   `FSCTL_SET_REPARSE_POINT` failure, POSIX-delete the just-created directory …
   The prototype already does this (`links.go`'s `SymlinkAt`)."* True of
   `SymlinkAt`; **`CreateJunctionAt` has no cleanup at all** — and per the ADR's
   own privilege table, junctions are the *only* flavour available to an
   unprivileged, Developer-Mode-off user, i.e. exactly the population most likely
   to hit the window. Neither function cleans up when the post-claim reopen
   fails, only when the FSCTL does.
3. **"Through the handle already held" is not implementable as specified.**
   `SymlinkAt`'s cleanup is `DeleteAt(parent, name, …)` — a **re-open by name**,
   not a handle disposal. To do what §6.6 says, the post-claim reopen must
   request `DELETE` access; it currently requests `FILE_GENERIC_WRITE|FILE_GENERIC_READ`.

Separately, the spike's own recovery recommendation (`A7.two_step_recovery`) was
to let **`unwatch`** clear an empty real directory; the ADR chose **`Delete`**
instead. I think the ADR is *right* — `unwatch` is agent-reachable and `Delete` is
user-only, so the ADR's choice preserves the create-only-for-agents asymmetry —
but it diverges from the recorded recommendation without saying so.

**Owner:** ADR §6.6 / RW19, then **P3.1** (measure the interlock), **P4.3**
(flavour probe and cleanup), **P4.6** (the UI affordance).

#### F9. The R12 override quietly guts R13, and root *removal* is undecided. *(Medium)*

§10.2 overrides R12 from a process-lifetime pin to a per-operation pin. The
justification (a process pin makes `t.Setenv` impossible and adds no property
within an operation) is sound, and I agree with the override.

But the consequence for R13 is not stated. Under a per-operation pin,
`verifyRoot()` compares the root's identity against a value recorded *microseconds
earlier in the same operation* — a case that F-b already makes harmless. It
cannot see a replacement **between** operations, which is the case R13 was
written for ("silently operating on the wrong store"). §4.1's *Weakness* comes
close to admitting this but lands on "the check exists to turn silently operating
on the wrong store into a loud error", which is the one thing it cannot do. §4.9
nonetheless marks R13 **"yes"**.

`A4.root_removed` (INFO) is a second undecided case the ADR is silent on, and its
finding text says so explicitly:

> removing the pinned root while a handle is open → nil ; a subsequent `MkdirAt`
> through the handle → `STATUS_DELETE_PENDING` ; **`Verify()` → nil**. Windows
> keeps the object alive for the open handle, so the store keeps working against
> a directory that is no longer reachable by name — **the ADR must decide whether
> that is acceptable**.

A cheap fix covers both: keep a process-level last-seen `objectID` keyed on the
resolved root **string**, and compare on each `openRootedFS`. Different string
(the `t.Setenv` case) → new entry, no error. Same string, different identity →
the loud error R13 was written to produce.

**Owner:** ADR §4.1 / §4.9 / §10.2, then **P3.1**.

#### F10. §10.1 overrides a spec clause it did not need to override. *(Low — but it shrinks what P1.8 must approve)*

§10.1 and §12 present junction acceptance as requiring an override of the spec's
*"created and identified by the application under an explicitly accepted design"*,
on the ground that identification is unachievable. The unachievability argument
is **correct** — a store-created junction is byte-for-byte identical to an
attacker's, and any sidecar registry would be attacker-writable and consulted as
a check-then-use. I tried to break it and could not: the reparse buffer's
`PrintName` is equally forgeable, and there is no authenticated channel.

But the spec answers this itself, 6 lines later:

> The phase-zero spike **may recommend application-created junctions as a
> fallback** if they can preserve all containment and unwatch guarantees without
> elevation. That fallback must be explicit and tested, not silently selected for
> arbitrary reparse points. — spec, *Reparse points and watch semantics*

The ADR's design satisfies that clause literally: containment preserved
(`P14.unlink_junction`, `P14.delete_descend`, Scope A/B/C), unwatch guarantees
preserved, no elevation, an explicit allowlist rather than arbitrary tags. **No
override is needed.** What *does* need overriding is invariant 5's "exactly one
**store-owned** watch link" — "store-owned" is unverifiable for exactly the reason
§10.1 gives. Retargeting the override there makes the ask smaller and more
accurate.

**On the junction decision itself I concur, plainly.** The parity argument holds:
A1 (content in the watched source) cannot plant a link in the store's namespace
at all, and A2 planting one is content creation indistinguishable from the user
running `scratchpad watch`, which the Linux code already forgives without asking
who made it. Everything an attacker gains from junctions — RR1, RR2, §3.11's
wrong-button-on-the-card — is closed by tag-aware classification, which the design
needs whether or not we ever create one. Rejecting junctions would buy nothing and
would remove `watch` from every Developer-Mode-off machine.

One residual to record: under `LAN=1`, a reparse point in the store namespace is
an **exfiltration** primitive, not merely a local read — it converts a
filesystem-write capability into network-readable content. The acceptance is
configuration-dependent and the README/release notes should say so alongside
RW8's *"watch only trees you trust"*.

**Owner:** ADR §10.1, §12 item 2, RW6, RW8.

#### F11. Prototype code review. *(Low)*

I traced every early return in `winfs.go`, `links.go` and `atomicwrite.go`.

**Handle lifetimes are correct.** Every `ntOpenAt` success is closed on the
success path and on every error path; `OpenRealDir`, `OpenBrowsableDir`,
`OpenRealDirStrict` and `openStrictAt` all close the previous level before
replacing it, matching `storefs_linux.go`'s ordering; `ReadDirHandle` duplicates
before handing the handle to `os.NewFile` so the `*os.File`'s `Close` cannot
consume a caller's anchor; `AtomicWriteFile`'s `done` switch correctly prevents
the deferred cleanup from deleting the *destination* after a successful rename
(the one place a naive `defer` would destroy exactly what was just written).
`unsafe` is confined to layout construction and `renameBuffer` carries the
64-bit `HANDLE` compile guard. I found no leak.

**The claimed atomicity survives reading the code.** `AtomicWriteFile` is
create-temp → write → `RenameAtNT(FileRenameInformationEx, RootDirectory=parent,
REPLACE|POSIX)` with a class-10 fallback gated on
`isUnsupportedRenameClass` — narrow, and correctly excluding real failures. No
path degrades to remove-then-rename: the destination is never named by a removal,
which the namespace-removal audit (`P13.no_dest_removal`, REQUIRED) proves
mechanically, and `removeThenRenameUNSAFE` is unexported and exists only as the
negative control.

Smaller items for **P3.1/P3.8**'s checklist:

- **Unchecked `uint16` truncation, three sites.** `ntOpenAt`'s
  `us.Length = uint16((len(u16)-1)*2)`, and `SetMountPointRaw`/`setSymlinkReparse`'s
  `SubstituteNameLength` / `PrintNameLength` / `ReparseDataLength`. A long target
  silently produces a malformed buffer rather than a clean error. `maxReparseSize`
  (16 KiB) is defined but never enforced on the write side.
- **`windows.Write(src, data)` ignores the returned count.** No short-write loop,
  where the Linux original's `os.File.Write` guarantees full-write-or-error.
- **`RemoveTreeAt` has no depth bound**, although R16 names `removeTreeAt`
  specifically. Pre-existing on Linux; carry it forward deliberately or fix both.
- **`DirObserver.Close`'s backstop goroutine** can block on `CloseHandle`
  indefinitely and leak the handle. Instrument-only, deleted with the package.
- **`OpenBrowsableDir` is stricter than Linux on one path** and should stay that
  way: it requires `DirHasHTML` to *succeed* before forgiving the boundary, where
  `storefs_linux.go` treats a read error as "no HTML" and forgives. §4.3 says the
  Linux guard is "preserved"; preserving the fail-open half would be a small
  regression against the prototype.

#### F12. RW1's release gate is unenforceable today. *(Low)*

RW1 declares the "Delete / target replaced" matrix cell a hard gate before any
Windows binary ships. `MATRIX.Delete.target_replaced` is **YES** in run 9, so the
property holds. But EXECUTION.md already records that `main` has **no branch
protection rule**, so "required check" is a no-op at the repository level. A
release gate that no mechanism enforces is a note, not a gate. Operator action,
already tracked; worth repeating here because RW1 is the ADR's own top risk.

#### F13. `internal/winspike/` is deleted at the end of Phase 1 and its assertions have no migration plan. *(Low-Medium)*

The A-series and P13-series properties exist **only** in the spike package. §11's
P3.12 row names the six hooks and the RW5 racing test; RW1 gates on one matrix
cell. Nothing covers `A5.*` (F1's proof), `A6.swap_midwalk` + `A6.negative_control`
(F3's proof), `A3.nested_strict.*`, `A11.*`, `A10.rename_race`, `A12.*`,
`P13.continuous_existence` + its negative control, or `P13.no_dest_removal`'s
audit. Several of them are the *only* evidence that the corrected design differs
from the naive one, and several carry a working negative control — which is the
part that is expensive to rebuild and easy to lose.

**Required action:** an explicit inventory in §11 mapping each spike property to
the `internal/store` test that inherits it, landing **before** winspike is
removed. Owner: **P3.11 / P3.12**.

## What I could not verify

1. **Anything requiring a Windows host.** I have none. Every code judgement above
   is by reading; every measurement is a read of the CI log for run 32908643117.
   I ran no Go test on any platform.
2. **The whole unmeasured set carries forward unchanged**, and I found no reason
   to disagree with the ADR's dispositions for any of it: ReFS/Dev Drive
   (`M1.refs_smb`, RW9/P6.6), SMB/UNC, FAT32, cloud placeholders (`M2.cloud`,
   RW13/P4.6), antivirus transient distribution (`M13.av`, RW10/P6.1),
   `ReadDirectoryChangesW` overflow (`M15.overflow`, RW12/P4.2), a genuinely
   non-elevated session (RW16/P5.5), 32-bit Windows (excluded).
3. **F1's exploitability.** `M4.noprivilege` shows an *unserviced* non-Microsoft
   tag can be created unprivileged. Whether a **driver-serviced** tag (WCI,
   PROJFS, a vendor filter) can be created unprivileged with an attacker-chosen
   redirect is not measured and I could not determine it. F1's severity therefore
   rests on the falsification of the design claim, not on a demonstrated exploit.
   The fix is cheap enough that this should not change the conclusion.
4. **Whether `FILE_DELETE_ON_CLOSE` permits `FSCTL_SET_REPARSE_POINT` on the same
   handle**, and whether `FileDispositionInformation{DeleteFile: FALSE}` clears a
   create-time delete-on-close — the ADR's own `[UNMEASURED]`, correctly flagged.
5. **Whether Go's `os.Open` grants `FILE_SHARE_DELETE`** in the pinned toolchain.
   This matters for R15 in `internal/watch`'s `desiredDirs`, which uses `os.Open`
   rather than a store primitive. Worth one grep in P4.1.
6. **`spike-findings.md` was being edited concurrently** by another agent
   appending the P1.3/P1.5 write-up; it landed as `9dfa2c5` during this review
   (563 → 1163 lines). I re-read the committed version. It now records runs 6–9
   including both `SECURITY-FAIL`s, re-bases §9–§11 on run 9, and carries **both**
   of my top findings independently: §10.1 (`A11.ancestor_swapped`, "containment
   BROKE") and §10.3 (the R3 self-correction and the strict primitives). §§1–8
   still carry run 5's tally. **All findings above are against the ADR**, which is
   committed, stable, and was *not* updated by `9dfa2c5` — the evidence document

7. **The P2.7 preconditions.** I read the review and agree Pre-1/Pre-2/Pre-3 are
