# P3.14 Implementation Red Team

## Verdict

**PASS WITH FINDINGS.**

I read the code, not the execution notes. The mechanism layer is the strongest
part of this port. Specifically, and each independently confirmed by tracing
every call:

- **No handle leak.** I checked every `NtCreateFile`/`CreateFileW`/
  `DuplicateHandle` in the five Windows production files against every early
  return, `break`, `defer` and recursive call. Every acquisition is closed on
  the success path and on every error path; there is no double-close, no
  close-then-use, no leak in a loop, and no `*os.File` handed out without an
  owner. `atomicWriteFileAt`'s `done` switch is correct in both directions —
  the handle is closed exactly once on the success path (`return f.Close()`)
  and exactly once on every failure path (the defer), and it never deletes
  the destination after a successful rename.
- **No remove-then-rename degradation.** `atomicWriteFileAt` is
  create-temp → write → `NtSetInformationFile(FileRenameInformationEx,
  RootDirectory=parent, REPLACE|POSIX)` with a class-10 fallback gated on a
  four-status allowlist. The destination name is never passed to any removal
  primitive anywhere in the write path. Since `P13.change_records` withdrew the
  watcher-detection hypothesis, this review *is* the guard; it holds.
- **Recursive deletion is open-then-classify-from-the-handle**, not
  classify-then-open. `removeTreeAtDepth` (`annotationfs_windows.go:735`) opens
  with the strict primitive first and treats the *failure* as the
  classification, and the prototype's negative control
  (`removeTreeAtByAttributeUnsafeForTest`) was migrated rather than dropped.
  `A6.negative_control`'s property survives the port.
- **Error translation does not turn a refusal into a silent success.** Nothing
  maps to `fs.ErrNotExist` that is really permission or reparse.
  `STATUS_REPARSE_POINT_ENCOUNTERED` and `STATUS_OBJECT_NAME_COLLISION` both
  reach `errExists` through `translateClaim`, and `Watch`'s idempotence hangs
  off the *reparse* branch (`errExistsReparse`), which is the correct one per
  `M8.claim_error_map`. `STATUS_IO_REPARSE_TAG_NOT_HANDLED` is handled
  alongside it, which the ADR only asked for defensively.
- **`unsafe` and the ABI are sound on both arches.** The four hand-rolled
  structures have correct offsets and identical layout on amd64 and arm64; the
  64-bit `HANDLE` assumption is a compile-time assertion that I verified
  actually fires (`GOARCH=386` fails the build with the intended message).

Four findings are worth acting on before release, three of them Medium. None is
a containment break. That is why this is PASS WITH FINDINGS rather than FAIL —
but **M1 and M2 are user-visible wedges with no recovery path**, and M2 was
introduced by this work, so neither should ship as-is.

## Findings

### M1 — `symlinkAt`'s post-claim reopen failure leaves a permanently wedged name. ADR §6.6 rule 1 requires the cleanup that is missing, and P4.3's commit message says the gap is closed. *(Medium)*

`internal/store/link_windows.go:91-99`

```go
func symlinkAt(parent int, target, name string) error {
	if err := mkdirClaim(parent, name); err != nil {
		return err
	}
	h, err := ntOpenAt(windows.Handle(parent), name, ...|windows.DELETE, ...)
	if err != nil {
		return translateOpen("open new link", err)   // <-- the claimed directory is left behind
	}
	defer windows.CloseHandle(h)
```

`mkdirClaim` has already created a real, empty directory at `name`. If the
reopen fails, that directory stays. The FSCTL branch below (`:111-114`) does
self-heal through the handle; the reopen branch has no handle to heal through
and does not fall back to the by-name `rmdirAt` rollback that `Publish` uses at
`store.go:742` for exactly the same shape.

The ADR names this precisely, as a revision-2 correction, in §6.6 rule 1:

> **Neither cleans up when the post-claim *reopen* fails**, only when the FSCTL
> does. Both failure points leave the same wedged empty directory.

Owner is listed as **P4.3**, which has landed (2c97384). That commit's message
states the reopen gaps "were already closed in link_windows.go's unified
`symlinkAt` … now covered by a test rather than only by reading the code." Two
of the three §6.6 rule-1 gaps are indeed closed (the junction flavour shares the
cleanup; the reopen requests `DELETE`). The reopen-*failure* gap is not, and the
test that is supposed to cover rule 1 —
`watchlink_windows_test.go:TestSymlinkAtSelfHealsOnFSCTLFailure` — injects its
fault via `checkedNameLen`, i.e. at the FSCTL step, so it never exercises this
branch.

**What an unlucky user experiences.** The reopen requests
`FILE_GENERIC_WRITE|FILE_GENERIC_READ|DELETE` on a directory created
microseconds earlier. Realistic failures: an inherited *Deny Delete* ACE on the
store root in a managed environment (`STATUS_ACCESS_DENIED`), or a scanner /
indexer / Explorer holding the new directory (`STATUS_SHARING_VIOLATION`). The
first `scratchpad watch` fails; every retry then hits `mkdirClaim` →
`errExists` → `readlinkAt` → `ERROR_NOT_A_REPARSE_POINT` → the "already exists
as a directory, not a watch link … delete it and retry" message. The name is
consumed until the user runs `scratchpad delete` by hand. On Linux `symlinkat`
is one atomic call and this failure mode does not exist, so this is a
Windows-only reliability regression.

**Fix.** One line, matching `Publish`'s own rollback:

```go
	if err != nil {
		_ = rmdirAt(parent, name) // rule 1: the claim must not outlive the failure
		return translateOpen("open new link", err)
	}
```

`rmdirAt` refuses a non-empty directory and never follows a link, so the
rollback cannot destroy content even if the name was substituted in the window.
Add a fault-injection test on the reopen (the `runStoreOpHook` mechanism already
in this package is the obvious vehicle) so rule 1's *second* failure point is
covered, not only its first.

### M2 — the store creates artifact trees it then refuses to delete, forever. Introduced by P3.9's depth bound. *(Medium)*

`internal/store/annotationfs_windows.go:731-734` and its twin
`internal/store/annotationfs_linux.go:224-227`; no matching bound in
`ValidateFilePath` (`store.go:684`), `mkdirsAt` (`storefs_windows.go:689`) or
`writeFileAt`.

`removeTreeAtDepth` returns a hard error past `maxArtifactWalkDepth` (64).
Nothing bounds *creation* to the same depth: `ValidateFilePath` validates each
segment but never counts them, and `mkdirsAt` walks as deep as it is told. The
two halves disagree, and the disagreement is one-directional.

I could not run this on Windows, so I reproduced it on Linux in an isolated copy
of the tree — the control flow is character-for-character the same on both
backends (`Delete` at `store.go:1112` is untagged shared code, and both
`removeTreeAtDepth`s carry the identical bound and the identical
`readErr = err; break`):

```
published OK; maxArtifactWalkDepth=64
after publish:  74 entries, max depth 71
Delete #1 -> scratchpad: "d" exceeds the maximum artifact tree depth (64)
after delete #1: 74 entries, max depth 71
Delete #2 -> scratchpad: "d" exceeds the maximum artifact tree depth (64)
List() -> 1 artifacts
```

Reproduced 3/3. There is no partial destruction — the recursion errors on the
way *down*, before any removal — which is the one mercy here. But the artifact
is undeletable through the CLI and the web UI, permanently, and no retry can
ever finish. It stays listed, stays previewed, and stays on disk. The user's
only remedy is a manual `rmdir /s` outside the tool, which is exactly the "the
web UI is where deletion happens" contract this store is built around.

Reachable through `scratchpad publish -dir` of any deep source tree (a
`node_modules`, a vendored SDK, a deep monorepo path), or by an agent handing
`Publish` a file path with 65+ segments. Note that `sizeWalkAt` and `List`
already tolerate the same bound gracefully (they just stop counting) — deletion
is the only walk that turns the bound into a hard error.

**Fix**, in preference order:

1. Bound creation to agree with removal: reject a publish whose file path
   exceeds `maxArtifactWalkDepth` segments in `ValidateFilePath`, with a clear
   message. This makes the invariant "the store never creates what it cannot
   remove" true by construction, and it is the only fix that also covers a
   `cp -r` that arrives another way (which still needs (2)).
2. Make the removal bound non-fatal: past the bound, keep descending but stop
   *only* if the walk fails to make progress. Because `removeTreeAtDepth` never
   follows a reparse point on Windows and never follows a symlink on Linux, the
   cycle risk that motivates R16 for *browsing* does not exist for a no-follow
   removal — the recursion is already bounded by the filesystem's own path
   limit. R16's bound is doing less work here than it appears to.

Whichever is chosen, add a shared (untagged) regression test; the current suite
has no deep-tree delete case on either platform.

### M3 — every `FILE_CREATE`/`FILE_OPEN_IF` in the package relies on `OBJ_DONT_REPARSE` alone — the exact primitive `A5` proved inert for non-Microsoft tags. The strict-open discipline covers only `FILE_OPEN`. *(Medium, defence-in-depth)*

Six sites, none carrying `FILE_OPEN_REPARSE_POINT`:

| site | disposition |
|---|---|
| `storefs_windows.go:292` `mkdirClaim` | `FILE_CREATE` |
| `storefs_windows.go:726` `writeFileAt` | `FILE_CREATE` |
| `annotationfs_windows.go:536` `atomicWriteFileAt` temp | `FILE_CREATE` |
| `annotationfs_windows.go:159` `openRendezvousLockFile` | `FILE_OPEN_IF` |
| `annotationfs_windows.go:249` `openLockFileAt` | `FILE_OPEN_IF` |
| `link_windows.go:92` `symlinkAt` (via `mkdirClaim`) | `FILE_CREATE` |

ADR §2.1 is unambiguous that `OBJ_DONT_REPARSE` is "necessary and NOT
sufficient", and `A5.obj_dont_reparse_inert_for_unknown_tags` measured why: for
a non-Microsoft tag, the flag does nothing, and what refuses the operation on a
bare CI runner is `STATUS_IO_REPARSE_TAG_NOT_HANDLED` — *"no driver claimed this
tag"*, not *"we asked not to reparse"*. On a machine that **has** a driver
servicing the tag (ProjFS / VFS-for-Git, Windows Containers' WCIFS, a vendor
filter — the "watched repository" population, precisely), the reparse is
serviced and the operation is reissued at the driver's target.

The port applied the fix — `FILE_OPEN_REPARSE_POINT` plus a tag read from the
handle — to `FILE_OPEN` only (`openStrictAt`, `storefs_windows.go:244`). There
is no equivalent for the create dispositions, and neither the ADR nor the code
says why. §6.6's error table treats an unknown tag on a `FILE_CREATE` claim
purely as an error-mapping question ("`STATUS_IO_REPARSE_TAG_NOT_HANDLED` from a
claim → also `errExistsReparse` … **[UNMEASURED]**"), never as a *traverse*
question. That is the gap.

`FILE_OPEN_REPARSE_POINT` is legal with `FILE_CREATE` and does exactly what is
wanted: an existing reparse point at the name collides
(`STATUS_OBJECT_NAME_COLLISION`) instead of being resolved through. This is not
speculative — it is what the Go standard library does for the same purpose, with
the same reasoning, in `os.Root`'s O_EXCL claim
(`$GOROOT/src/internal/syscall/windows/at_windows.go:129-131`):

```go
	case flag&(syscall.O_CREAT|syscall.O_EXCL) == (syscall.O_CREAT | syscall.O_EXCL):
		disposition = FILE_CREATE
		options |= FILE_OPEN_REPARSE_POINT // don't follow symlinks
```

and again in its `Symlinkat` (`:541`), which combines `FILE_CREATE` with
`FILE_OPEN_REPARSE_POINT` in one call.

**Impact, honestly bounded.** The compensating controls are real and I want them
on the record rather than overstating this:

- `Publish`: a traversed `mkdirClaim` is caught one line later by `openDirAt`
  (`store.go:740`), which *is* strict — so the operation fails and no file
  content is written. Residue: an empty directory created at the driver's
  target, and the rollback `rmdirAt` removes the attacker's link rather than
  that directory.
- `openAnnotationFS`: same shape, same catch at `openRealDirAt`.
- `writeFileAt`: **not** caught. A serviced unknown tag planted at a file name
  inside a just-created artifact directory captures the write — an arbitrary
  file write as the server account. Multi-precondition (a servicing driver plus
  a race inside a directory we created empty microseconds earlier), but this is
  the one site with no backstop.
- `openRendezvousLockFile` / `openLockFileAt`: the rendezvous ends up on an
  object outside the store, silently defeating the annotation lock.
- `atomicWriteFileAt`'s temp: unguessable random name, not plantable.

**Fix.** Add `windows.FILE_OPEN_REPARSE_POINT` to `options` at all six sites,
and state in `win32_windows.go`'s header that the strict-open discipline covers
create dispositions too — the flag is the whole fix there, since a create cannot
open-then-classify. Cost is zero and it also makes the claim error
deterministically `STATUS_OBJECT_NAME_COLLISION`, simplifying `translateClaim`'s
reparse branch to pure defence in depth.

### L1 — `ntOpenAt`'s "single path component" guard does not reject `.` or `..`. *(Low)*

`internal/store/win32_windows.go:113-115`

```go
	if name == "" || strings.ContainsAny(name, `\/`) {
```

`..` is syntactically one component and passes. Relative to an
`OBJECT_ATTRIBUTES.RootDirectory` anchor it walks *up*, out of containment — the
one direction the whole design exists to prevent. The doc comment two lines
above claims this check exists "because every containment argument in this
package depends on no walk ever handing the kernel more than one component of
attacker-reachable structure at a time", which `..` violates in spirit while
satisfying the letter.

Not currently reachable: `validateName` (`store.go:138`) and `validateSegment`
(`store.go:153`) both reject `.` and `..`, and every caller goes through one of
them or through `os.DirEntry.Name()` (Go never yields `.`/`..`). So this is a
defence-in-depth gap in the primitive that is supposed to be the last line, not
a live hole. Go's own `Deleteat` special-cases `name == "."` for exactly this
reason.

**Fix.** `if name == "" || name == "." || name == ".." || strings.ContainsAny(...)`.

### L2 — `NTUnicodeString.MaximumLength` can truncate to zero while `Length` is `0xFFFE`. *(Low)*

`internal/store/win32_windows.go:121-131`. The F11 bound is `nameBytes > 0xFFFF`,
but `nameBytes` is always even, so `0xFFFE` passes — and then
`MaximumLength: uint16(len(u16) * 2)` computes `uint16(0x10000)` = `0`, i.e. a
string claiming 65534 bytes of content in a 0-byte buffer. The F11 fix removed
the *silent* truncation from `Length` and left a smaller one in
`MaximumLength`. Unreachable (names are ≤100/255 chars), but the check is
explicitly defensive. **Fix:** bound at `0xFFFD`, or compute
`MaximumLength: uint16(nameBytes + 2)`.

### L3 — the four hand-rolled OS structures carry no `structs.HostLayout`. *(Low)*

`attrTagInfo` (`win32_windows.go:170`), `fileIDInfoRaw` (`:192`),
`reparseHeader` (`:218`), and `watch/identity_windows.go:43`'s `fileIDInfo`.
Offsets are correct today on amd64 and arm64 — I verified each against the
Windows headers — and Go's current layout rules make them correct. But
`structs.HostLayout` is the marker Go 1.23+ added precisely to *promise* that,
and the Go standard library now uses it on this exact class of struct (see
`at_windows.go`'s `reparseDataBufferT`). This file's entire premise is
auditable, guarded ABI; adding the marker costs one line each and makes the
guarantee real rather than conventional.

### L4 — `skipWalkError` uses `os.IsNotExist`, the predicate that already produced one Windows bug in this tree. *(Low)*

`internal/watch/identity_windows.go:159`. `os.IsNotExist` does not walk an
`Unwrap` chain — which is exactly the defect `annotations.go:276` documents at
length after it bit `loadNotesRaw` on Windows. It happens to work here because
the errors reaching it are bare `syscall.Errno` or `*os.PathError`, both of
which `os.IsNotExist` handles. It stops working the moment anything wrapped (a
`*winError`, or a future `fmt.Errorf("%w")`) reaches this function. The very
next line already uses `errors.Is(err, fs.ErrPermission)`. **Fix:** make it
`errors.Is(err, fs.ErrNotExist)` for consistency and durability.

### L5 — test-only audit instrumentation is compiled into the shipped Windows binary and takes a global mutex on every entry removal. *(Low)*

`internal/store/annotationfs_windows.go:663-691`. `writeAuditMu`/`writeAuditOn`/
`writeAuditLog`/`writeAuditStart`/`writeAuditStop` are used only by
`annotationfs_windows_test.go`, and `recordNamespaceRemoval` (called from
`deleteEntryAt:640`, i.e. once per *file* in every tree removal) takes an
unconditional `sync.Mutex` even when disarmed. The Linux backend has no
equivalent, so the "mechanically equivalent port" claim is weaker here than
elsewhere. This package already has the right pattern one file over:
`runStoreOpHook` (`store.go:31`) is a nil-checked function pointer with the
setter in a `_test.go`. **Fix:** move the audit globals and the two
start/stop functions into the `_test.go`, leaving a nil-checked
`var recordNamespaceRemoval func(string)` hook (or nothing at all) on the
production path.

### L6 — `serveMarkdown` is dead code that reads a store document by path. *(Low)*

`internal/web/markdown.go:85-101`. No production caller — only the handle-based
`serveMarkdownFile` is wired up (`server.go:867,896`). But it is still compiled,
and it does the two things this design forbids: `os.ReadFile(path)` re-resolves
a document from a string, and on Windows `os.Open`'s share mode omits
`FILE_SHARE_DELETE` — `P13.go_share_mode` verbatim. Its `?raw=1` branch is
`http.ServeFile`, which is worse on both counts. Delete it before someone wires
it up in good faith.

### L7 — `Delete` collapses every failure into "not found", and Windows widens that error space considerably. *(Low, shared code — flagged for P3.13/P4.7 rather than owned here)*

`internal/store/store.go:1106,1110`. Any `openDirAt` failure becomes
`"artifact %s not found"`. On Linux that is nearly always genuine. On Windows the
same line now absorbs a reparse refusal on any of ~30 tags, `STATUS_SHARING_VIOLATION`
from a scanner, `ERROR_CANT_ACCESS_FILE` from an unserviced ProjFS/cloud entry,
and `fs.ErrPermission`. The user sees "not found" for something the folder page
is still rendering. `winError` already carries the NTSTATUS for exactly this
purpose; nothing surfaces it here.

## What I could **not** verify

1. **Anything requiring Windows execution.** I have no Windows host. Every
   claim above is code reading plus cross-checking against the Go 1.27 runtime
   sources on disk and the spike's own measurement table. CI run 32962872576 is
   green across all nine jobs, but green CI is evidence the tests pass, not that
   the untested branches behave.
2. **M3's premise, directly.** That a *serviced* non-Microsoft reparse tag
   causes a `FILE_CREATE` to traverse rather than fail. `A5` established the
   OPEN half; no runner has a third-party filter driver, and
   `MATRIX.EXCLUDED` says so. The ADR's own `[UNMEASURED]` on
   `STATUS_IO_REPARSE_TAG_NOT_HANDLED`-from-a-claim is the same blind spot from
   the other side. The recommended fix is correct regardless of which way the
   measurement lands, which is why I recommend it without the measurement.
3. **Whether `-count=20` would catch a handle leak. It would not — and nothing
   else would either.** Two independent reasons: (a) 20 iterations of a package
   suite leak tens of handles at worst, against a per-process kernel-handle
   ceiling in the millions, and no test asserts a handle count; (b) more
   fundamentally, because *every* handle in this package grants
   `FILE_SHARE_DELETE`, a leaked handle does not block a rename or a delete, so
   a leak has **no functional symptom at all** on this codebase — it is silent
   by construction. The stress job's real value is race and ordering coverage.
   If "no leaked handles under repeated tests" is to remain Phase 3 exit
   evidence, it needs an actual instrument: a Windows-only `TestMain` (or a
   `t.Cleanup` helper) sampling `GetProcessHandleCount` before and after and
   failing on unbounded growth. I found no such instrument
   (`grep GetProcessHandleCount` → nothing).
4. **Wildcard characters in a lookup segment.** `checkLookupSegmentPlatform`
   (`names_windows.go:91`) refuses `:`, trailing dot/space and DOS device
   basenames. It does **not** refuse `*`, `?`, `"`, `<`, `>` or `|`, and
   `validateSegment` allows them. `scratchpad delete '*'` and a URL segment `a*b`
   therefore reach `NtCreateFile` with a wildcard in `ObjectName`. I believe
   `NtCreateFile` rejects these with `STATUS_OBJECT_NAME_INVALID` (wildcards are
   an `NtQueryDirectoryFile` concept), which would make it a clean 404 — but I
   could not verify it, and P3.12's attack matrix covers ADS syntax and reserved
   names without covering this. Cheap defensive fix: add them to
   `checkLookupSegmentPlatform`, which already exists for exactly this class of
   Windows-only name ambiguity. Cheaper still: measure it in P3.12.
5. **DEDUP / WOF under the strict open** (the ADR's own §5.4 exclusion). If a
   WOF-compressed `.html` sets `FILE_ATTRIBUTE_REPARSE_POINT`, `openRealFileAt`
   refuses it and the document 404s on a compressed volume. `attrTagInfo.isReparse`
   is a bare attribute test with no tag allowlist on the *file* path, so the
   outcome hinges entirely on that bit.
6. **The `ERROR_CLOUD_FILE_*` skip set** in `identity_windows.go:182-211`
   (`M2.cloud`, explicitly not measurable on a runner). The list is by name
   rather than by range, which is the right call; whether it is *complete* is
   unverified, and an omission there is a watcher boot loop, not a skip.
7. **arm64 at runtime.** `windows-arm64-build` is build-only and
   `winspike.yml`'s arm64 job covered the *spike* package, which is being
   deleted. The production `internal/store` suite has never executed on arm64.
   All ABI in `win32_windows.go` is architecture-identical and both arches
   build and vet clean locally, so I expect no difference — but "expect" is the
   operative word, and Phase 3's exit evidence does not distinguish the arches.
8. **M1's likelihood, as opposed to its existence.** The reopen failing on a
   normal machine depends on ACL inheritance and scanner behaviour I cannot
   sample. The gap is real and ADR-required regardless of how often it fires.

## Build and tag checks (all clean)

- `GOOS=windows GOARCH=amd64 go build ./... && go vet ./...` — clean.
- `GOOS=windows GOARCH=arm64 go build ./... && go vet ./...` — clean.
- `GOOS=windows GOARCH=386 go build ./...` — fails as designed:
  `win32_windows.go:37:41: cannot use [8]byte{} (value of type [8]byte) as
  [4]byte value`. The 64-bit `HANDLE` assertion is real, not decorative.
- `go build ./... && go vet ./...` (linux) — clean.
- Every file's build tag audited: `internal/store` is `linux`-or-`windows` only,
  with `names_linux.go`/`names_windows.go` a true pair; `internal/watch` splits
  `unix`/`windows`; `internal/testutil` and `internal/winspike` carry matching
  `!windows` companions. **No Windows-only symbol is reachable from a Linux
  build or vice versa, and no `_test.go` breaks either platform.** The one
  structural note: `internal/store` will not build on darwin or any BSD, which
  is intentional but undeclared — a `//go:build linux || windows` guard file
  with a clear compile error would be kinder than four "undefined:" errors.
