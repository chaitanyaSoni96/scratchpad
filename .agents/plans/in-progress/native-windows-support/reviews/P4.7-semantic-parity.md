# P4.7 Semantic Parity Review

## Verdict

**PASS WITH FINDINGS — but the documentation half fails acceptance criterion 9.**

The behavioural port is good. I compared every user- and agent-facing surface
across the two platforms — CLI exit codes and message text, name handling,
watch semantics and `watches` output, ignore rules, the web UI's tiles and
affordances, notes ordering/ids/`rev`/malformed handling, the watcher, and a
store carried from one platform to the other — and found **no divergence that
changes what a correct operation does**. Publish, list, delete, notes,
markdown, previews, SSE, watch and unwatch behave the same way on both
platforms for every input that is legal on both. Exit codes were **not**
loosened for Windows: every assertion in `cmd/scratchpad/main_e2e_test.go` is
a literal integer with no `runtime.GOOS` branch anywhere in the file.

Nine of the divergences that do exist are unavoidable consequences of NTFS or
of Win32 (case folding, junctions, reserved device names, reparse-tag
refusal, sharing-violation retries, UNC/device-namespace refusal). Six are
avoidable, and two of those are the reason this is not a clean pass:

- **P-1a (High, documentation).** `docs/windows.md` and `docs/internals.md`
  both state, unconditionally, that a watched repository's `CON`-named entry
  "stays reachable and deletable". On Windows it is neither:
  `checkLookupSegmentPlatform` (`names_windows.go:52`) refuses a reserved DOS
  device basename in **every lookup segment**, and
  `TestValidateSegmentAcceptsDeviceNames` asserts exactly that refusal. Two
  user-facing documents say the opposite of what the code and its own test do.
- **P-2 (High, documentation).** Case-insensitivity — the single most
  user-visible Windows divergence, touching publish collisions, URL
  resolution, ignore rules and the `.annotations` reserved name — appears in
  **no** user-facing document. `docs/ignore-rules.md`, which is where the
  `matchName` platform pair actually lands, does not mention platforms at all.

The remaining avoidable findings are P-3 (a permission error is a logged skip
on Windows and a fatal process exit on Linux — the boot loop the ADR fixed on
one platform only), P-4 (junction-flavour watch links, the default for an
ordinary Developer-Mode-off user, have zero coverage in `internal/web` and
`internal/watch`), P-5 (`internal/watch` canonicalises the two watch-link
flavours differently), and P-6 (three Windows containment primitives and two
`readlinkAt` refusal branches have no direct test where their Linux twins do).

On the specific question the task raised: **no, a user never sees an 8.3 short
name where Linux would show the real path.** `Watch` stores
`GetFinalPathNameByHandleW(VOLUME_NAME_DOS)`, which `M6.resolution` measured
is long-name canonical, and that is the string `readlinkAt` returns and
`Watches` prints. The `watch` command's own confirmation line echoes the
argument the user typed — on both platforms — so that is parity, not
divergence.

## Findings

Ranked by severity. P-1a, P-1b, P-2, P-3, P-4, P-5, P-6, P-9 and P-10 are the
**avoidable** ones — the real output of this review.

### P-1a — HIGH (documentation, Windows-only). Two documents state the exact opposite of the shipped lookup rule

`docs/windows.md`, "Naming":

> Names the store merely **looks up** stay looser, so a watched repository that
> already contains a folder called `CON` remains reachable and removable.

`docs/internals.md:118-123`:

> …the portable-name rule deliberately does not apply there, so an entry a
> watched repository already named `CON` stays reachable and deletable.

Both are false on Windows. `internal/store/names_windows.go:52` refuses a
reserved DOS device basename in any lookup segment; `validateSegment`
(`store.go`) calls it on every URL segment, every `delete`/`unwatch` name and
every notes doc path. `TestValidateSegmentAcceptsDeviceNames`
(`names_test.go:117`) asserts the rejection under `runtime.GOOS == "windows"`
and the acceptance elsewhere, so the test suite and the docs disagree about
the same sentence.

The history is visible in the tracker: P2.5 deliberately kept
`checkPortableName` out of `validateSegment` precisely because tightening it
"would make a watched repository's own `CON`-or-similar-named entries
unreachable and undeletable through scratchpad, which is a regression, not a
hardening" (EXEC:254-258) — and then P3.13 F-2's remediation shipped exactly
that tightening on Windows via `checkLookupSegmentPlatform` (EXEC:1533-1546).
The docs were written against the P2.5 wording and never revisited.

**Ruling: the behaviour is unavoidable** (§6.10's `M18.relative_open.*`
records that the handle-relative primitive fails closed for these anyway, so
relaxing the check would not make such an entry reachable — it would only
change which layer refuses). **The documentation is a defect.** Both sentences
need a Windows carve-out, and `docs/cli.md`'s "Lookups of what already
exists … validate looser than publish" paragraph needs the same.

**Owner:** P6.4 (docs), or whoever next holds `docs/` scope.

### P-1b — MEDIUM (behaviour, pre-existing shape, Windows-widened). Entries the UI lists but every lookup path refuses

`List`, `Watches` and `internal/web`'s card builders classify entries with
`Visible` + `classifyEntry` and **never** call `validateSegment`. Every lookup
path does. So any name that is visible-but-unaddressable produces a card and a
`scratchpad list` row that 404s when clicked and cannot be removed.

On Linux the class is narrow: a name containing a backslash (`mkdir 'a\b'`),
a control character, or over 255 bytes. On Windows it widens to every reserved
DOS device basename and every name with a trailing dot or space — and these
are *reachable in practice*, because WSL and other NT-native tools create them
freely on NTFS and a Windows developer's watched source tree is exactly where
they turn up.

Concretely: a directory named `aux` holding an `index.html` in the store root
is listed by `scratchpad list` with a working-looking URL, drawn as a card by
the folder page, 404s on click, and `scratchpad delete -name aux` fails with
`invalid path segment "aux"`. There is no way to remove it through scratchpad.

This is the same *shape* as RW15 (an unknown-tag entry that is invisible and
un-removable, still deferred to P4.6) arriving from a different cause, and it
argues for the same fix. `docs/ignore-rules.md` already states the doctrine
this violates: **"Hidden means unreachable, not merely unlisted."** The
converse — listed means reachable — should hold too.

**Fix (either):** (a) route listing through `validateSegment` so an
unaddressable entry is not advertised; or (b) render it as the inert
"unsupported entry" tile RW15 already asks for, with an explanation, and give
`delete` a lookup path that can reach it.

**Owner:** P4.6 (UI half) / P6 (store half). Rules out of P4.7's own scope; I
am filing it, not fixing it.

### P-2 — HIGH (documentation). Case-insensitivity is in no user-facing document

NTFS case folding changes four things a user or agent will hit:

1. `publish -name Report` then `publish -name report` fails on Windows and
   succeeds on Linux. The failure message quotes the spelling the caller
   typed (`"report" already exists`), not the one on disk (`Report`), which is
   the confusing half of an otherwise clear error.
2. `GET /a/REPORT/` resolves on Windows and 404s on Linux — every open in the
   backend carries `OBJ_CASE_INSENSITIVE`, and `visibleSegments`' `os.Stat`
   folds too. The spec's Compatibility Policy promises "logical URL paths
   retain the actual directory spelling returned by the filesystem";
   `ResolvePath` sets `a.Name` from the **URL segment**, so the promise is not
   kept for a hand-typed case variant. (Generated links always carry the disk
   spelling, because they come from `ReadDir`.)
3. Ignore rules fold — including `!` negations, so a Windows user's
   `.scratchpadignore` un-hides more than the same file does on Linux.
4. `nameEquals` folds the reserved-name guard, so a Windows user cannot have a
   top-level directory whose name folds to `.annotations` or
   `.scratchpad-lock`.

Items 1, 3 and 4 are **unavoidable**; item 3 is not merely unavoidable but
*required* (P3.13 F-2 showed the unfolded version left `.SSH`, `key.PEM`,
`Node_Modules` served on NTFS). Item 2's *spelling* is avoidable — either
normalise to the filesystem spelling (a `301` to the canonical path is the
cheap version) or amend the spec sentence.

None of this appears in `docs/windows.md`, `docs/cli.md`, `docs/ignore-rules.md`,
`docs/notes.md`, `README.md` or `skill/SKILL.md`. `docs/ignore-rules.md` is the
document the `matchName` pair actually belongs in and it does not mention
platforms at all.

**Owner:** P6.4, plus a spec amendment or a `ResolvePath` change for item 2.

### P-3 — MEDIUM (behaviour, the *Linux* side is the worse one). A permission error is a logged skip on Windows and a fatal exit on Linux

`internal/watch/identity_windows.go:126-211` skips and logs `fs.ErrPermission`,
`ERROR_SHARING_VIOLATION`, `ERROR_LOCK_VIOLATION` and the reparse/ProjFS/cloud
families. `internal/watch/identity_unix.go:61` skips `os.IsNotExist` and
nothing else. Everything not skipped propagates out of `desiredDirs` →
`reconcile` → `newWatcher` and is fatal to `scratchpad-web` by design.

So a single unreadable directory anywhere under the store root — a `chmod 000`
build artifact, a root-owned directory in a watched repo, an
`EPERM`-on-`openat` case — prevents the Linux web server from starting at all,
under systemd it becomes a restart loop, and the user gets no site. On Windows
the identical condition costs one subtree's live refresh and a log line.

This is the *exact* boot loop ADR §6.11 exists to fix, fixed on one platform
only. The Windows implementation's own comment concedes the point:

> `fs.ErrPermission`: an ACL the server's account cannot read. **Not a
> platform-specific finding**, but grouped here because Windows's default ACL
> surface makes it far more likely to be hit by an ordinary, non-adversarial
> entry than Linux's mode bits are.

"More likely on Windows" is an argument about frequency, not about which
behaviour is correct. Two behaviours, one correct.

**Fix:** add `fs.ErrPermission` (and, defensibly, nothing else) to
`skipWalkError` on Linux, with the same "logged skip, root stays strict"
discipline. Keep root fatal on both, as EXEC:1026-1034 decided.

**Owner:** P6 (this is a Linux behaviour change and needs its own regression
test; it is out of the Windows phases' scope but should not be lost).

### P-4 — MEDIUM (coverage). The junction flavour — the default for an ordinary Windows user — has zero coverage in `internal/web` and `internal/watch`

`docs/windows.md`'s own table says Developer Mode **off** is the case that
produces a junction, and `errNoLinkPrivilege` is unreachable in practice
(EXEC:1908-1925), so a junction is what `watch` produces on any ordinary,
non-Developer-Mode, non-elevated Windows machine. That is the majority
configuration.

`internal/store` covers it reasonably (`TestWatchOverExistingJunctionIsNoOp`,
`TestWatchViaJunctionIsListedAndUnwatchable`,
`TestRemoveTreeAtLeavesJunctionTargetIntact`,
`TestPublishAncestorReplacedWithJunctionOrUnknownTag`,
`TestPublishSurvivesRootReplacedWithJunctionMidOperation`, plus row 3 of
`TestDegradedModeWithPrivilegeGenuinelyRevoked`). `internal/web` and
`internal/watch` cover it **not at all**: all three web link tests and all four
watcher link tests gate on `testutil.RequireSymlinks` and have no junction
twin. Nothing anywhere exercises browsing a watched folder over HTTP, the
folder card's unwatch affordance, the SSE refresh, or watcher registration
through a junction.

The primitive to fix this already exists and is dead code:
`testutil.RequireWatchLinks` / `WatchLinkCapable`
(`internal/testutil/watchlink_windows.go`) has **zero call sites** in the tree,
and `SCRATCHPAD_TEST_WATCH_LINKS` is set by no workflow. Its own doc comment
says a full migration "is a deliberately separate, larger change … and is not
attempted here." This finding is that change coming due.

The template for doing it right is also already in the tree:
`TestSaveNotesDestinationReplacedWithLinkNeverEscapes` splits a `/junction`
subtest (which runs in degraded mode) from a `/dirsymlink` subtest (which
skips).

**Owner:** P4.6 / P6.1.

### P-5 — MEDIUM (behaviour, Windows-only, reasoned not measured). `internal/watch` canonicalises the two link flavours differently

`internal/watch/watch.go:295` `canonicalDir` is `filepath.EvalSymlinks`. Go
1.27's `walkSymlinks` (`$GOROOT/src/path/filepath/symlink.go:85-93`) resolves
a component only when `fi.Mode()&fs.ModeSymlink != 0`, and continues past
anything else that `IsDir()`. Since Go 1.23, `os.Lstat` reports a junction as
`ModeDir|ModeIrregular` and **not** `ModeSymlink` — which is exactly what the
ADR measured (`P14.junction_modesymlink`, `P14.junction_not_dir`) and what
`link_windows.go`'s `IsLinkInfo` is built on.

Consequence: for a **symlink** watch link, `desiredDirs` registers the watched
tree under its **source** path (matching Linux); for a **junction**, it
registers it under its **store-side** path. Two behaviours inside one platform,
and only the one Linux shares is tested.

The user-visible cost is small — `Hub.Broadcast` carries no paths, so the SSE
refresh is identical — but it is not zero:

- the canonical-path dedupe (`if _, seen := dirs[canonical]; seen`) that
  collapses one source directory watched under two names does not fire for
  junctions, so one directory gets two `ReadDirectoryChangesW` registrations;
- `skipEntry`'s log lines and `desiredDirs`' error text name a different path
  than the same failure names on Linux.

**Fix:** canonicalise through a junction-aware primitive (`os.Readlink` does
resolve `IO_REPARSE_TAG_MOUNT_POINT`, or the store's own handle-based walk)
rather than `EvalSymlinks`.

**Confidence:** reasoned from the Go 1.27 sources on disk plus the ADR's own
measurements. I have no Windows host and did not observe it. If a P4.2 owner
disagrees, the cheap disproof is one junction-flavoured
`TestDesiredDirsFollowsWatchLink…` — which P-4 asks for anyway.

### P-6 — MEDIUM (coverage, spec AC5). Windows containment primitives with no direct test where their Linux twins have one

`internal/store/storefs_linux_test.go` unit-tests
`openAbsoluteDirNoFollow`'s three refusals (relative target, symlinked
ancestor, symlinked final component). There is **no `storefs_windows_test.go`**.
`openAbsoluteDirNoFollowWin`, `validateAbsoluteWindowsPath` and
`openVolumeRootNoFollow` are reached only indirectly through `Watch` /
`ResolvePath`, and `validateAbsoluteWindowsPath` is the single validator both
`Root()` (§4.1) and `readlinkAt`'s target check (§3.3) share.

Worse, two refusal branches inside `link_windows.go`'s `readlinkAt` have no
test at all — `grep` finds neither `SYMLINK_FLAG_RELATIVE`/"relative symlink"
nor `Volume{` in any `_test.go` in the tree:

- the `SYMLINK_FLAG_RELATIVE` refusal (a relative substitute name that
  `CreateFile` would resolve against the process CWD). The ADR carries this as
  `[UNMEASURED]` with owner **P3.4**; it is still unmeasured.
- the `\??\Volume{` volume-mount-point refusal (§5.3), the only thing
  separating a volume mount point from a junction, which share a tag.

Both are reachable via a pre-existing or planted link, which is precisely the
population Scope A forgives.

**Owner:** P6.1/P6.3.

### P-7 — LOW (documentation). "symlink" is still stated unconditionally in four places

- `README.md`: ``scratchpad watch ./chart-folder # symlink instead of copy``
- `docs/cli.md`: "`watch` **symlinks** an external folder in"; "A watch link
  is the only permitted **symlink** boundary"; "publish, delete, and unwatch
  never operate through a **symlinked** project path"
- `docs/internals.md:21`: "`internal/watch` — fsnotify over the whole root
  (following **symlinks**, …)"; `:128-132` "must be real directories, never
  **symlinks**"
- `skill/SKILL.md:101`: "A watch link is the only **symlink** boundary the site
  follows" (its Windows Rules bullet at `:104` is correct and says "reparse
  point: a directory symbolic link … otherwise a junction")

`docs/windows.md` gets this right. The others are the documents an agent or a
Windows user reads first. "link" or "watch link" is the portable word.

Also in this bucket: `docs/cli.md`'s "Lookups of what already exists … validate
looser than publish" is true only on Linux (see P-1a, and the `:`/trailing-dot
rows of the divergence table).

### P-8 — LOW (documentation). "data-compatible in both directions" over-claims

`docs/windows.md`, "Data root": *"Existing stores are data-compatible in both
directions. There is no migration."*

Reasoning through a store containing a watch link, notes, a
`.scratchpadignore` and a name legal on one platform only:

- **Notes** — fully portable. Plain JSON in a mirrored directory tree, shared
  policy, shared `rev`, shared sort. The only casualty is two case-variant doc
  paths, which cannot coexist on NTFS.
- **`.scratchpadignore`** — portable as a file; its *meaning* changes (row 4).
  A Linux store with a `readme` rule and a `README` folder hides more on
  Windows. Deliberate; needs the P-2 sentence.
- **Watch links** — never portable, in either direction, and never were: the
  target is a machine-local absolute path. A Linux symlink carried onto NTFS
  fails `validateAbsoluteWindowsPath` and is **silently dropped** from
  `Watches()` and `List()`. That is not a divergence — a dangling symlink is
  dropped by `linkTargetIsDir` on Linux too — but the doc sentence should say
  so. A junction carried to Linux does not survive the copy at all.
- **A name legal on one platform only** — P-1b.

**Fix:** one sentence — artifacts and notes are portable; watch links are
machine-local and must be re-created with `scratchpad watch` after a move.

### P-9 — LOW (behaviour, Windows-only). A store root deleted and recreated while the process runs wedges it permanently

`storefs_windows.go:56-77`'s `rootIdentityCache` is process-lifetime and keyed
on the resolved root **string**. If the root's `FILE_ID_INFO` changes between
two `openRootedFS` calls, every later call fails with

> `scratchpad: the store root "…" was replaced with a different directory since this process last used it — refusing to operate on it (identity was …, now …)`

Linux has no counterpart: `openRootedFS` re-opens the root by path each time.

The control is right (it is R13, and it catches "silently operating on the
wrong store"). The **user experience** is not: a user who deletes and recreates
`%USERPROFILE%\.scratchpad`, or restores it from a backup, or lets a sync
client replace it, must restart `scratchpad-web.exe`; the message does not say
so; and in the web layer almost every caller turns `openRootedFS`'s error into
`return nil, false`, so the site simply **404s everything** with the real
reason visible nowhere. Compare `annotationfs_windows.go:135`, which does say
"restart the server" for the analogous lock-file case.

**Fix (cheap):** append the remediation to the message, and surface it from the
web layer as an error page rather than a silent 404. **Fix (better):** invalidate
the cache entry and re-pin when the root's identity changes *and* the previous
handle is gone, so an ordinary recreate self-heals while a mid-operation swap
still fails.

### P-10 — LOW (behaviour, Windows-only). `Delete`'s "not found" absorbs a much larger error space on Windows

Handed to P4.7 by P3.14 L7. **I concur, and it is avoidable.**
`store.go`'s `Delete` turns any `openDirAt` failure into
`artifact %s not found`. On Windows that now absorbs a `reparseRefusal` on any
of ~30 tags, `STATUS_SHARING_VIOLATION` from a scanner,
`ERROR_CANT_ACCESS_FILE` from an unserviced ProjFS/cloud entry, and
`fs.ErrPermission`. The user is told "not found" about a card the folder page
is still drawing. `winError` already carries the NTSTATUS for exactly this.
Adding it costs one `errors.As` and changes no Linux behaviour.

### P-11 — INFO. `IsLinkInfo`'s over-approximation has no reachable phantom today, but the guard is implicit

On Windows `IsLinkInfo`/`IsLinkEntry` return true for `ModeIrregular`, so at
the two remaining read-only sites (`internal/web`'s `folderUnwatch`,
`internal/watch`'s `desiredDirs`) *any* reparse point classifies as a link.
For `folderUnwatch` this is **required** — a junction is `ModeIrregular` and
without it a junction folder tile would silently lose its unwatch button — and
no phantom is reachable, because every card-construction path first passes
through `classifyEntry`, which drops unknown tags before a tile exists. That
safety is a property of the *callers*, not of `folderUnwatch`, and nothing
records it at the call site.

`desiredDirs` is the looser one: an unknown-tag **directory** reparse point
reports `IsDir()` true, so the watcher walks into a subtree `internal/store`
refuses to list or serve. Bounded (`crossedLink` blocks a second link) and
harmless — extra events on a tree with no content — but it is an inconsistency
between the two packages' classification, and it is untested.

### P-12 — INFO. The one Windows-only failure mode Linux has no analogue for is never exercised

`errNoLinkPrivilege` requires *both* symlink and junction creation to fail.
`TestDegradedModeWithPrivilegeGenuinelyRevoked` reaches row 2 (privilege
removed, Developer Mode on → symlink) and row 3 (both off → junction) and both
**succeed**. `assertWatchFlavour` contains real assertions on the failure
message's wording (it must name Developer Mode; it must not offer elevation as
the default) that no CI run has ever executed. EXEC:1908-1925 says the same:
acceptance criterion 6 is satisfied "by construction … not by error handling."
`docs/windows.md` already tells the user "You should not see this."

Accept as-is; note it so nobody mistakes the assertion's presence for evidence.

**Two corrections to the framing in the task.** The 313 / 286+27 figures are
**whole-suite** totals from run `32965663917`, not `internal/store` (that

`internal/winspike`**, the Phase-1 spike package `winspike.yml` says is deleted

byte-identical, so the delta is purely 27 tests moving PASS → SKIP.

**All 27 have one reason, verbatim identical:**

**Ruling, test by test:**

| Verdict | Count | Which |
|---|---|---|
| **Genuine capability gap** — the test itself creates a symlink, so it cannot run without the privilege | 21 | the remaining `store_test.go`, `annotations_test.go`, `attack_test.go`, `storefs_windows_attack_test.go /dirsymlink`, `internal/watch`, `internal/web` symlink tests |

The six over-gated tests never call `os.Symlink` themselves. Their subject is
`Watch`/`Unwatch`, which a **junction** satisfies — `errNoLinkPrivilege` is
reached only when *both* flavours fail. On a real Developer-Mode-off Windows
box `scratchpad watch` works and these six would pass; CI reports them un-run.
This is P-4.

`TestFilesFromDirRejectsNonRegularEntries` deserves its own line. Its Linux
sibling is `TestFilesFromDirRejectsNamedPipe`, behind `//go:build unix`. So on
a symlink-incapable Windows machine, `publish -dir`'s documented "symlinks,
FIFOs, devices, and other special files reject the whole publish" rule has
**zero** coverage in either direction. A junction or an unknown-tag entry would
test the same rule without the privilege.

**The larger point about the job itself.** `SCRATCHPAD_TEST_SYMLINKS=0` is a
**test-harness override**; production `symlinkAt` never consults it, and the
runner underneath remains elevated with Developer Mode on. The
`windows-degraded-test` job therefore proves that the `RequireSymlinks` guard
is wired, not that the product works without link privilege. The evidence for
*that* claim lives entirely in
`internal/store/degraded_windows_test.go`, which ignores the env var, removes
`SeCreateSymbolicLinkPrivilege` from a child process's own token with

DEGRADED|token_before|held=true    DEGRADED|token_after|held=false
DEGRADED|publish|ok   list|ok   notes|ok   delete|ok
DEGRADED|watch|label=row2|outcome=succeeded|flavour_tag=0xA000000C   (SYMLINK)
DEGRADED|watch|label=row3|outcome=succeeded|flavour_tag=0xA0000003   (MOUNT_POINT)

That is real evidence and it satisfies spec AC6. It does not cover the web or

**Coverage holes found while auditing the skips** (beyond P-6):

- The eight `TestAtomicWrite*` cases unit-test the **Windows** replace path;
  there is no `annotationfs_linux_test.go` — Linux's temp+rename is covered
  only behaviourally through `annotations_test.go`. Likewise
  `TestRemoveTreeAtSwapMidWalkAndNegativeControl` and the lock-rendezvous tests

- `testutil.RequireWatchLinks` emits the marker `SKIP(symlink-capability)`

## What I could not verify

1. **Anything requiring a Windows host.** I have none. Every Windows claim here
   is code reading, plus the Go 1.27 sources on disk, plus the ADR's and
   spike's measurement tables, plus three green CI runs read end to end
   (`32965663917`, `32966551366`, `32962872576`).
2. **P-5's premise, directly.** That `filepath.EvalSymlinks` leaves a junction
   unresolved. Reasoned from `$GOROOT/src/path/filepath/symlink.go:85-93` plus
   the ADR's `P14.junction_modesymlink`. The ADR's own `M5.junction` records
   `EvalSymlinks` *erroring* on a junction as an intermediate component, which
   does not match what the Go 1.27 source does; one of the two observations is
   stale or was made on a different shape, and I could not settle which.
3. **P-1b's worst case.** Whether an NT-native-created directory literally
   named `CON` or `report.` is actually *openable* by this store's
   handle-relative primitive on NTFS. The ADR's `M18.relative_open.*` records
   `STATUS_OBJECT_NAME_NOT_FOUND` for these names, but as far as I can tell
   from the ADR that was measured against names that do not exist, which is a
   different question. If the primitive *can* open them, P-1b is worse than I
   have graded it (the entry is reachable by the store but refused by the
   validator); if it cannot, P-1a's behavioural half is genuinely unavoidable
   and only the docs need fixing.
4. **WOF / DEDUP under the strict open.** `openRealFileAt` refuses any reparse
   attribute on a file. If a `compact`-compressed `.html` sets
   `FILE_ATTRIBUTE_REPARSE_POINT`, every document in that artifact 404s and
   `dirHasHTMLFD` stops recognising the folder as an artifact at all. Already
   P3.14's unverified item 5 and the ADR's §5.4 `[UNMEASURED]`; I am not
   re-filing it, but it is the largest unmeasured *user-visible* Windows risk
   left, and it is not in `docs/windows.md`'s known-limitations list.
5. **OneDrive.** Whether a store or a watched tree under a OneDrive root
   mass-rehydrates. I traced the read paths and believe not — `statAt`,
   `dirHasHTMLFD`, `loadArtifactAt`, `sizeWalkAt` and `previewBytes` all read
   attributes only, never content — but RW13's `RECALL_ON_*` skip is still
   open with no code anywhere mentioning recall attributes, and no runner has
   OneDrive.
6. **ReFS / Dev Drive, SMB, FAT/exFAT, arm64 at runtime, and a genuinely
   non-elevated interactive session.** All excluded from CI by construction.
   `testutil.RequireNTFS` never fired on any run I read, so the NTFS gate has
   never been exercised either.
7. **Whether the duplicated error strings have already drifted.** EXEC:538-544
   records that `openRealDir`'s two user-facing messages were *reproduced* in
   `storefs_windows.go` rather than shared through a typed error. I compared
   them by eye and they match today; nothing enforces that they keep matching,
   and no test asserts the Linux wording and the Windows wording against each
   other.
