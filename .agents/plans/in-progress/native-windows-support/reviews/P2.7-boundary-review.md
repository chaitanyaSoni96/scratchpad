# P2.7 Boundary Review

## Verdict

**PASS WITH FINDINGS.**

Phase 2's gate — "Linux suite passes and both Windows commands cross-compile" —
is genuinely met, and its exit evidence ("green Linux tests, green Windows
cross-build, shared files free of Unix APIs, and a reviewed platform API
inventory") holds on every clause I could execute. I re-ran everything rather
than trusting the commit message or the inventory.

On the two questions P2.7 actually asks:

- **Was security-sensitive mechanism made generic? No.** This is the strongest
  part of the change. No interface was introduced, no helper took a flags or
  mode parameter, and every security-carrying flag survives verbatim. The
  specific hazard the task names — "a helper named `unlinkAt` that can remove
  either a file or a directory" — did **not** happen: `unlinkAt` is
  `Unlinkat(…, 0)` (cannot remove a directory) and `rmdirAt` is
  `Unlinkat(…, AT_REMOVEDIR)` (cannot remove a non-directory). Two narrow
  primitives, not one dangerous one.
- **Did domain policy leak into platform files? Partly — but it was already
  there, and this commit did not add to it; it duplicated it.** Four domain
  decisions (the definition of an artifact, two user-facing error strings, the
  one-watch-boundary rule, and `OpenDocument`'s validation prologue) live in
  `storefs_linux.go` and now have a Windows twin that must re-author them.
  That meets `threat-model-windows.md` R20's *reverse* falsifier. It is F2
  below, and it is a Phase-3 pre-condition, not a Phase-2 defect.

The Linux refactor is mechanically equivalent — I checked every converted call
site individually. Nothing regressed to a path-based operation; the one
signature change (`watch.identity`) moved in the safe direction, from a path to
a handle.

Nine findings follow. None of them is a live vulnerability on either platform
today, and none of them justifies blocking Phase 3's start. Three (F1, F2, F4)
**must** be closed before the corresponding Phase 3 implementation task writes
its Windows mechanism, because each of them is a trap that only springs when a
stub becomes real. F3 must be closed before P3.11 removes the native Windows
job's `continue-on-error`.

## What I verified item by item

### 1. Mechanical equivalence of the Linux refactor — PASS

Every converted call site, checked against `36bb133^`:

| Old (shared `store.go`/`annotations.go`) | New | Equivalent? |
|---|---|---|
| `unix.Close(fd)` ×10 | `closeFD(fd)` = `unix.Close(fd)` | yes |
| `unix.Mkdirat(parent, name, 0o755)` + `errors.Is(err, unix.EEXIST)` | `mkdirClaim` (same call, EEXIST→`errExists`) + `errors.Is(err, errExists)` | yes |
| `unix.Unlinkat(parent, name, unix.AT_REMOVEDIR)` | `rmdirAt` — **`AT_REMOVEDIR` retained** | yes |
| `unix.Symlinkat(abs, parent, name)` | `symlinkAt(parent, abs, name)` → `unix.Symlinkat(target, parent, name)` — argument order swapped in the signature, call site passes correctly | yes |
| `buf[4096]` + `unix.Readlinkat` + `string(buf[:n]) != abs` | `readlinkAt` — same 4096 buffer, same truncation behaviour, compared to the same `abs` | yes |
| `unix.Fstatat(parent, name, &st, unix.AT_SYMLINK_NOFOLLOW)` + `st.Mode&S_IFMT==S_IFLNK` (Unwatch **and** Delete) | `isLinkAt` — **still `Fstatat`, still `AT_SYMLINK_NOFOLLOW`, still fd-relative** | yes |
| `unix.Unlinkat(parent, name, 0)` | `unlinkAt` — flag `0` retained | yes |
| `unix.Flock(int(f.Fd()), LOCK_SH/LOCK_EX/LOCK_UN)` | `flockFile`/`funlockFile` — 1:1 | yes |
| `unix.Openat(locks, name+".lock", O_CREAT\|O_RDWR\|O_CLOEXEC\|O_NOFOLLOW, 0o600)` | `openLockFileAt` — every flag and the mode retained | yes |
| `identity(path)` → `os.Stat(canonical)` + `Sys().(*syscall.Stat_t)` | `identity(*os.File)` → `dir.Stat()` (Fstat) + same assertion | yes for the identity value; **see F5** for the error path |

Specifically, on the four regressions the brief told me to hunt for:

- **A dropped `errors.Is` check?** No. `errors.Is(err, unix.EEXIST)` became
  `errors.Is(err, errExists)` with the translation done inside the platform
  helper, which is what the spec's "Error translation should preserve
  `errors.Is` behavior for existence…" asks for. I confirmed no caller anywhere
  in `internal/` or `cmd/` depends on `unix.EEXIST` escaping from `Publish` or
  `Watch`, so the loss of the wrapped errno is unobservable.
- **An `EEXIST` that became a generic error?** No. `errExists` is a distinct
  package-private sentinel, produced by exactly two functions, and both
  `Publish` and `Watch` still branch on it to produce their specific messages.
- **A `Fstatat(AT_SYMLINK_NOFOLLOW)` that became an `os.Lstat`?** **No.**
  `isLinkAt` is still `Fstatat` against the pinned parent fd. The path-based
  `os.Lstat` classifications that exist (`annotate`, `WatchLinkFor`) were
  already path-based before this commit and are read-only/advisory.
- **A descriptor-relative operation that became path-based?** **No — and one
  went the other way.** `desiredDirs` previously did two independent path
  lookups (`os.Stat(canonical)` for identity, `os.ReadDir(dir)` for entries);
  it now opens the directory once and answers both from that one handle. That
  is the R14-shaped improvement the inventory claims, and it is real.

### 2. Was security-sensitive mechanism made generic? — PASS

```
$ grep -rn "interface {" --include='*.go' internal/store internal/watch | grep -v _test.go
internal/watch/watch.go:24:type backend interface {   ← pre-existing, unrelated
```

No filesystem interface was introduced; the spec's prohibition holds. Helper by
helper:

- `closeFD`, `mkdirClaim`, `rmdirAt`, `symlinkAt`, `readlinkAt`, `unlinkAt`,
  `isLinkAt`, `flockFile`, `funlockFile`, `openLockFileAt` are each **one
  syscall**, with **no flags or mode parameter**. There is no call site at
  which a security flag could be passed away, because none of them accepts one.
- The `unlinkAt`/`rmdirAt` split is correct and deliberate: `flags=0` fails
  with `EISDIR` on a directory, `AT_REMOVEDIR` fails with `ENOTDIR` on a
  non-directory. Neither is a general "remove this thing" primitive.
- `flockFile(f *os.File, exclusive bool)` is the broadest of them — it will
  lock any file — but the *policy* (that the rendezvous object is the store-root
  descriptor, not `.annotations`) stayed in shared `annotations.go`. That is the
  right side of the line.
- `openLockFileAt` is the second-broadest — it is effectively "create-or-open a
  0600 file at this parent, no-follow". Narrow enough, named for its one use,
  and no flags parameter. Acceptable.
- `IsLinkInfo`/`IsLinkEntry` are newly **exported** package API. I agree with
  the inventory's reasoning (one classification decision for three packages
  beats three copies), and the alternative really would have been the
  duplication R20 forbids.

#### T2 — what a junction actually does on the read paths, and why it is fail-closed

Go reports a junction as `ModeIrregular`, so on Windows `IsLinkEntry(e)` is
`false` **and** `e.IsDir()` is `false`. Following that through each consumer:

- `store.entryIsDir` (`store.go:270-278`): `e.IsDir()` false → `!IsLinkEntry(e)`
  true → **returns false before reaching the `os.Stat`**. This matters: that
  `os.Stat` *follows*, and would report the junction's target as a directory.
  The junction-blind classifier is what gates it. The junction is skipped, not
  descended.
- `internal/web.entryIsDirFS` (`server.go:325-333`): identical shape, identical
  outcome.
- `store.List` (`store.go:368-372`): `entryIsDir` already excluded it, so
  `crossedLink` is never armed by a junction and nothing descends.
- `internal/watch.desiredDirs` (`watch.go:258-274`): `isLink` false and `isDir`
  false → the `walk` recursion is not entered.
- `store.Watches` (`store.go:656`): a junction is not reported as a watch link.
  Under-listing, not escape.
- `store.WatchLinkFor` (`store.go:625`) / `internal/web.folderUnwatch`
  (`server.go:237`): return `""` / `nil` for a junction, so the web card offers
  **Delete** where it should offer **Unwatch** — exactly threat model §3.11.
  Inert today because `Delete` fails at T1's first line.

So the misclassification's blast radius in Phase 2 is: *a junction is invisible
in listings, and its card shows the wrong button*. No traversal, no
destruction. **Not a HIGH finding.** And note the pleasant accident: because
every "is it a directory" decision that would follow a junction is gated
*behind* `IsLinkEntry`, being blind to junctions currently fails **closed** for
traversal. Fixing `IsLinkEntry` to report junctions without simultaneously
fixing `entryIsDir`'s follow-through `os.Stat` would make things **worse**, not
better. That inversion is recorded as part of F4.

## Findings

### F1 — HIGH (latent). Three Windows stubs return a benign constant instead of the sentinel, and `dirHasHTMLFD`'s constant is fail-**open**

`storefs_windows.go` gives four helpers a silent, plausible-looking value
because their signatures have no error channel:

| Stub | Value | If it becomes reachable |
|---|---|---|
| `dirHasHTMLFD(fd) bool` (line 57) | `false` | Disables **two security rules at once**: `openRealDir`'s `rejectArtifacts` guard (`storefs_linux.go:108` — spec invariant 3, artifact nesting) and `openBrowsableDir`'s `!dirHasHTMLFD(fd)` condition on crossing a link (`storefs_linux.go:204` — spec invariant 5, exactly one watch boundary). Both silently vanish. |
| `fdPath(fd) string` (line 47) | `""` | `loadArtifact(project, name, "")` — and `filepath.Join("", x) == x`, i.e. a **CWD-relative** walk. An empty path is the worst possible poison value. |
| `closeFD(fd)` (line 49) | no-op | Silent handle leak on the exact path R15 governs ("every handle is closed on success and on every error path"). |
| `pruneAt(r, segs)` (line 75) | no-op | Empty project directories never pruned. Cosmetic; listed for completeness. |

There is **no safe constant for `dirHasHTMLFD`**: `false` is fail-open in
`openRealDir`/`openBrowsableDir` and fail-closed in `Delete`; `true` inverts
both. That is the proof that a constant is the wrong answer here, not a
tuning choice.

All four are unreachable today (proved by T1). The trap is ordering: P3.1/P3.2
land `openRootedFS`/`openRealDir` first by the plan's own sequence, and at that
instant these four go live with no compile error and no test failure.

**Action:** give each of the four a loud failure that the trace proves is
unreachable — e.g. a package-private `windowsUnimplemented()` that panics with
the sentinel text, called from all four bodies — or change `dirHasHTMLFD`'s
signature to `(bool, error)` on both platforms. Do this **before** P3.2 writes
`openRealDir`. **Owner: P3.1** (add as an explicit sub-item), verified by
**P3.14**.

### F2 — MEDIUM. Domain policy sits on the platform side of the boundary and is now structurally duplicated

This is P2.7's headline question, and the honest answer is nuanced: **`36bb133`
did not move any policy into a platform file.** Everything below was already in
`storefs_linux.go` before it. But by creating `storefs_windows.go`, the commit
turned "policy that happens to live in the Linux file" into "policy that Phase
3 must re-author in a second file", which is precisely R20's reverse falsifier:
*"a policy decision (what is an artifact, what is visible, what names are
allowed) duplicated into a platform file."*

The four sites:

1. **`dirHasHTMLFD` (`storefs_linux.go:70-82`) encodes the definition of an
   artifact** — `strings.HasSuffix(strings.ToLower(name), ".html")` plus a
   regular-file test. This is *the* central domain rule from `CLAUDE.md`. The
   Windows twin is a constant (F1).
2. **`openRealDir` (`storefs_linux.go:102-111`) owns two user-facing error
   strings** — `"project ancestor %q is a symlink"` and `"%q is an artifact,
   not a project"`. P2.3's own wording says user-facing errors stay in shared
   code. The Windows author will have to reproduce both, in English, from
   scratch, or the two platforms will report the same rejection differently.
3. **`openBrowsableDir` (`storefs_linux.go:196-223`) implements spec invariant 5**
   — the `crossed` flag and the "don't cross out of an artifact directory"
   guard are pure policy expressed only in mechanism terms.
4. **`OpenDocument` (`storefs_linux.go:243-255`) runs a policy prologue** —
   `visibleSegments` + a `validateSegment` loop — before delegating to
   `openPathFile`. The Windows twin (`storefs_windows.go:82`) drops both and
   returns `nil, false`, conflating "not implemented" with "not found". (The
   stub's own comment concedes this; it is the one place where the otherwise
   excellent "never fake a benign result" discipline is knowingly broken.)

**Action:** before P3.2/P3.6 writes any Windows mechanism, hoist into shared
code: (a) the `.html`-suffix predicate, leaving the platform file with a
"list this directory's regular entries" mechanism only; (b) the two error
strings, so the platform returns a typed condition and shared code renders the
message; (c) `OpenDocument`'s validation prologue into a shared wrapper over a
platform `openPathFile`. Doing this first means the Windows author implements
mechanism only, which is what the boundary was for. **Owner: P3.2 and P3.6, as
a pre-condition; re-checked at P3.13.**

### F3 — MEDIUM. A security test already passes vacuously on Windows

From the windows-2025 job's own log (run 32901529797): 43 PASS, 52 FAIL, 19
SKIP. Among the passes:

```
--- PASS: TestPublishAndNestedWatchRejectSymlinkProject
--- PASS: TestSaveNotesRequiresDocExists
--- PASS: TestNotesReadHiddenPath404s
--- PASS: TestListFragmentRejectsInvalidFolders
```

`TestPublishAndNestedWatchRejectSymlinkProject` (`store_test.go:349-375`) is a
containment test. Its assertions are `Publish(...) err == nil → fail`,
`Watch(...) err == nil → fail`, plus "the external sentinel is unchanged and
nothing was created outside". On Windows all of those hold **because
`openRootedFS` returned `errWindowsUnimplemented` and nothing happened at all**
— not because containment worked. It passes for entirely the wrong reason.

Harmless while the job carries `continue-on-error`. The moment P3.11 removes
that allowance, this is a green security test asserting nothing. It is the same
failure mode P0.5's F1/F2 identified for skips, arriving through a different
door.

**Action:** negative security assertions must assert the *reason*, not just
`err != nil` — the cheapest general fix is a Windows job step that fails if any
`--- PASS` line coexists with a `not implemented yet` sentinel in the same
package's `-v` output, mirroring the existing `SKIP(symlink-capability)` guard.
**Owner: P3.11** (before removing `continue-on-error`), designed at **P3.12**.

### F4 — MEDIUM. The junction-blind classifier is safe only by an unenforced ordering invariant

T1/T2 prove `IsLinkInfo`/`IsLinkEntry` cannot cause harm today, and I accept the
implementer's judgement that a real (imprecise) answer beats an error stub for
read-only listing paths that must still render a page. But:

- The safety property is *"`openRootedFS`/`openAnnotationFS` is the first gate
  on every mutation"*. Nothing in the code, the tests, or the plan enforces it.
  It is stated only in a doc comment (`link_windows.go:44-52`).
- Phase 3's task list has **no ordering constraint** saying these two functions
  must be replaced before P3.1 lands `openRootedFS`. P3.1 is the *first* Phase 3
  task; the day it merges, every classification site in T2 goes live.
- T2's inversion makes a partial fix actively dangerous: fixing `IsLinkEntry`
  to report junctions **without** also fixing `entryIsDir`/`entryIsDirFS`'s
  follow-through `os.Stat` (`store.go:274-277`, `server.go:330-332`) converts
  today's fail-closed skip into a path-based descent through the junction.
- `WatchLinkFor` returning `""` for a junction means the web card offers Delete
  instead of Unwatch (threat model §3.11) — the exact RR1 setup, waiting only
  for `Delete` to work.

**Action:** add to **P3.1** an explicit precondition — *"replace
`IsLinkInfo`/`IsLinkEntry` with a `FILE_ATTRIBUTE_TAG_INFO` tag-allowlist check,
and convert `entryIsDir`/`entryIsDirFS` to a no-follow classification, before
implementing `openRootedFS`"* — and land a Windows-only failing test
(`TestJunctionIsClassifiedAsLink`) now so the ordering is enforced by CI rather
than by a comment. **Owner: P3.1, tested by P3.12.**

### F5 — LOW. `desiredDirs`'s error tolerance changed; the inventory calls it "mechanically equivalent"

Before (`watch.go@36bb133^:238-252`): `canonicalDir` (ENOENT tolerated when
`!required`) → `identity(canonical)` = `os.Stat` (**any** error fatal, ENOENT
included) → `os.ReadDir(dir)` (ENOENT tolerated).

After (`watch.go:233-256`): `canonicalDir` → `os.Open(dir)` (**ENOENT now
tolerated** when `!required`) → `identity(f)` = `Fstat` (cannot be ENOENT) →
`f.ReadDir(-1)`.

A directory that vanishes between `canonicalDir` and identity used to produce a
fatal `reconcile` error — which by design kills the web process (`CLAUDE.md`:
"Other watcher/reconcile failures are fatal to the web process") — and is now
silently skipped. That is almost certainly an **improvement** (it matches the
`ReadDir` branch immediately below and shrinks threat model RR9's DoS window),
but it is a behaviour change in shared reconciliation policy that the inventory
describes as "mechanically equivalent on Linux". It is invisible to the test
suite (E1 confirms an identical passing-test set), which is exactly why it
should be written down.

Secondary, same site: `defer f.Close()` inside the recursive `walk` closure
means the watcher now holds one open descriptor per level of tree depth where
it previously held none. Bounded by real tree depth and harmless in practice —
but R16 still has no depth bound, so it belongs on that ticket.

**Action:** record both in the inventory §5. **Owner: P4.2.**

### F6 — LOW. `/proc/self/fd`: right count, wrong consequence in both directions; and one CI gap worth closing

The four sites are correctly identified. But `EXECUTION.md` says they "compile
on Windows and silently misbehave", and the inventory says they "will compile
on Windows but silently misresolve at runtime". Both are imprecise:

- **Today they are unreachable, not misbehaving.** All four are downstream of
  `store.ResolveFolder`, which on Windows returns `false` at
  `openRootedFS` (`store.go:181-184`) before any of them is constructed. The
  whole web layer is inert on Windows in Phase 2.
- **Once reachable, the consequence is degradation, not escape.**
  `"/proc/self/fd/N"` on Windows is a rooted-but-driveless path resolving
  against the current drive, i.e. `<drive>:\proc\self\fd\N`. `os.ReadDir` there
  returns a not-found error, so `docCount`→0 (line 296/300),
  `siblings`→`nil` (line 605-611), `hasRenderable`→`false` (line 648-654), and
  `entryIsDirFS`'s `os.Stat` →`false`. Wrong pages, no containment escape —
  and the "unless something can create `C:\proc\self\fd\…`" caveat requires
  write access to the drive root, which is administrator-only by default.

**Is leaving these to P3.6/P4.6 acceptable? Yes.** And the cross-build gate is
**not** giving false assurance, because both the CI job comment and
`EXECUTION.md` state in as many words that "compiling is not working" and that
a green cross-build proves source portability only. The gate is honestly
labelled.

One real gap is worth closing now, because this bug class is invisible to both
the compiler and `go vet`: **CI never runs `GOOS=windows go vet ./...`.** The
cross-build job runs only `go build ./cmd/...`, which does not typecheck test
files and does not vet. **Action:** add `GOOS=windows go vet ./...` and a grep
gate for `/proc`, `/dev`, `/sys` literals outside `*_linux.go`/`*_unix.go` to
the cross-build job. **Owner: P3.6 / P4.6** (as already assigned), with the CI
step available immediately.
