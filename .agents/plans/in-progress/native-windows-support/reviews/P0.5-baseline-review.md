# P0.5 Baseline Review

## Verdict

**PASS WITH FINDINGS.**

Phase 0's stated gate — "current Linux tests pass and Windows compile failures
are captured as expected evidence" — is genuinely met, and I verified every
load-bearing claim myself rather than accepting the commit message. CI really
does cover Linux, Windows cross-build for both architectures, native Windows
amd64, and native Windows arm64 compile. The Windows failures are real,
correctly attributed, and not harness bugs. The test reclassification is
honest: zero Linux skips, zero lost tests, no changed assertions.

Nine findings follow. None of them justify blocking Phase 1, which is a
research-and-ADR phase that touches no CI and no tests. Two of them (F1, F2)
**must** be closed before the `continue-on-error` allowances are removed,
because as written the Windows job will go green while silently running none
of the security tests it exists to run. I recommend the gate pass with F1 and
F2 recorded as blocking pre-conditions on P3.11/P4, and F3/F4 fixed now since
they are edits to the tracker, not to code.

## Findings, ranked by severity

### F1 — HIGH — the symlink-capable Windows job cannot become the spec's REQUIRED job as written; a capability-less runner will go green with the security suite silently skipped

The spec's *Build and release* section requires: "At least one Windows CI job
must run the full suite with Developer Mode or an equivalent symlink-capable
test environment. Security tests that cannot obtain the capability should
report a skip with a reason; a separate required job must exercise them."

The current design has **one** Windows test job that is simultaneously the
"full suite" job and the only place symlink tests could run, and it makes the
capability advisory rather than mandatory:

```yaml
if ($env:SCRATCHPAD_TEST_SYMLINKS -ne "1") {
  Write-Host "SCRATCHPAD-SKIP: symlink capability ABSENT - tests ... will self-skip"
}
go test ./...
```

It prints a warning and proceeds. Today the runner probes PRESENT, so this is
latent — but the moment `continue-on-error` is removed at P3.11/P4, a runner
image change, a Developer Mode policy change, or a transient probe failure
turns this into a **green required job with every `Watch`, unwatch,
annotation-symlink, nested-link and watched-tree containment test skipped**.
That is exactly the failure mode a security gate exists to prevent, and
nothing in the pipeline counts skips.

Compounding this: `SCRATCHPAD_TEST_SYMLINKS=0` is a silent global off-switch
for the entire symlink-dependent security suite. The `"1"` direction is safe
(claiming capability you lack makes tests fail loudly), but `"0"` disables
them with no signal above a per-test skip line. Anyone editing the workflow —
or an environment that sets the variable for unrelated reasons — can turn the
suite off without any job turning red.

The design is **structurally able** to become the required job — the probe
already produces the exact signal needed — so this is a completion gap, not a
wrong architecture. Concretely:

**Recommended action.** Split the native Windows testing into two jobs before
the allowance is lifted:
1. `windows-native-test` (full suite, capability-tolerant): keep the probe,
   keep the advisory skip path, keep it non-required. This is the "reports a
   skip with a reason" job.
2. `windows-symlink-security` (REQUIRED): after the probe, hard-fail when
   `SCRATCHPAD_TEST_SYMLINKS -ne "1"` (`exit 1`, message naming Developer
   Mode as the remediation), then run the named security/watch suites
   explicitly by `-run` pattern as the plan's *Verification Commands* section
   already asks ("Native test jobs should additionally run named security and
   end-to-end suites so they cannot disappear behind package-level success
   after an accidental rename").
   Additionally assert `--- SKIP` count is zero in this job, so a future guard
   added to a capability-independent test cannot silently erase it.

Also add a zero-skip assertion to `linux-test` for the same reason — Linux is
0 skips today (E1) and that property should be enforced, not observed.

**Owning task:** P0.3 to add the assertion and the job split now (cheap, no
code dependency); P3.11 / P4.6 must not remove `continue-on-error` until it
exists. Worth adding an explicit line to P2.6 and P3.11 saying the allowance
may only be removed together with the capability assertion.

### F5 — MEDIUM — `RequireSymlinks` guards `Watch`-based tests, which will make degraded-mode security assertions vanish on Windows precisely where they matter most

The implementer's decision to guard tests that create symlinks *indirectly*
through `store.Watch` is **correct as a Phase 0 mechanical step** — those tests
genuinely cannot run without the capability today, and leaving them
unconditionally failing would have been worse. I would have made the same call.

But it will cause a real loss once a Windows backend exists, and this should be
recorded now rather than rediscovered at P4.4. Consider
`TestWatchCreateOnly`: its first assertion needs capability (a watch must
succeed), but its second and third assertions —
`Watch("", "taken", other)` must fail with `already exists`, and
`Watch("", "solid", src)` must fail against a real directory — are exactly the
**degraded-mode and collision-rejection** behaviours P4.4 says must work
without link privilege. Whole-test guarding means that on a machine without
Developer Mode, the collision rejection is untested. The same shape applies to
`TestUnwatch` (refusing real directories) and
`TestPublishAndNestedWatchRejectSymlinkProject` (rejecting a symlinked project
path — a rejection path that does not itself need to create a link).

Second, forward-looking risk: `SymlinkCapable()` probes `os.Symlink`
specifically. If the Phase 1 ADR selects application-created **junctions** as
the Windows watch mechanism (the spec explicitly leaves that fallback open),
the probe asks the wrong question — it will report incapable on a machine where
`store.Watch` would succeed, and skip tests that should have run. The helper
should eventually ask "can the store create a watch link here?", not "can
`os.Symlink`?".

**Recommended action.** (a) Add a note to P4.3/P4.4 that the negative and
degraded-mode assertions currently sharing a test body with a capability-
requiring assertion must be split into separate, unguarded tests when the
Windows watch backend lands, naming `TestWatchCreateOnly`, `TestUnwatch`, and
`TestPublishAndNestedWatchRejectSymlinkProject`. (b) Add a note to P1.4/P1.6
that if the ADR selects junctions, `testutil.SymlinkCapable` must be
re-expressed in terms of the store's own link primitive.

**Owning task:** P4.4 for (a), P1.6 for (b).

### F6 — LOW-MEDIUM — `RequireNTFS`'s "cannot determine filesystem → skip" is the wrong default for a required security job, and its doc comment overstates the guarantee

Asked directly: **it is a hole, not a safe default** — but a low-impact one
today, because `RequireNTFS` has zero call sites (`grep` outside
`internal/testutil` returns nothing). It is a P0.4 deliverable defined ahead of
use, which is fine.

The comment claims skipping on an undeterminable filesystem means the test
"cannot pass vacuously". That is only true at the level of the individual test
function; at the level of CI, a skip **is** a vacuous pass, because no job
counts skips (see F1). If `GetVolumeInformation` fails for any reason —
an unusual mount, a permission quirk, a network path — the NTFS-dependent
security tests disappear and the required job stays green.

Note also that `SymlinkCapable`'s `sync.Once` is **correct**: the env override
is consulted before the `Once`, the probe is guarded, `probeSymlink`
deliberately uses `os.MkdirTemp` rather than a `t.TempDir()` so the cached
answer outlives any single test, and it creates a *directory* symlink, which
matches what `store.Watch` needs on Windows. The non-Windows early return means
the cache is Windows-only. I found no correctness defect there.

**Recommended action.** Once `RequireNTFS` acquires call sites, make
"cannot determine" a **failure** in the required security job and a skip
elsewhere — e.g. gate on the same `SCRATCHPAD_TEST_SYMLINKS`-style strictness
signal the required job sets, or have the required job assert a zero skip
count so an unexpected NTFS skip turns the job red. Soften the doc comment in
the meantime.

**Owning task:** P3.12 (where the NTFS-dependent attack tests land).

### F8 — LOW — supply-chain and workflow-hygiene items

- `actions/checkout@v4` and `actions/setup-go@v5` are floating tags, not SHA
  pins. The run logs do resolve them to SHAs
  (`checkout` → `11d5960a...`, `setup-go` → `40f1582b...`), so today's state is
  known, but a tag can be repointed. This repo's spec dedicates P5.7 to
  supply-chain review, so the standard is already set internally.
- `on: push` has no branch or path filter, so every push to every branch spends
  two Windows runners. The repo is public (verified), so this is free rather
  than costly, but combined with `pull_request: branches: [main]` it produces
  duplicate runs for same-repo PRs.
- No `concurrency:` group, so superseded pushes are not cancelled.
- No `go mod tidy -diff` / `go mod verify` check. Dependency drift would go
  unnoticed; the reviewed commit itself carries a stale-`// indirect` fix that
  no check would have caught (E9).

**Recommended action.** Pin both actions to SHAs with a version comment; add a
`concurrency: group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true`
block; add `go mod tidy -diff` to `linux-test`. Note that
`${{ github.ref }}` in a `concurrency:` key is not a `run:` interpolation and
does not reintroduce injection surface.

**Owning task:** P5.6/P5.7.
