# P6.2 Final Threat-Model Audit

## Verdict

**The containment design holds. The release gate does not.**

Two separable judgements, and they point opposite ways:

- **Acceptance criterion 10 is MET.** I re-traced every mutating entry point on
  both platforms against the shipped code and found **no path-based TOCTOU
  escape**. Every mutation issues through a handle pinned *before* the check
  that authorised it. `OBJ_DONT_REPARSE` is genuinely not load-bearing anywhere
  — I enumerated all 17 Win32 open sites and confirmed the strict open
  (`FILE_OPEN_REPARSE_POINT` + `FILE_ATTRIBUTE_TAG_INFO` read from the *same*
  handle + a tag allowlist) is the actual primitive at every site that descends.
  No containment decision reduces to a path-prefix comparison. Both
  Linux-affecting security fixes — the `visibleSegments` ignore bypass and the
  A11 ancestor traversal — are genuinely closed in `internal/store`, not
  narrowed.
- **Acceptance criterion 5 is NOT MET**, on two independent grounds, and four
  ADR dispositions are stale or falsely closed.

The single most important thing on this page is not a code defect. It is that
**the CI job which runs the entire Windows security corpus carries
`continue-on-error: true`** (`ci.yml:108`), as do the degraded-mode job
(`:204`) and the Windows stress job (`:336`). The suite is green today — I
checked run `32970247103`, job `98182132443`: 239 result lines, all packages
`ok`, zero symlink-capability skips — but *nothing forces it to stay green*.
RW1's release gate (`MATRIX.Delete.target_replaced` must pass before any Windows
binary ships) is therefore unenforced twice over: the ADR records the missing
branch-protection rule (F12) but not this, which is the nearer of the two
failures. A test that cannot fail the build is weak evidence for a release gate.

(That green run is commit `a956d9b`; the branch has since moved and the run for
the current head had not finished when I wrote this. The point stands
independently of which commit is green — the job's result does not gate.)

Nothing I found lets any operation escape the store root, cross more than one
watch boundary, follow an untrusted link, or overwrite a claimed name.

**Post-publication amendment.** P6.3 F1 challenged one line this audit cleared,
and it was right: §1.2 checked the wrong operand of a two-comparison guard.
**§10 adjudicates it, upholds it, corrects its impact statement upward
(content, not merely listings), and lands the fix and the measurement F1 could
not make.** It does not disturb the AC10 verdict — the defect is a
confidentiality bypass inside the store, not a containment escape — but it does
mean this document shipped with a cleared line that should not have been
cleared.

## 1. The four things I was asked to test rather than accept

### 1.1 `OBJ_DONT_REPARSE` is not load-bearing; the strict open is the primitive — **CONFIRMED**

There are 17 Win32 open sites in `internal/store`. Sixteen are no-follow. One
follows deliberately.

| Site | Disposition | `FILE_OPEN_REPARSE_POINT`? | `OBJ_DONT_REPARSE`? | Same-handle tag check? |
|---|---|---|---|---|
| `openRootedFS` (`storefs_windows.go:125`) | `OPEN_EXISTING` | yes (`FILE_FLAG_`) | n/a (Win32) | **yes** — `attrTagOf` → `isReparse()` refuse, `isDir()` require |
| `openStrictAt` (`:245`) | `FILE_OPEN` | yes | yes | **yes** — `attrTagOf` → `reparseRefusal` |
| `mkdirClaim` (`:308`) | `FILE_CREATE` | yes | yes | n/a (create) |
| `rmdirAt` (`:325`) | `FILE_OPEN` | yes | no (`OBJ_CASE_INSENSITIVE` only) | n/a — opens the entry *as itself* to remove it |
| `openVolumeRootNoFollow` (`:494`) | `OPEN_EXISTING` | yes (`FILE_FLAG_`) | n/a | **yes** |
| `canonicalizeWatchTarget` (`:547`) | `OPEN_EXISTING` | **no — follows** | n/a | `isDir()` only |
| `statAt` (`:613`) | `FILE_OPEN` | yes | no | **yes** — this *is* the classifier |
| `linkTargetIsDir` (`:672`) | `FILE_OPEN` | yes | no | yes |
| `writeFileAt` (`:750`) | `FILE_CREATE` | yes | yes | n/a (create) |
| `readLinkTagAt` (`link_windows.go:67`) | `FILE_OPEN` | yes | no | reads the reparse buffer |
| `symlinkAt` post-claim reopen (`:102`) | `FILE_OPEN` | yes | no | n/a — opens what is at the name |
| `readlinkAt` (`:167`) | `FILE_OPEN` | yes | no | tag allowlist + flags + target validator |
| `unlinkAt` (`:208`) | `FILE_OPEN` | yes | no | n/a — removes the entry |
| `openRendezvousLockFile` (`annotationfs_windows.go:167`) | `FILE_OPEN_IF` | yes | yes | `fileIDOf` identity |
| `openLockFileAt` (`:262`) | `FILE_OPEN_IF` | yes | yes | n/a |
| `atomicWriteFileAt` temp (`:555`) | `FILE_CREATE` | yes | yes | n/a (create) |
| `deleteEntryAt` (`:660`) | `FILE_OPEN` | yes | no | n/a — removes the entry |

Two properties follow, and I checked both by construction rather than by reading
the comments:

1. **Every directory descent goes through `openStrictAt`.** `openRealDirAt` and
   `openDirAt` are both one-line aliases of it (`storefs_windows.go:267,282`);
   the only other directory anchors are `openRootedFS` and
   `openVolumeRootNoFollow`, which apply the identical tag+isDir discipline
   inline. `openRealDir`, `openBrowsableDir`, `openAbsoluteDirNoFollowWin`,
   `mkdirsAt`, `pruneAt`, `annotationFS.openDir`, `removeTreeAt`,
   `walkAnnotationDir`, `List`, `Watches`, `WatchLinkFor` and `crossOrOpen` all
   descend exclusively through those names. There is no bypass.
2. **Removing `OBJ_DONT_REPARSE` would break nothing.** At `FILE_OPEN`
   traversal sites the refusal comes from `attrTagOf` on the returned handle, so
   the flag only short-circuits a Microsoft-tagged component before a handle
   exists — and since `ntOpenAt` enforces a *single* component at runtime
   (`win32_windows.go:145`, a check not a comment), there is no intermediate
   component for it to short-circuit. At the six create dispositions there is no
   post-open classify step at all, and the thing carrying those sites is
   `FILE_OPEN_REPARSE_POINT` (added by P3.14 M3), not `OBJ_DONT_REPARSE`. The
   ADR's own framing — *necessary and not sufficient*, `noFollowAttrs`'
   comment — is accurate, and I could not find a site where it is doing the
   work.

The one following open, `canonicalizeWatchTarget`, is the documented exception:
its output is re-validated by `validateAbsoluteWindowsPath` and then consumed
only by `openAbsoluteDirNoFollowWin`, component by component. It is never
handed to a subsequent `CreateFile` as a path.

### 1.2 No containment decision reduces to a path-prefix comparison — **CONFIRMED**, with the reasoning spelled out

I enumerated every string comparison in the four packages and classified each.
Four of them touch security; none of the four is decisive.

- **`joinInRoot`'s `filepath.Rel` + `HasPrefix("..")`** (`store.go:313-314`),
  reached from `artifactDir`, `existingDir` and `notesPath`. **Not
  load-bearing.** Every segment has already been through `validateName` or
  `validateSegment`, both of which reject `/`, `\`, `.` and `..` outright,
  *before* the join. A segment set that could produce an escaping join cannot
  reach it. The authoritative containment is the per-segment handle walk from
  the pinned root. The joined string is used afterwards only as `Artifact.Dir`,
  a display path.
- **`Visible`'s `filepath.Rel(root, dir)`** (`ignore.go:371`). This *is* a
  security decision — it gates the hard-coded `.annotations` /
  `.scratchpad-lock` reserved-name guard (`rel == "."`) and selects which ignore
  segments apply. It is nonetheless not defeatable by spelling: I traced all
  eight call sites and every one passes a `dir` built by
  `filepath.Join(Root(), …)` from the *same* `Root()` string the `Rel` is taken
  against — `visibleSegments` (`store.go:207`), `List` (`:520`), `Watches`
  (`:1006`), and `internal/web`'s four sites, all via `logicalFolderPath`
  (`server.go:689`), which is literally `filepath.Join(store.Root(), rel)`. The
  8.3-alias and case hazards of threat model §4.7 require the two operands to be
  spelled differently by different producers; here they have one producer.

  > **CORRECTION (P6.3 F1 — see §10).** The paragraph above is true of the
  > `dir` operand and the `filepath.Rel` it feeds, and it is **not the
  > operand that matters**. `ignore.go:390` makes *two* comparisons, and the
  > reserved-name deny uses the second one — `nameEquals(name, …)` — whose
  > `name` operand **does** have two producers, one of them a requester-
  > supplied URL segment. I stated the precondition for the hazard and then
  > verified it on the operand that does not have it. F1 is upheld; the fix
  > and the measurement are in §10. This bullet is left standing rather than
  > rewritten, because the shape of the mistake is the useful part.
- **`alreadyInsideRoot`** (`storefs_windows.go:597`) — the prefix half is the
  *fallback*. The primary is `FILE_ID_INFO` identity via a handle-by-handle
  open of the canonicalised target (`:585`). The prefix half answers only
  "inside", never "is", and a bypass yields a self-watch bounded by the
  identity-keyed cycle guard in `List`/`Watches`. This is RR12/RW14, accepted.
- **`readlinkAt`'s `\??\Volume{` and `\??\UNC\` prefixes**
  (`link_windows.go:183,196`). These operate on the reparse buffer read from an
  open handle, not on a re-resolved path, and they *refuse* — fail-closed. The
  result then passes `validateAbsoluteWindowsPath` and a component walk.

Everything else in the sweep is a `.html`/`.md` suffix test, a display-scoped
`HasPrefix(a.Project+"/", prefix)` in `internal/web`, gzip content-type
handling, or CLI flag parsing.

### 1.3 Every mutating entry point is handle-anchored — **CONFIRMED**, with one bounded window named

| Entry point | Root pinned | Parent pinned | Authorising check | Mutation | Re-resolution between? |
|---|---|---|---|---|---|
| `Publish` | `openRootedFS(true)` — tag + `isDir` + `checkRootIdentity` | `rfs.openRealDir(segs, true, true)`, strict per segment | `rejectArtifacts` via `dirHasHTMLFD(fd)` **on the pinned fd** | `mkdirClaim(parent, name)` → `openDirAt(parent, name)` → `writeFileAt` | **none** |
| `Watch` | same | same | target checks are outside containment; store-side checks are on the pinned parent | `symlinkAt(parent, real, name)` — claim, reopen, FSCTL, all on one handle chain | **none store-side** |
| `Unwatch` | `openRootedFS(false)` | `rfs.openRealDir(segs, false, false)` — refuses any reparse ancestor | `isLinkAt(parent, name)` | `unlinkAt(parent, name)` | see below |
| `Delete` | same | same | `isLinkAt`, then `openDirAt`+`dirHasHTMLFD` | `unlinkAt` / `rmdirAt` / `removeTreeAt(parent, name)` | **none that matters** — `removeTreeAt` re-opens with the *strict* primitive and that open **is** the classification |
| `SaveNotes` / `ResolveNote` / `ReplyNote` / notes delete | `openAnnotationFS` pins root then strict-opens `.annotations` from it | `annotationFS.openDir`, strict per segment | `rev` guard under `lockDocument` inside the rendezvous | `atomicWriteFileAt` — temp `FILE_CREATE` on the pinned parent, rename via `NtSetInformationFile(FileRenameInformationEx, RootDirectory=parent)` through the temp's own handle | **none** |
| `removeNotesFor` (from Delete/Unwatch) | same | same | — | `removeSubtree` → `removeTreeAt` | **none** |

The one residual window: in `Unwatch` and `Delete`, `isLinkAt(parent, name)` and
the subsequent `unlinkAt(parent, name)` are two separate opens of the same name
against the same pinned parent. A2 can substitute the entry between them.
**Bounded and not an escape:** `unlinkAt` opens whatever is at the name with
`FILE_OPEN_REPARSE_POINT|FILE_DIRECTORY_FILE` and POSIX-disposes *that handle*,
so the worst case is that a different store-root entry is unlinked — something
A2 could do directly — and it can never reach a link's target. Linux has the
identical shape (`Fstatat` then `Unlinkat`) and always has. Recorded, not
raised.

### 1.4 The two Linux-affecting fixes — **both genuinely closed, not narrowed**

**`visibleSegments` (P3.13 F-1).** The artifact short-circuit is now gated on
`dir != root` (`store.go:202`). Traced: on iteration 1 `dir == root`, so the
short-circuit is skipped and `Visible(root, seg0, …)` **always** runs. The
short-circuit can only fire from iteration 2 onward, i.e. after `seg0` has
passed `Visible` and `root/seg0` has been found to hold `.html` — which is
exactly the intended semantic ("inside a real, visible artifact; the rest is
assets"). A stray root-level `.html` can no longer disable anything. Regression
test `TestRootLevelHTMLDoesNotDisableIgnoreRules` (`ignore_test.go:312`) asserts
eight hidden paths stay hidden **and** carries a positive control proving real
artifact assets stay reachable; `TestRootLevelHTMLDoesNotExposeHiddenPathsOverHTTP`
covers the HTTP route. Both run on both platforms.

The companion half, F-2, is also real: `matchName` now exists as a genuine
platform pair (`names_windows.go:79` folds both operands, `names_linux.go:23` is
byte-identical to the `path.Match` it replaced), `matchSegments` routes through
it (`ignore.go:174`), and `TestMatchNameCaseVariants` /
`TestVisibleDefaultIgnoresCaseVariants` assert the platform-appropriate answer
on **both** platforms rather than skipping on Linux.

**A11 ancestor traversal.** Closed on both platforms, by the same shape:

- Linux `openAbsoluteDirNoFollow` (`storefs_linux.go:440`) — refuses a relative
  target, anchors at `/` via `openFilesystemRootNoFollow`, then `openDirAt`
  (`O_NOFOLLOW|O_DIRECTORY`) per component.
- Windows `openAbsoluteDirNoFollowWin` (`storefs_windows.go:462`) —
  `validateAbsoluteWindowsPath`, anchors at `C:\` via
  `openVolumeRootNoFollow`, then `openRealDirAt` per component.

I verified this is the *only* route: the sole consumers of `readlinkAt`'s output
in `internal/store` are `crossWatchBoundary` → `openAbsoluteDirNoFollowWin`,
`sameWatchTarget` (identity, also via the component walk), and two display
strings. No path-based open of a link target survives anywhere in the package.
Tests: `TestOpenAbsoluteDirNoFollowRefuses{RelativeTarget,SymlinkAncestor,FinalComponentSymlink}`
(Linux), `TestOpenAbsoluteDirNoFollowWinRefuses{RelativeTarget,UNCTarget,JunctionAncestor}`
plus `…OpensRealTarget` as positive control (Windows, added in `2d51cb3`),
`TestBrowseRefusesWatchAncestorSymlinkSwap` (integration, shared), and
`TestWatchResolvesSymlinkedAncestorAtCreation` pinning the compatibility case.

**But the same hazard is still open in a second package.** `internal/watch`'s
`desiredDirs` (`watch.go:271-284`) crosses the watch boundary by its *own*,
path-based mechanism: `entry.IsDir()`, then a follow-through `os.Stat(path)`,
then `walk(path, …)` with `openWatchDir(path)` — no ancestor discipline, no
handle anchoring, no strict open. It honours the one-crossing rule
(`isLink && crossedLink → continue`) but not the no-follow-ancestors rule. This
is P3.13 F-3, unremediated. It serves no content and reads no file, so the
consequence is *which directories receive fsnotify registrations*, not
disclosure. Honest answer to the question as posed: **closed in `internal/store`
on both platforms; the identical defect class remains in `internal/watch`.**

## 7. AC10 — "a final independent security review finds no known path-based TOCTOU escape"

### **MET.**

Evidence, in the order I would want it challenged:

1. **Every mutating entry point is handle-anchored, verified by trace, not by
   claim.** §1.3's table covers all six. In each, the handle is pinned before the
   check that authorises the write, and no path string is re-resolved between
   them. `ntOpenAt` enforces the single-component rule at runtime, so no walk
   ever hands the kernel more than one component of attacker-reachable structure.
2. **The classification primitive cannot be raced.** `openStrictAt` opens and
   reads `FILE_ATTRIBUTE_TAG_INFO` from *the same handle* — there is no
   stat-then-open window at all — and `removeTreeAt` goes further, making the
   attempted strict open itself the classification, so a mid-walk substitution
   (`A6.swap_midwalk`) is caught by construction rather than detected.
3. **The one measured containment break in the whole corpus is closed on both
   platforms.** `A11.ancestor_swapped` was not a race — the ancestors were never
   validated, so the condition was persistent — and the handle-by-handle walk
   from the filesystem/volume root removes the path string it depended on.
4. **The two Linux-affecting fixes are closed rather than narrowed** (§1.4),
   each with a regression test carrying a positive control.
5. **`OBJ_DONT_REPARSE`, the primitive P1.7 F1 caught the ADR wrongly relying
   on, is genuinely not load-bearing** (§1.1) — I checked this by enumeration,
   because it is precisely the class of claim this project has already had to
   retract once.
6. **An independent prior reviewer reached the same conclusion by a different
   route.** P3.13 traced nine mutating entry points on both platforms and found
   no validate-then-open. I did not read its trace before doing my own.

Three qualifications, none of which I think overturns the verdict:

- **AC10 is a statement about escapes, not about all check-then-use.** Two
  check-then-use windows survive and I have named both: `isLinkAt`→`unlinkAt` in
  `Unwatch`/`Delete` (bounded to unlinking a different *store* entry, matching
  Linux, no target reachable), and `internal/watch`'s path-based boundary
  crossing (item 7 — a genuine instance of the defect class, in a component that
  serves no content). Neither is an escape. Both should be in the register rather

- **Two dispositions describe mechanisms that are not the ones running** (FD-2,
  FD-3). Both happen to be safe — the code is stricter than the document in one

  rule-1 false closure. A reviewer trusting the ADR would be wrong twice.
- **No one in this review chain has had a Windows host.** Every Windows
  conclusion here is code reading plus CI logs. The CI evidence is real and

## 10. Adjudication — P6.3 F1 (8.3 short-name alias vs. `Visible`)

**F1 is upheld.** Its critique of this audit is correct, its mechanism is
correct, and its impact statement is **too generous** — the exposure is content,
not only listings. Fixed at `7cd3306`.

### 10.1 The critique of §1.2 is correct

`ignore.go:390` makes **two** comparisons:

```go
if rel == "." && (nameEquals(name, AnnotationsDir) || nameEquals(name, lockFileName)) {
```

`rel` comes from `filepath.Rel(root, dir)`. `name` is passed in by the caller.
§1.2 traced the **`dir`** operand, established it has a single producer, and
concluded the line is "not defeatable by spelling". That is sound reasoning
about `rel` and says nothing about `name`, which is the operand the
reserved-name deny actually compares — and `name` has **two** producers:

| Producer | Call sites | Spelling |
|---|---|---|
| `os.DirEntry.Name()` | `List` (`store.go:520`), `Watches` (`:1006`), `internal/web` ×4, `internal/watch` (`watch.go:283`) | the filesystem's own — always the long name. Safe. |
| **a requester-supplied URL segment** | `visibleSegments` (`store.go:207`) — one site | whatever the caller typed. **The hazard.** |

I wrote down the precondition for the hazard — *"the two operands [must be]
spelled differently by different producers"* — and then checked it against the
operand that does not satisfy it. That is a worse error than missing the issue
outright, because it produced a positive clearance rather than a gap. Threat
model §4.7(b) had named `Visible` explicitly; I read that section and still
checked the wrong half.

### 10.2 The structural half, verified independently

- `validateSegment` → `checkLookupSegmentPlatform` (`names_windows.go`) refuses
  `:`, a trailing dot/space and reserved DOS device basenames. It does **not**
  refuse `~`. `ANNOTA~1` passes validation.
- `nameEquals` is `strings.EqualFold`; `EqualFold("ANNOTA~1", ".annotations")`
  is false. The reserved-name deny does not fire.
- `matchName` is `path.Match` over lower-cased operands;
  `path.Match("node_modules", "node_m~1")` is false. No `defaultIgnores` or
  `.scratchpadignore` rule fires either.
- `visibleSegments` then advanced `dir` with the **aliased** spelling, so an
  anchored multi-segment rule (`node_modules/**`) was defeated for every deeper
  segment too — a consequence F1 did not name and which widens it.

Create paths were never exposed: `nameRe` excludes `~`, so `Publish`/`Watch`
cannot be driven through an alias.

### 10.3 The decisive step, settled by measurement

F1's whole finding rests on one unexecuted question: *does a
`RootDirectory`-relative `NtCreateFile` — the store's own traversal primitive,
not a Win32 path open — resolve an 8.3 alias?* If not, F1 collapses to a
documentation note.

`TestShortNameAliasDoesNotBypassVisibility`
(`internal/store/shortname_windows_test.go`) settles it on CI. It opens both
`.annotations` and its alias through `openRealDirAt` from the pinned root and
compares `objectIDOf`, and **logs the answer either way** under a
`P6.3.F1 MEASUREMENT:` marker — a "no" is a result worth recording, not a
silent pass. The alias itself is obtained from `GetShortPathNameW` rather than
predicted from NTFS's generation algorithm; predicting it is the mistake F1's
own fallback fix would have baked in, and the mistake P-5 made on this branch
when it reasoned about `EvalSymlinks` from Go's source instead of measuring it.

**Result — measured, run
[32993449212](https://github.com/chaitanyaSoni96/scratchpad/actions/runs/32993449212),
jobs `98256532795` (symlink-capable) and `98256533002` (degraded), both
`windows-2025`, commit `7cd3306`:**

```text

             "my-long-artifact-name"="MY-LON~1"(true)
P6.3.F1 MEASUREMENT: a RootDirectory-relative NtCreateFile RESOLVES the 8.3
alias "ANNOTA~1" to the same object as ".annotations" (alias open err=<nil>).
```

**F1's mechanism is confirmed, not merely plausible.** All three names carry an

`internal/store` is `ok` in **both** Windows jobs on that run. The run is red,
but for an unrelated reason in a package this work does not touch — see §10.8.

The test is capability-gated (`SKIP(8dot3-capability)`) because a volume with

owns CI:** add a zero-`SKIP(8dot3-capability)` assertion to

### 10.4 The impact statement — F1 bounds it too tightly

F1 bounds the exposure to *"**listing** disclosure, not content"*, reasoning
that `/a/` serves a file only under an `.html`-bearing ancestor and that neither
`.annotations` nor a credential directory has one.

**That half holds, and I have pinned it.** Note sidecars are `<doc>.html.json`;
`dirHasHTMLFD`'s `HasSuffix(…, ".html")` correctly does not match them, and
`ResolveDoc` requires `.md`. Neither route can serve a sidecar. Likewise the
credential entries `defaultIgnores` names: `.ssh/`, `.gnupg/`, `.aws/` hold
`id_rsa` / `credentials`, which are neither `.md` nor artifact assets, and
`.env` / `.netrc` / `*.pem` are files, which are only ever served as assets
*inside* an artifact — where visibility checks already stop by design.

**But it does not generalise, and the generalisation is the exposure.** An
ignore-hidden **directory** is not a credential directory; it is any directory,
and two routes serve bytes out of one:

- `ResolveDoc` serves **any `.md`** under a visible path;
- `ResolvePath` resolves **any artifact** (a directory holding `.html`) and
  every asset beneath it.

`node_modules` and `.venv` routinely contain both, and a user-written
`.scratchpadignore` rule — whose entire purpose is "do not show this" — was
fully bypassable. `TestIgnoreHidesContentNotJustListings` (`ignore_test.go`,
both platforms) makes this executable rather than argued: it asserts markdown
and an artifact inside `node_modules/` and inside a `.scratchpadignore`-hidden
directory are refused, with a **positive control** proving byte-identical
content one directory over *is* served — so the ignore rule is demonstrably the
only thing withholding it.

**Verdict on severity: F1 is at least a Medium, and on a `LAN=1` instance it is
a Medium-High.** It is still not a containment escape — the segment remains a
single component opened relative to a pinned parent, so **AC10 is unaffected** —
and the content reachable is markdown and HTML the user asked to hide, never a
credential file and never a note sidecar. I am not re-labelling it; I am
recording that the ceiling is higher than F1 stated.

One smaller correction: F1 says "`Delete` and `Unwatch` on an aliased path fail
closed". True over HTTP, and for a better reason than the one given —
`handleDelete` → `resolveRequest` → `ResolvePath`, which requires an artifact,
so a non-artifact 404s before `rmdirAt`'s non-empty refusal is ever reached.

### 10.5 The fix, and why not the two alternatives

`canonicalLookupName(dir, name)` — the third member of the ADR §7.4
name-comparison pair, beside `nameEquals` and `matchName`. It asks the
filesystem what the entry is called and `visibleSegments` decides on **that**;
the canonical name also advances `dir`, closing the anchored-rule variant in
§10.2. Compile-time no-op on Linux.

| Option | Closes reserved names | Closes ignore rules (the content half) | Basis | Cost |
|---|---|---|---|---|
| **1. `objectIDOf` after the open** (F1's preference) | yes | **no** | sound — the "correct test" of threat model §4.10(c) | needs `.annotations`' identity on every lookup, and puts a policy decision inside `openBrowsableDir`, a mechanism function (R20's reverse falsifier) |
| **2. refuse the 8.3 *shape*** (F1's fallback) | yes | yes, for aliases | **a string guess at NTFS's generation algorithm** | a repo's literal `FOO~1.TXT` becomes unaddressable; wrong in one direction or the other the moment the algorithm or the repo surprises us |
| **3. canonicalise the name** (landed) | yes | **yes** | **a fact obtained from the filesystem** | one `GetLongPathNameW` per lookup segment, alongside an `os.Stat` and a `hasHTML` `ReadDir` already there |

Option 1 fixes the smaller half — the two reserved names — and leaves every
ignore rule, i.e. every content route in §10.4, still bypassable. That is
decisive against it on its own; the layering objection is secondary. Option 2 is
one line and I nearly took it, but it reasons *about* the filesystem instead of
*asking* it, which is the failure mode this branch has already paid for twice
(P1.7 F1's `OBJ_DONT_REPARSE`, P4.7 P-5's `EvalSymlinks`). Option 3 is the same
philosophy that made `matchName` and `nameEquals` correct — measure, do not
predict — and it generalises to any future aliasing mechanism rather than to 8.3
alone.

**Normalise the decision, not the request.** A caller may still address a
*visible* entry by any spelling NTFS accepts, so case-variant URLs
(`/a/ART/index.html`) keep working exactly as `docs/windows.md` documents. Only
the visibility decision moves to the on-disk name. The test's **fourth section
is a negative control for precisely this**: an ordinary, visible artifact
addressed by its own 8.3 alias must stay reachable — an assertion Option 2 would
fail, so the trade-off is pinned in code and not merely argued here.

Both new tests were falsified before being trusted: neutering `Visible` makes
`TestIgnoreHidesContentNotJustListings` fail with eight errors, and rewriting
the Linux pair member makes `TestCanonicalLookupNameIsOnDiskSpelling` fail.

Flagging rather than fixing, for that task's owner. Two things make it worth
flagging loudly rather than as a passing note:

1. **It is RW23, which the ADR records as closed** (§6.11, finding F6). A
   regression there is a persistent failure to *start* the web process, not a

2. **The gating change worked.** `c035304` removed the `continue-on-error`

   that regime, and it caught a real regression in a security-relevant control

## 11. AC5's coverage half — the `internal/winspike` migration inventory

Requested as an inventory and a plan, not as tests: another task holds
`internal/store`. Nothing in this section was implemented.

### 11.1 What `winspike` actually contributes today

Measured, not assumed:

- **56 `RequireProperty` call sites.** `RequireProperty` (`report_test.go:48`)
  calls `t.Errorf` when the property is false, so these — and only these — can
  fail a build. Everything else is data.
- **301 `Report` call sites**, of which 110 are `NotMeasured`, 6 `No`, 2
  `Partial`, 56 `Info`, 113 a dynamic `boolVerdict`. **None can fail.** The
  file says so itself: *"Measurements report; they do not assert. A surprising
  answer is data, not a test failure."* This is the right design for a spike
  and it means the corpus is far smaller than its 369 measurement lines suggest.
- **53 of the 56 exercise a *prototype* function** — `winspike.OpenRoot`,
  `(*Root).OpenRealDir`, `RemoveTreeAt`, `AtomicWriteFile`, `MkdirAt`,
  `OpenRegularFileAt`, `OpenBrowsableDir`. Three do not: `P14.junction_not_dir`
  (`os.Lstat`), `RR1.removeall` (`os.RemoveAll`), `M1.intermediate` (the raw
  unexported `ntOpenAt`).
- **On Linux the package is empty.** `go test ./internal/winspike` reports
  `[no test files]`; `doc_other.go` is a `//go:build !windows` stub. It also
  runs in its **own workflow** (`Winspike (Phase 1 temporary)`), not in `CI`, so
  deleting the package removes a separate green check rather than shrinking an
  existing one.
- **Nothing imports it.** `internal/store` and `internal/watch` carry comments
  saying logic was *copied, not imported*, "because that package is scheduled
  for deletion". `doc_other.go` says it is "deleted at the end of Phase 1". We
  are in Phase 6.

**A prototype function is not the product function.** That is the whole reason
these 53 are not coverage of `internal/store`: they assert that
`winspike.OpenRoot` refuses a file, not that `openRootedFS` does. The two are
mechanically similar and were written from the same design, which is exactly
what makes the substitution easy to miss.

### 11.5 What cannot be migrated — stated plainly, as asked

**Five properties are facts about Windows and Go, not properties of our code.**
There is no product API to call, so no product test can assert them. They are
load-bearing anyway, because each is the *reason* a design decision was made:

| Property | The fact | What it justifies | What is lost |
|---|---|---|---|
| `A5.obj_dont_reparse_inert_for_unknown_tags` | `OBJ_DONT_REPARSE` does **not** refuse a non-Microsoft tag when no driver services it | The entire strict-open primitive (ADR §2.1, P1.7 F1) | The evidence that the falsified design was falsified. A future reader sees `noFollowAttrs` carrying `OBJ_DONT_REPARSE` and may reasonably conclude it is the control |
| `M1.intermediate` | `OBJ_DONT_REPARSE` *does* fail on a Microsoft-tagged **intermediate** component | Why the flag is kept at all — "necessary and not sufficient" | The other half of the same argument |
| `P14.junction_not_dir` | Go reports a junction as neither `ModeSymlink` nor `ModeDir` | R5, `classifyEntry`, and `IsLinkEntry`'s `ModeIrregular` over-approximation | The basis for the over-approximation being *measured* rather than guessed |
| `RR1.removeall` | `os.RemoveAll` on a junction removes the link, not the target | That the danger is specifically a hand-rolled walk — and ours is the hand-rolled one | The scoping argument for RW1 |
| `M9`, `M10.posix_nt` | A handle-relative rename variant exists; POSIX delete removes the name immediately | `renameAtNT`'s class choice and `deleteByHandlePosix` | Why those two APIs and not the obvious Win32 ones |

**These must not be deleted, and must not be faked into product tests.** Writing
a test that calls `ntOpenAt` with and without `OBJ_DONT_REPARSE` inside
`internal/store` would put a Win32 conformance probe in a package whose tests are
supposed to be about the store's behaviour — and it would fail on a machine with
a filter driver installed, which is the very condition it is measuring.

The honest disposition is that **they change category, not location**: from
*executable assertion* to *recorded measurement with a run id*. Three of the five
are already cited that way in the ADR (§2.1, §5.2, §4.5). The other two,
`M9` and `M10.posix_nt`, are cited by id but their meaning lives only in the
prototype's source. **Recommended before deletion:** a short §11.2 appendix in
the ADR quoting the five measurements verbatim with run `32908643117` and the
job ids, so the design rationale survives the package. That is the difference
between "we measured this" and "a deleted file once measured this".

**One property diverges and must be migrated inverted, not copied.**
`A5.unknown_tag_removed` asserts the prototype's `RemoveTreeAt` **removes** an
unknown-tag entry. The product **refuses** it at `Delete`'s top-level dispatch
(P6.2 FD-2, now corrected in ADR §4.5). A mechanical migration would assert the
opposite of shipped behaviour. It is already covered, correctly inverted, by
`TestUnknownTagEntryIsInvisibleAndInert`. Flagged because it is the one row in
the whole corpus where copying the prototype's assertion would introduce a bug.

**One more divergence worth carrying:** `P14.unlink_junction` exercises
`winspike.DeleteAt`, which takes its options from the caller. The product's
`unlinkAt` hard-codes `FILE_DIRECTORY_FILE` (P3.13 F-6, still open), so a
*file*-shaped allowlisted link is un-removable on Windows. The prototype can
assert a property the product does not have. Migrate the directory case; do not
migrate the file case without first deciding F-6.

### 11.6 AC5 verdict, restated

Unchanged: **NOT MET on the coverage half.** The gating half is closed
(`c035304`). Three matrix cells still have no product test, and §11.4 items 1–3
are exactly what closes them. Until then `internal/winspike` cannot be deleted
without losing coverage — which is the finding: **a package documented as
"deleted at the end of Phase 1" is, in Phase 6, still the only place three
release-blocking matrix cells are exercised at all.**
