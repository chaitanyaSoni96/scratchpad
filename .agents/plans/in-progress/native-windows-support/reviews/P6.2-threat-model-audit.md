# P6.2 Final Threat-Model Audit

## Verdict

**The containment design holds. The release gate does not.**

Two separable judgements, and they point opposite ways:

- **Acceptance criterion 10 is MET.** I re-traced every mutating entry point on
  both platforms against the shipped code and found **no path-based TOCTOU
  escape**. Every mutation issues through a handle pinned *before* the check
  that authorised it. `OBJ_DONT_REPARSE` is genuinely not load-bearing anywhere
  — I enumerated all 17 Win32 open sites and confirmed the strict open
  (`FILE_OPEN_REPARSE_POINT` + `FILE_ATTRIBUTE_TAG_INFO` read from the *same*
  handle + a tag allowlist) is the actual primitive at every site that descends.
  No containment decision reduces to a path-prefix comparison. Both
  Linux-affecting security fixes — the `visibleSegments` ignore bypass and the
  A11 ancestor traversal — are genuinely closed in `internal/store`, not
  narrowed.
- **Acceptance criterion 5 is NOT MET**, on two independent grounds, and four
  ADR dispositions are stale or falsely closed.

The single most important thing on this page is not a code defect. It is that
**the CI job which runs the entire Windows security corpus carries
`continue-on-error: true`** (`ci.yml:108`), as do the degraded-mode job
(`:204`) and the Windows stress job (`:336`). The suite is green today — I
checked run `32970247103`, job `98182132443`: 239 result lines, all packages
`ok`, zero symlink-capability skips — but *nothing forces it to stay green*.
RW1's release gate (`MATRIX.Delete.target_replaced` must pass before any Windows
binary ships) is therefore unenforced twice over: the ADR records the missing
branch-protection rule (F12) but not this, which is the nearer of the two
failures. A test that cannot fail the build is weak evidence for a release gate.

(That green run is commit `a956d9b`; the branch has since moved and the run for
the current head had not finished when I wrote this. The point stands
independently of which commit is green — the job's result does not gate.)

Nothing I found lets any operation escape the store root, cross more than one
watch boundary, follow an untrusted link, or overwrite a claimed name.

## 1. The four things I was asked to test rather than accept

### 1.1 `OBJ_DONT_REPARSE` is not load-bearing; the strict open is the primitive — **CONFIRMED**

There are 17 Win32 open sites in `internal/store`. Sixteen are no-follow. One
follows deliberately.

| Site | Disposition | `FILE_OPEN_REPARSE_POINT`? | `OBJ_DONT_REPARSE`? | Same-handle tag check? |
|---|---|---|---|---|
| `openRootedFS` (`storefs_windows.go:125`) | `OPEN_EXISTING` | yes (`FILE_FLAG_`) | n/a (Win32) | **yes** — `attrTagOf` → `isReparse()` refuse, `isDir()` require |
| `openStrictAt` (`:245`) | `FILE_OPEN` | yes | yes | **yes** — `attrTagOf` → `reparseRefusal` |
| `mkdirClaim` (`:308`) | `FILE_CREATE` | yes | yes | n/a (create) |
| `rmdirAt` (`:325`) | `FILE_OPEN` | yes | no (`OBJ_CASE_INSENSITIVE` only) | n/a — opens the entry *as itself* to remove it |
| `openVolumeRootNoFollow` (`:494`) | `OPEN_EXISTING` | yes (`FILE_FLAG_`) | n/a | **yes** |
| `canonicalizeWatchTarget` (`:547`) | `OPEN_EXISTING` | **no — follows** | n/a | `isDir()` only |
| `statAt` (`:613`) | `FILE_OPEN` | yes | no | **yes** — this *is* the classifier |
| `linkTargetIsDir` (`:672`) | `FILE_OPEN` | yes | no | yes |
| `writeFileAt` (`:750`) | `FILE_CREATE` | yes | yes | n/a (create) |
| `readLinkTagAt` (`link_windows.go:67`) | `FILE_OPEN` | yes | no | reads the reparse buffer |
| `symlinkAt` post-claim reopen (`:102`) | `FILE_OPEN` | yes | no | n/a — opens what is at the name |
| `readlinkAt` (`:167`) | `FILE_OPEN` | yes | no | tag allowlist + flags + target validator |
| `unlinkAt` (`:208`) | `FILE_OPEN` | yes | no | n/a — removes the entry |
| `openRendezvousLockFile` (`annotationfs_windows.go:167`) | `FILE_OPEN_IF` | yes | yes | `fileIDOf` identity |
| `openLockFileAt` (`:262`) | `FILE_OPEN_IF` | yes | yes | n/a |
| `atomicWriteFileAt` temp (`:555`) | `FILE_CREATE` | yes | yes | n/a (create) |
| `deleteEntryAt` (`:660`) | `FILE_OPEN` | yes | no | n/a — removes the entry |

Two properties follow, and I checked both by construction rather than by reading
the comments:

1. **Every directory descent goes through `openStrictAt`.** `openRealDirAt` and
   `openDirAt` are both one-line aliases of it (`storefs_windows.go:267,282`);
   the only other directory anchors are `openRootedFS` and
   `openVolumeRootNoFollow`, which apply the identical tag+isDir discipline
   inline. `openRealDir`, `openBrowsableDir`, `openAbsoluteDirNoFollowWin`,
   `mkdirsAt`, `pruneAt`, `annotationFS.openDir`, `removeTreeAt`,
   `walkAnnotationDir`, `List`, `Watches`, `WatchLinkFor` and `crossOrOpen` all
   descend exclusively through those names. There is no bypass.
2. **Removing `OBJ_DONT_REPARSE` would break nothing.** At `FILE_OPEN`
   traversal sites the refusal comes from `attrTagOf` on the returned handle, so
   the flag only short-circuits a Microsoft-tagged component before a handle
   exists — and since `ntOpenAt` enforces a *single* component at runtime
   (`win32_windows.go:145`, a check not a comment), there is no intermediate
   component for it to short-circuit. At the six create dispositions there is no
   post-open classify step at all, and the thing carrying those sites is
   `FILE_OPEN_REPARSE_POINT` (added by P3.14 M3), not `OBJ_DONT_REPARSE`. The
   ADR's own framing — *necessary and not sufficient*, `noFollowAttrs`'
   comment — is accurate, and I could not find a site where it is doing the
   work.

The one following open, `canonicalizeWatchTarget`, is the documented exception:
its output is re-validated by `validateAbsoluteWindowsPath` and then consumed
only by `openAbsoluteDirNoFollowWin`, component by component. It is never
handed to a subsequent `CreateFile` as a path.

### 1.2 No containment decision reduces to a path-prefix comparison — **CONFIRMED**, with the reasoning spelled out

I enumerated every string comparison in the four packages and classified each.
Four of them touch security; none of the four is decisive.

- **`joinInRoot`'s `filepath.Rel` + `HasPrefix("..")`** (`store.go:313-314`),
  reached from `artifactDir`, `existingDir` and `notesPath`. **Not
  load-bearing.** Every segment has already been through `validateName` or
  `validateSegment`, both of which reject `/`, `\`, `.` and `..` outright,
  *before* the join. A segment set that could produce an escaping join cannot
  reach it. The authoritative containment is the per-segment handle walk from
  the pinned root. The joined string is used afterwards only as `Artifact.Dir`,
  a display path.
- **`Visible`'s `filepath.Rel(root, dir)`** (`ignore.go:371`). This *is* a
  security decision — it gates the hard-coded `.annotations` /
  `.scratchpad-lock` reserved-name guard (`rel == "."`) and selects which ignore
  segments apply. It is nonetheless not defeatable by spelling: I traced all
  eight call sites and every one passes a `dir` built by
  `filepath.Join(Root(), …)` from the *same* `Root()` string the `Rel` is taken
  against — `visibleSegments` (`store.go:207`), `List` (`:520`), `Watches`
  (`:1006`), and `internal/web`'s four sites, all via `logicalFolderPath`
  (`server.go:689`), which is literally `filepath.Join(store.Root(), rel)`. The
  8.3-alias and case hazards of threat model §4.7 require the two operands to be
  spelled differently by different producers; here they have one producer.
- **`alreadyInsideRoot`** (`storefs_windows.go:597`) — the prefix half is the
  *fallback*. The primary is `FILE_ID_INFO` identity via a handle-by-handle
  open of the canonicalised target (`:585`). The prefix half answers only
  "inside", never "is", and a bypass yields a self-watch bounded by the
  identity-keyed cycle guard in `List`/`Watches`. This is RR12/RW14, accepted.
- **`readlinkAt`'s `\??\Volume{` and `\??\UNC\` prefixes**
  (`link_windows.go:183,196`). These operate on the reparse buffer read from an
  open handle, not on a re-resolved path, and they *refuse* — fail-closed. The
  result then passes `validateAbsoluteWindowsPath` and a component walk.

Everything else in the sweep is a `.html`/`.md` suffix test, a display-scoped
`HasPrefix(a.Project+"/", prefix)` in `internal/web`, gzip content-type
handling, or CLI flag parsing.

### 1.3 Every mutating entry point is handle-anchored — **CONFIRMED**, with one bounded window named

| Entry point | Root pinned | Parent pinned | Authorising check | Mutation | Re-resolution between? |
|---|---|---|---|---|---|
| `Publish` | `openRootedFS(true)` — tag + `isDir` + `checkRootIdentity` | `rfs.openRealDir(segs, true, true)`, strict per segment | `rejectArtifacts` via `dirHasHTMLFD(fd)` **on the pinned fd** | `mkdirClaim(parent, name)` → `openDirAt(parent, name)` → `writeFileAt` | **none** |
| `Watch` | same | same | target checks are outside containment; store-side checks are on the pinned parent | `symlinkAt(parent, real, name)` — claim, reopen, FSCTL, all on one handle chain | **none store-side** |
| `Unwatch` | `openRootedFS(false)` | `rfs.openRealDir(segs, false, false)` — refuses any reparse ancestor | `isLinkAt(parent, name)` | `unlinkAt(parent, name)` | see below |
| `Delete` | same | same | `isLinkAt`, then `openDirAt`+`dirHasHTMLFD` | `unlinkAt` / `rmdirAt` / `removeTreeAt(parent, name)` | **none that matters** — `removeTreeAt` re-opens with the *strict* primitive and that open **is** the classification |
| `SaveNotes` / `ResolveNote` / `ReplyNote` / notes delete | `openAnnotationFS` pins root then strict-opens `.annotations` from it | `annotationFS.openDir`, strict per segment | `rev` guard under `lockDocument` inside the rendezvous | `atomicWriteFileAt` — temp `FILE_CREATE` on the pinned parent, rename via `NtSetInformationFile(FileRenameInformationEx, RootDirectory=parent)` through the temp's own handle | **none** |
| `removeNotesFor` (from Delete/Unwatch) | same | same | — | `removeSubtree` → `removeTreeAt` | **none** |

The one residual window: in `Unwatch` and `Delete`, `isLinkAt(parent, name)` and
the subsequent `unlinkAt(parent, name)` are two separate opens of the same name
against the same pinned parent. A2 can substitute the entry between them.
**Bounded and not an escape:** `unlinkAt` opens whatever is at the name with
`FILE_OPEN_REPARSE_POINT|FILE_DIRECTORY_FILE` and POSIX-disposes *that handle*,
so the worst case is that a different store-root entry is unlinked — something
A2 could do directly — and it can never reach a link's target. Linux has the
identical shape (`Fstatat` then `Unlinkat`) and always has. Recorded, not
raised.

### 1.4 The two Linux-affecting fixes — **both genuinely closed, not narrowed**

**`visibleSegments` (P3.13 F-1).** The artifact short-circuit is now gated on
`dir != root` (`store.go:202`). Traced: on iteration 1 `dir == root`, so the
short-circuit is skipped and `Visible(root, seg0, …)` **always** runs. The
short-circuit can only fire from iteration 2 onward, i.e. after `seg0` has
passed `Visible` and `root/seg0` has been found to hold `.html` — which is
exactly the intended semantic ("inside a real, visible artifact; the rest is
assets"). A stray root-level `.html` can no longer disable anything. Regression
test `TestRootLevelHTMLDoesNotDisableIgnoreRules` (`ignore_test.go:312`) asserts
eight hidden paths stay hidden **and** carries a positive control proving real
artifact assets stay reachable; `TestRootLevelHTMLDoesNotExposeHiddenPathsOverHTTP`
covers the HTTP route. Both run on both platforms.

The companion half, F-2, is also real: `matchName` now exists as a genuine
platform pair (`names_windows.go:79` folds both operands, `names_linux.go:23` is
byte-identical to the `path.Match` it replaced), `matchSegments` routes through
it (`ignore.go:174`), and `TestMatchNameCaseVariants` /
`TestVisibleDefaultIgnoresCaseVariants` assert the platform-appropriate answer
on **both** platforms rather than skipping on Linux.

**A11 ancestor traversal.** Closed on both platforms, by the same shape:

- Linux `openAbsoluteDirNoFollow` (`storefs_linux.go:440`) — refuses a relative
  target, anchors at `/` via `openFilesystemRootNoFollow`, then `openDirAt`
  (`O_NOFOLLOW|O_DIRECTORY`) per component.
- Windows `openAbsoluteDirNoFollowWin` (`storefs_windows.go:462`) —
  `validateAbsoluteWindowsPath`, anchors at `C:\` via
  `openVolumeRootNoFollow`, then `openRealDirAt` per component.

I verified this is the *only* route: the sole consumers of `readlinkAt`'s output
in `internal/store` are `crossWatchBoundary` → `openAbsoluteDirNoFollowWin`,
`sameWatchTarget` (identity, also via the component walk), and two display
strings. No path-based open of a link target survives anywhere in the package.
Tests: `TestOpenAbsoluteDirNoFollowRefuses{RelativeTarget,SymlinkAncestor,FinalComponentSymlink}`
(Linux), `TestOpenAbsoluteDirNoFollowWinRefuses{RelativeTarget,UNCTarget,JunctionAncestor}`
plus `…OpensRealTarget` as positive control (Windows, added in `2d51cb3`),
`TestBrowseRefusesWatchAncestorSymlinkSwap` (integration, shared), and
`TestWatchResolvesSymlinkedAncestorAtCreation` pinning the compatibility case.

**But the same hazard is still open in a second package.** `internal/watch`'s
`desiredDirs` (`watch.go:271-284`) crosses the watch boundary by its *own*,
path-based mechanism: `entry.IsDir()`, then a follow-through `os.Stat(path)`,
then `walk(path, …)` with `openWatchDir(path)` — no ancestor discipline, no
handle anchoring, no strict open. It honours the one-crossing rule
(`isLink && crossedLink → continue`) but not the no-follow-ancestors rule. This
is P3.13 F-3, unremediated. It serves no content and reads no file, so the
consequence is *which directories receive fsnotify registrations*, not
disclosure. Honest answer to the question as posed: **closed in `internal/store`
on both platforms; the identical defect class remains in `internal/watch`.**

## 7. AC10 — "a final independent security review finds no known path-based TOCTOU escape"

### **MET.**

Evidence, in the order I would want it challenged:

1. **Every mutating entry point is handle-anchored, verified by trace, not by
   claim.** §1.3's table covers all six. In each, the handle is pinned before the
   check that authorises the write, and no path string is re-resolved between
   them. `ntOpenAt` enforces the single-component rule at runtime, so no walk
   ever hands the kernel more than one component of attacker-reachable structure.
2. **The classification primitive cannot be raced.** `openStrictAt` opens and
   reads `FILE_ATTRIBUTE_TAG_INFO` from *the same handle* — there is no
   stat-then-open window at all — and `removeTreeAt` goes further, making the
   attempted strict open itself the classification, so a mid-walk substitution
   (`A6.swap_midwalk`) is caught by construction rather than detected.
3. **The one measured containment break in the whole corpus is closed on both
   platforms.** `A11.ancestor_swapped` was not a race — the ancestors were never
   validated, so the condition was persistent — and the handle-by-handle walk
   from the filesystem/volume root removes the path string it depended on.
4. **The two Linux-affecting fixes are closed rather than narrowed** (§1.4),
   each with a regression test carrying a positive control.
5. **`OBJ_DONT_REPARSE`, the primitive P1.7 F1 caught the ADR wrongly relying
   on, is genuinely not load-bearing** (§1.1) — I checked this by enumeration,
   because it is precisely the class of claim this project has already had to
   retract once.
6. **An independent prior reviewer reached the same conclusion by a different
   route.** P3.13 traced nine mutating entry points on both platforms and found
   no validate-then-open. I did not read its trace before doing my own.

Three qualifications, none of which I think overturns the verdict:

- **AC10 is a statement about escapes, not about all check-then-use.** Two
  check-then-use windows survive and I have named both: `isLinkAt`→`unlinkAt` in
  `Unwatch`/`Delete` (bounded to unlinking a different *store* entry, matching
  Linux, no target reachable), and `internal/watch`'s path-based boundary
  crossing (item 7 — a genuine instance of the defect class, in a component that
  serves no content). Neither is an escape. Both should be in the register rather
  than absent from it, which is why they are.
- **Two dispositions describe mechanisms that are not the ones running** (FD-2,
  FD-3). Both happen to be safe — the code is stricter than the document in one
  case and equivalent-by-another-route in the other — but "the ADR says X and X
  does not execute" is the exact failure mode that produced RW4 and the §6.6
  rule-1 false closure. A reviewer trusting the ADR would be wrong twice.
- **No one in this review chain has had a Windows host.** Every Windows
  conclusion here is code reading plus CI logs. The CI evidence is real and
  currently green — but see item 1: it is not gating.

## 8. What I could not verify

Stated plainly, because an honest "unverified" is worth more than an assumed
pass.

- **Anything requiring a Windows machine.** I read the Windows code and the CI
  logs; I did not run a Windows binary. Every Windows verdict above is
  "the code says so and CI agrees", never "I observed it".
- **The ten environmental items in §6's second table.** ReFS/Dev Drive, SMB,
  FAT/exFAT, the antivirus transient distribution, cloud placeholder tags, a
  genuinely non-elevated session, `ReadDirectoryChangesW` overflow, arm64 at
  runtime, 32-bit, directory hard links. Two of these — RW9's Dev Drive check
  and RW16's non-elevated confirmation — were promised as **manual pre-beta
  checks** and I can find no record that either was done.
- **Whether the `\??\Volume{` prefix test is exhaustive** for distinguishing a
  volume mount point from a junction. It matches the documented substitute-name
  form; I have no way to confirm no other form reaches the same effect, and the
  `FILE_ID_INFO.VolumeSerialNumber` cross-check threat model §4.3(c) proposed as
  the second layer is not implemented.
- **Whether `IsLinkInfo`/`IsLinkEntry`'s `ModeIrregular` over-approximation has
  a reachable phantom.** P4.7 P-11 says it does not today and the guard is
  implicit; I could not construct a counter-example, but I also could not prove
  its absence.
- **The two installer verification jobs**, which are red. Out of scope for this
  audit and owned elsewhere — but note the installer is what registers the
  Scheduled Task and therefore what decides the *bind address* in a real
  deployment. Invariant 9 holds in `install.ps1`'s source; whether it holds
  end to end is unproven while those jobs fail.
- **The branch was moving under me.** Eleven commits landed while this audit
  was in progress. The trace work is `eecbed6`; I re-verified every finding by
  grep and re-ran the full local suite at `a70dceb` (see the Method caveat), and
  closed register item 8 as a result. I did **not** re-trace §1.1–§1.3 against
  `a70dceb` — the diff between the two touches `internal/watch`, the installer
  and docs, not the `internal/store` containment primitives those sections
  cover, but that is an inference from the diffstat rather than a re-trace.

## 9. What would close the gate

Small, and all four are named above:

1. Remove `continue-on-error` from `windows-symlink-required`,
   `windows-degraded-test` and `stress-windows`; add the branch-protection rule
   RW1's F12 asks for. *(Register item 1.)*
2. Add three tests: root-is-a-file, root-is-a-reparse-point (per tag), and
   Delete/parent-replaced against the shipped code. *(Register item 2, AC5.)*
3. Correct the four dispositions in §3.2 — FD-1 needs live owners or explicit
   acceptances, FD-2 and FD-3 need the ADR text to match the code, FD-4 needs
   §6.9 revised or its "complete list" claim withdrawn.
4. Record register items 6, 9 and 13 somewhere durable; they are currently
   accepted only in this document.

None of these is a containment fix. The containment work is done.
