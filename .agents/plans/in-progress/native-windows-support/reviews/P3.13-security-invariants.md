# P3.13 Security Invariants Review

## Verdict

**PASS WITH FINDINGS.**

The question P3.13 exists to answer — *is there a validate-then-open path in any
mutation?* — is answered **no**. I traced all nine mutating entry points from
untrusted input to the final handle operation, on both platforms, and every one
of them issues its mutation through a descriptor or `HANDLE` that was pinned
**before** the check that authorised it. No mutation re-resolves a path string
between the authorising classification and the write. ADR §2.1's four
consequences hold as written, and the `A11.ancestor_swapped` fix is genuinely
present on **both** platforms (`openAbsoluteDirNoFollow` /
`openAbsoluteDirNoFollowWin`) rather than assumed.

Two findings are nevertheless **release blockers**, and neither is a TOCTOU:

- **F-1 (High, cross-platform, pre-existing).** A single `*.html` file placed
  directly in the store root disables **every** visibility rule for path
  lookup — including the hard-coded `.annotations` reserved-name guard and the
  credential entries in `defaultIgnores`. I reproduced unauthenticated reads of
  a `*.pem` and `.md` files inside `.git`/`node_modules`/`.venv`, and an
  unauthenticated recursive `DELETE` of an artifact inside `.git`. One
  mis-ordered line in `visibleSegments`.
- **F-2 (High, Windows-only).** ADR §7.4's second bullet — the `matchName`
  platform pair for `defaultIgnores` — was **never implemented**. `path.Match`
  is still called directly and is case-sensitive on both platforms, so RR5's
  credential-ignore half is live on NTFS exactly as the threat model describes
  it. RW4 records this risk as *"Mitigated — §7.4"*; that row is wrong. There
  is no test, and the spec's Security Test Matrix names the case as a release
  blocker in two rows.

§6.9's table of surviving path re-resolutions is **not complete**. Its eight
rows are individually accurate and rows 1, 4, 5, 6, 7 and 8 are genuinely
*closed* (better than the table's own disposition in four cases), but I found
**seven live re-resolution sites the table does not list**, one of which
(F-3, `internal/watch`) is the exact `IsLinkEntry`-fixed-but-follow-through-
unfixed combination P2.7 F4 warned must never ship. Per §6.9's own standing
instruction — *"anything P3.13 finds that is not here is a defect in this
document"* — that is F-8, an ADR defect.

Nothing I found lets any operation escape the store root, cross more than one
watch boundary, follow an untrusted link, or overwrite a claimed name.

### Handle lifetime

I audited every `int`-returning helper's callers for close-on-success and
close-on-every-error. **No leak found.** Specifically: `ResolvePath`'s per-
iteration `parent`/`fd` pair closes on all four exits; `List`/`Watches`'
recursive `walk` transfers ownership with `ownFD`/`defer closeFD`;
`Publish` rolls back with `rmdirAt` when the post-claim `openDirAt` fails;
`openStrictAt` closes on both the tag-read error and the refusal;
`openRootedFS` (Windows) closes on all five error exits; `openAnnotationFS`
closes `storeRoot`/`lock` on each subsequent failure;
`openAbsoluteDirNoFollow{,Win}` closes the previous level before returning an
error; `annotationLock.Close` unlocks then closes in that order on every path.
`atomicWriteFileAt`'s `done` switch is correct — the deferred
`deleteByHandlePosix` fires on every path except a successful replace, which is
the only moment at which the handle names the destination.

## The ten invariants

| # | Invariant | Holds? | Mechanism |
|---|---|---|---|
| **1** | Filesystem is the sole source of truth | **Holds** | No IPC, no database, no server-side index. The three process-level maps are not sources of truth: `rootIdentityCache`/`lockIdentityCache` (`storefs_windows.go:63`, `annotationfs_windows.go:127`) are *detectors* that only ever produce a loud refusal, and `ignoreCache` (`ignore.go:300`) is revalidated by mtime+size under a 1s TTL (`ignoreSet.fresh`). |
| **2** | Publish and watch atomically claim a new name and never overwrite | **Holds** | `mkdirClaim` = `unix.Mkdirat` / `NtCreateFile(FILE_CREATE\|FILE_DIRECTORY_FILE, OBJ_DONT_REPARSE)`; collisions surface as `errExists` via `unix.EEXIST` or `translateClaim`'s three-way map (`STATUS_OBJECT_NAME_COLLISION` **and** `STATUS_REPARSE_POINT_ENCOUNTERED`/`STATUS_IO_REPARSE_TAG_NOT_HANDLED` → `errExistsReparse`, which wraps `errExists` — the `M8.claim_error_map` fix). Per-file writes are `O_CREAT\|O_EXCL\|O_NOFOLLOW` / `FILE_CREATE\|FILE_NON_DIRECTORY_FILE`. `symlinkAt` claims through `mkdirClaim` before applying the tag. The only relaxation is same-target idempotence, gated by `readlinkAt` + `sameWatchTarget` (byte-exact on Linux, `FILE_ID_INFO` on Windows). `TestPublishConcurrentClaimExactlyOneWins` covers the race. |
| **3** | Artifact nesting and visibility rules remain platform-independent | **Nesting holds. Visibility DOES NOT.** | Nesting: `openRealDir(rejectArtifacts=true)` on both platforms over an identical `dirHasHTMLFD` predicate, plus shallowest-wins at read time in `ResolvePath`/`List`/`Watches` — all shared untagged code. Visibility: the *decision function* `Visible` is shared, but its effect is not platform-independent — **F-2** (`path.Match` is case-sensitive while NTFS folds, so `.SSH` is a reachable spelling of a hidden directory on Windows only) — and its *reachability guarantee* is defeated on both platforms by **F-1**. CLAUDE.md's "Hidden means unreachable, not just unlisted" is currently false. |
| **4** | A path operation cannot be redirected outside its approved root by a rename, symlink, junction, mount point or other reparse point during the operation | **Holds** | The root is pinned by handle (`unix.Open(…O_DIRECTORY\|O_NOFOLLOW)` / `CreateFile(…FILE_FLAG_OPEN_REPARSE_POINT)` + tag refusal + `isDir` + `FILE_ID_INFO` + `checkRootIdentity`). Every mutation walk is `openRealDir`, one strict open per segment. Every mutation primitive takes `(pinnedParent, singleName)` and the single-component restriction is a **runtime check**, not a comment (`ntOpenAt:113`, `statAt` on Linux `:124`). ADR §2.1 consequence 4 — "no path is ever re-resolved inside a mutation" — is true as traced above. |
| **5** | Browsing may cross exactly one store-owned watch link and must reject nested links in the watched source | **Holds for everything that serves content** | `openBrowsableDir`'s `crossed` flag + `crossWatchBoundary` + the handle-by-handle target walk from `/`/`C:\`. `List`/`Watches` use `crossedLink` with the identical mechanism. Post-crossing components are refused for **any** tag with no allowlist consulted. Caveat: `internal/watch` implements its own, path-based crossing (**F-3**) — it honours the one-crossing rule but not the no-follow-ancestors rule. It serves no content; the exposure is fsnotify registrations. |
| **6** | Delete and annotation operations never traverse an untrusted link | **Holds** | `Delete`/`Unwatch` reach their parent only through `openRealDir`, which refuses any reparse point at any ancestor. `removeTreeAt` is operation-as-classification on both platforms: `openRealDirAt`/`openDirAt` first, failure *is* the classification, leaf removal via `deleteEntryAt`/`Unlinkat(…,0)` which removes the entry and never a target. Verified by `TestRemoveTreeAtSwapMidWalkAndNegativeControl` — which includes `removeTreeAtByAttributeUnsafeForTest`, a negative control that provably destroys the external tree, so the assertion has teeth. `.annotations` is opened strict from the pinned root; every `annotationFS.openDir` segment is strict. |
| **7** | Unwatch removes only the store link and never modifies its target | **Holds** | There is no code path from `Unwatch` to any tree walk. `isLinkAt` must report an allow-listed tag; `unlinkAt` opens the entry with `FILE_OPEN_REPARSE_POINT` (the link, not the target) and POSIX-disposes it, or `unix.Unlinkat(…,0)` on Linux, which cannot remove a directory. Caveat **F-6**: `unlinkAt`'s hard-coded `FILE_DIRECTORY_FILE` means a *file*-shaped link is not removable on Windows — fail-closed, but a divergence from ADR §4.6's "flavour chosen from the tag". |
| **8** | Annotation writes remain revision-guarded and atomically replace the prior file | **Holds** | `saveNotesRaw` (`annotations.go:348`) compares `cur.Rev != expectRev` → `ErrRevMismatch`, under `lockDocument` (a per-document lock file) inside the shared rendezvous. ## Findings

### F-1 — HIGH (release blocker, cross-platform, pre-existing). A `*.html` file in the store root disables every visibility rule for path lookup

`visibleSegments` (`store.go:178`):

```go
dir := root
for _, s := range segs {
    if err := validateSegment(s); err != nil { return false }
    if hasHTML(dir) { return true }      // <-- dir == root on the first iteration
    full := filepath.Join(dir, s)
    fi, err := os.Stat(full)
    if !Visible(dir, s, err == nil && fi.IsDir()) { return false }
    dir = full
}
```

The "we are inside an artifact, the rest is assets" short-circuit is evaluated
with `dir == root` before the first segment is checked. The store root is never
treated as an artifact anywhere else — `List`, `ResolvePath`, `Watches` all
start their artifact test one level down — so this is the rule firing where it
has no meaning. When it fires, `visibleSegments` returns `true` unconditionally,
which takes out:

- the hard-coded `.annotations` / `.scratchpad-lock` reserved-name deny
  (`ignore.go:385`) — the one rule the ADR §7.4 and `CLAUDE.md` both single out
  as *not* overridable;
- every `defaultIgnores` entry, including `.ssh/`, `.gnupg/`, `.aws/`, `.env`,
  `.netrc`, `*.pem`;
- every `.scratchpadignore` rule in the store.

`VisiblePath`, `ResolvePath`, `ResolveDoc`, `ResolveFolder` and `OpenDocument`
all gate on this function, so it is the *only* thing making a hidden path
unreachable rather than merely unlisted.

**Reproduced end to end** against a real `scratchpad-web` on loopback (full
transcript in the appendix). With `index.html` present in the store root:

```
/p/.annotations                 404 -> 200
/a/.git/secret.md               404 -> 200   body: SECRET-IN-GIT
/a/node_modules/pkg/readme.md   404 -> 200   body: SECRET-IN-NM
/a/.venv/site/key.pem           ---- -> 200   body: PRIVATE-KEY-BYTES
DELETE /a/.git/hooks            ---- -> 200   .git/hooks recursively removed
```

Read exposure is bounded to `.md`, `.html` and assets inside an artifact
directory (a bare `.env` at the root is still not served, because
`ResolvePath` needs an html-bearing directory and `ResolveDoc` requires `.md`) —
but "assets inside an artifact" covers arbitrary file types, which is how
`key.pem` came back. The `DELETE` reaches `store.Delete`, which is
containment-correct; it simply should never have been offered a hidden target.

Listing is unaffected (`List`, `folderExtras`, `siblingItems` call `Visible`
directly), so this is invisible in the UI — the URLs just work.

Not a Windows regression: `visibleSegments`/`hasHTML` are shared untagged code
and behave identically on both platforms. It violates spec invariant 3 and
`CLAUDE.md`'s "Hidden means unreachable, not just unlisted".

**Remediation direction** (not applied — this review writes no Go): the
`hasHTML(dir)` test belongs after the current segment's `Visible` check, or must
be skipped while `dir == root`. Either is one line, and both need a regression
test at the store layer (`VisiblePath`) *and* the web layer (a 404 for
`/a/.git/x.md` with a root-level `index.html` present), because the store-layer
test alone would not have caught the `DELETE`.

**Owner:** unassigned — needs a new task. Nearest existing owners are P4.6 (web
affordances) and P6.6 (release matrix). It must not ship.

### F-2 — HIGH (release blocker, Windows-only). ADR §7.4's `matchName` platform pair was never implemented; RR5's credential-ignore half is live

ADR §7.4 requires two platform pairs. The first landed: `nameEquals`
(`storefs_linux.go:50` / `storefs_windows.go:183`) is `==` on Linux and
`strings.EqualFold` on Windows, and `ignore.go:385` uses it for both reserved
names. `TestVisibleHidesLockFileName` covers it. **RR5's `.annotations` half is
genuinely closed on Windows and correctly left byte-exact on Linux**, where
`.Annotations` is a different directory and treating it as content is right.

The second did not land. §7.4:

> **`defaultIgnores` matching** (`ignore.go:169`) goes through a platform pair,
> `matchName(pattern, name string) (bool, error)`: `path.Match` on Linux,
> `path.Match` over lower-cased operands on Windows.

`ignore.go:169` is still a bare `path.Match(pat[0], segs[0])`. There is no
`matchName` in the tree, no `ignore_windows.go`, and no `ignore_linux.go`.

Consequence on NTFS, in the threat model's own words (§4.10(b) item 2, rated
**High**):

> On NTFS a directory named `.SSH` or a file named `key.PEM` is the same object
> to the filesystem but does not match the rule. For A1 (a watched tree) this is
> a direct exposure of credential-shaped files through an unauthenticated
> server.

`M11` measured that NTFS folds `.ssh`/`.SSH` and `key.pem`/`key.PEM`, and
`internal/winspike/matrix_test.go:253` records the measurement together with
the note that *"the fix and its test are internal/store (ignore.go's …)"*. The
fix is absent. Item 3 of the same section (`.GIT/`, `Node_Modules/` defeating
the **cost** ignores) is live for the same reason, which is RR9's walk/watch
amplification.

Two further consequences worth stating: `!`-override lines are equally
case-sensitive, and `ignoreCache` keys on a path string, so two spellings of one
directory become two cache entries (§4.10(b) item 4).

**RW4's risk-register row currently reads "Mitigated — §7.4". It is not.** Half
of §7.4 shipped.

**Test coverage:** none. `grep` finds no `internal/store` test using `.SSH`,
`key.PEM`, `Node_Modules` or an upper-cased `.ANNOTATIONS`. The spec's Security
Test Matrix names this in two release-blocking rows — *Names / "Unicode and case
collisions"* and *Documents / "case variation"* — and the threat model
pre-specified the exact case as deterministic: *"`.SSH`/`key.PEM` against
`defaultIgnores`. Deterministic."* So spec Acceptance Criterion 5 ("every
security-matrix case has a test, documented exclusion, or accepted ADR") is not
met.

**Owner:** §7.4 names no P-task for this bullet — that is part of how it was
lost. Assign the fix to the same task that owns `nameEquals` (P3.7 landed the
reserved-name half) and the test to **P3.12**, whose matrix it belongs to.

### F-3 — MEDIUM. P2.7 finding F4's forbidden combination shipped in `internal/watch`

P2.7 F4 said, in as many words:

> fixing `IsLinkEntry` to report junctions **without** also fixing
> `entryIsDir`/`entryIsDirFS`'s follow-through `os.Stat` … converts today's
> fail-closed skip into a path-based descent through the junction.

`IsLinkEntry` **was** fixed — on Windows it is now
`Mode()&(os.ModeSymlink|os.ModeIrregular) != 0` (`link_windows.go:274`), which
reports junctions and unknown-tag directories. Both named follow-throughs were
also fixed: `store.go`'s `entryIsDir` was deleted outright in favour of
`classifyEntry`, and `server.go`'s `entryIsDirFS` was replaced by
`store.EntryIsDirAt`. Neither survives.

A third copy of the same pattern was not converted — `internal/watch/watch.go`
`:271-287`:

```go
isLink := store.IsLinkEntry(entry)
isDir  := entry.IsDir()                       // RR1.unknown_tag_isdir: true for a non-surrogate tag
if isLink && !crossedLink {
    if info, err := os.Stat(path); err == nil && info.IsDir() {   // path-based follow-through
        isDir = true
    }
}
if isLink && crossedLink { continue }
if isDir && store.Visible(dir, entry.Name(), true) {
    walk(path, false, crossedLink || isLink)   // descends by PATH
}
```

and the descent itself is path-based throughout: `canonicalDir` is
`filepath.EvalSymlinks` (`:297`), and `openWatchDir` on Windows is a plain
`CreateFile` **without** `FILE_FLAG_OPEN_REPARSE_POINT` (`identity_windows.go`),
so it follows reparse points at every component. `identity_windows.go` states
the choice deliberately — *"desiredDirs walks arbitrary absolute paths … so the
root-anchored primitive does not apply here"* — which is a fair argument for not
reusing `ntOpenAt`, but it is not an argument for classifying by
`DirEntry.IsDir()` plus a following `os.Stat`.

**Bounded exposure, and I want to be precise about it.** `internal/watch` reads
no file contents and serves nothing; `internal/web` reaches content exclusively
through `internal/store`. The consequence of a redirect here is that the watcher
registers fsnotify watches on directories outside the store or the watched
source, spending watch descriptors and emitting "something changed" pings. It
also diverges from Scope C: `store.classifyEntry` refuses to *explore* an
unrecognised tag, and this walk explores it whenever a filter driver services
it. On a machine without the driver the `EvalSymlinks`/open fails and
`skipWalkError` correctly swallows it — which means the *safe* behaviour here
depends on the machine's driver set, precisely the dependency ADR §2.1 exists to
remove.

Rated Medium rather than High because no content crosses, and because
`crossedLink` does bound it to one link per branch.

**Owner:** P4.1/P4.2 shipped this; the ticket needs re-opening. Minimum fix:
classify with a tag-aware, handle-based helper (the store already exports
`EntryIsDirAt`/`StatEntryAt` for exactly this shape), and stop treating
`entry.IsDir()` as authoritative. §6.9 should gain the row either way (F-8).

### F-4 — LOW. ADR §6.6 rule 1's second bullet is not implemented: the post-claim reopen failure still wedges a name

§6.6 rule 1 requires the two-step link creation to self-heal at **both**
failure points and calls the second one out explicitly:

> **Neither cleans up when the post-claim *reopen* fails**, only when the FSCTL
> does. Both failure points leave the same wedged empty directory.

`link_windows.go:91`:

```go
if err := mkdirClaim(parent, name); err != nil { return err }
h, err := ntOpenAt(parent, name, …|windows.DELETE, FILE_OPEN,
        FILE_DIRECTORY_FILE|FILE_OPEN_REPARSE_POINT, OBJ_CASE_INSENSITIVE, 0)
if err != nil {
    return translateOpen("open new link", err)   // the claimed directory is left behind
}
```

The FSCTL half **is** done, for both flavours, through the already-held handle
(`deleteByHandlePosix(h)` at `:112`), and the reopen does now request `DELETE`
access — which is what `2c97384`'s commit message verifies. The reopen-*failure*
branch is a separate clause and is still uncovered. It is reachable (a sharing
violation from an antivirus or indexer on the just-created directory is the
realistic trigger; an ACL denial is the other).

Impact is a usability trap, not containment: an empty directory consumes a name
that create-only semantics never release. Rule 3 — which **did** land in
`2c97384`, both the distinct `Watch` collision message and `Delete`'s `rmdirAt`
recovery — makes it user-recoverable, so this is Low rather than Medium.

Rule 2 (the `FILE_DELETE_ON_CLOSE` crash interlock) is also absent, but the ADR
pre-authorises that: *"If it does not hold, rule 3 alone carries the case."*
Rule 3 carries it. No finding.

**Owner:** P4.3.

### F-5 — LOW. `Delete` refuses an unrecognised reparse tag where ADR §4.5 and §5.1 say it unlinks it

ADR §4.5: *"**Any other reparse tag** → `unlinkAt` as well, never a descent."*
§5.1 Scope C: *"every other tag … unlinked by `Delete`."*

The code does neither. `isLinkAt` reports `false` for a non-allowlisted tag
(`classifyHandle` sets `IsLink` only for `isWatchTag`), so control reaches the
artifact branch, where `openDirAt` is the **strict** open and fails with a
`reparseRefusal`, and `Delete` returns `"artifact %s not found"`.

This is fail-closed and it is **deliberate**:
`TestUnknownTagEntryIsInvisibleAndInert` asserts exactly this outcome and cites
RW15/P4.6 as the intended escape hatch. So the code is right and the ADR is
stale. Recorded so the next reader does not "fix" the code to match the
document. Consequence: an unrecognised-tag entry in the store root is currently
un-removable through any CLI or HTTP verb.

**Owner:** ADR amendment (§4.5 bullet 2, §5.1 Scope C) + P4.6's RW15 affordance.

### F-6 — LOW. `unlinkAt`/`rmdirAt` hard-code `FILE_DIRECTORY_FILE`, so a file-shaped link is un-removable on Windows

ADR §4.6: *"Removal flavour is chosen from the tag, not guessed: the entry is
opened `FILE_OPEN_REPARSE_POINT` with `FILE_DIRECTORY_FILE` for `MOUNT_POINT`
and for a directory `SYMLINK`, `FILE_NON_DIRECTORY_FILE` for a file `SYMLINK`."*

`link_windows.go:192` passes `FILE_OPEN_REPARSE_POINT|FILE_DIRECTORY_FILE`
unconditionally, as does `rmdirAt` (`storefs_windows.go:308`). A file-shaped
`SYMLINK` in the store therefore opens with `STATUS_NOT_A_DIRECTORY`:
`Delete` classifies it as a link (the tag is allow-listed), calls `unlinkAt`,
and gets `errNotDir`; `Unwatch` fails identically. Linux's
`unix.Unlinkat(parent, name, 0)` removes it fine, so this is a platform
divergence as well as an ADR divergence.

Fail-closed, and the store never creates a file link, so this is only reachable
for an entry the user or another process planted. `deleteEntryAt`
(`annotationfs_windows.go:639`) is the correctly-unconstrained primitive and is
what `removeTreeAt`'s leaf case uses — the shape to copy.

**Owner:** P4.3 (mechanism) / P4.6 (the RW15 affordance that would expose it).

### F-7 — LOW. `verifyRoot` and `statLinkTarget` have zero call sites, while the ADR's prose says `verifyRoot()` runs before every mutation

ADR §4.4, §4.5 and §4.7 each list `verifyRoot()` as a step in the operation
sequence, and §4.9's R13 row says *"pre-mutation root identity
re-verification … yes"*. `verifyRoot` (`storefs_windows.go:192`) is never
called. `statLinkTarget` (both platforms) is likewise never called.

The *property* is delivered: `checkRootIdentity` runs inside `openRootedFS` on
every operation and is the cross-operation detector §4.1 designed to replace
what the R12 override removed. §4.1 already concedes `verifyRoot()` alone
"cannot do the one thing revision 1 credited it with". So this is not a missing
control — it is dead code that reads like a live one, on the highest-severity
operation in the design, which is how a future reader concludes a check runs
when it does not.

**Owner:** either delete both functions or call `verifyRoot` where §4.4/§4.5/§4.7
say it is called and amend the prose; ADR §4.9's R13 row should say the cache is
the whole mechanism.

### F-10 — INFO. `WatchLinkFor` validates nothing about its own input

`WatchLinkFor(rel)` (`store.go:874`) splits `rel` on `/` and feeds each segment
straight to `classifyEntry`→`statAt`→`ntOpenAt`. `ntOpenAt` rejects `/` and `\`
but not `:`, so `checkLookupSegmentPlatform`'s ADS refusal does not apply here.
Every current caller (`annotate`, `artifactUnwatch`, `Unwatch`'s error branches)
passes an already-validated `RelPath()`, so there is no live bypass — but it is
an exported function with no prologue of its own, and it is the one lookup path
in the store that does not run `validateSegment`.

On the wider question the task asked: I found **no** lookup path that reaches a
handle open without `validateSegment` first, other than this one.
`visibleSegments`, `ResolveFolder`, `existingDir`, `OpenDocument`, `notesPath`,
`WalkNotes` and `removeNotesFor` all run it. The Linux side of the
`checkLookupSegmentPlatform` split is correct: `:`, trailing dots/spaces and
DOS device basenames are ordinary legal Linux filename content that a watched
repository is entitled to use, and refusing them at *lookup* would make existing
watched files unreachable — while `checkPortableName` still applies at *create*
time on both platforms, which is the asymmetry the spec asked for.

## What I could not verify

Stated plainly, because a review that does not say this is worth less.

1. **Everything Windows-specific is code reading, not measurement.** I have no
   Windows host. `GOOS=windows go vet ./...` passes and CI run `32962872576` is
   green, but every Windows claim in this document — the strict open's tag
   refusal, `translateClaim`'s status map, `LockFileEx` semantics across two
   handles in one process, F-6's `STATUS_NOT_A_DIRECTORY` prediction, F-2's
   `.SSH` exposure — is reasoned from the source and the spike's measurements,
   not observed. F-2 in particular deserves a live NTFS confirmation before it
   is fixed, so the fix is verified against `$UpCase` and not against
   `strings.ToLower`.
2. **F-1 is verified on Linux only.** The mechanism is shared untagged code, so
   it must behave identically on Windows, but I did not run it there.
3. **The rendezvous residual remains open and unmeasurable here.** ADR §6.7
   states it exactly: if `<root>\.scratchpad-lock` is deleted and recreated
   between two *processes'* `openAnnotationFS` calls, both pin different objects
   and mutual exclusion is lost silently. `lockIdentityCache` is an in-process
   detector only and says so. `TestDeleteRacingSaveNotesNeverLeavesOrphanedNotes`
   (shared, so it runs on both platforms) does cover the **normal** case, and it
   is a genuine contention test rather than a scheduling coincidence — it holds
   the exclusive lock across a real sleep. So **`Delete` racing `SaveNotes` is
   closed for the ordering hazard**, which is what RR6 was about; the *swap*
   hazard is not, and P1.7 F5's "parity with Linux is FALSE" verdict still
   stands and is correctly recorded rather than argued away. I could not test
   the cross-process swap without Windows.
4. **The `LOCKFILE_FAIL_IMMEDIATELY` + bounded-retry rendezvous is an
   availability divergence I could not exercise.** Linux `flock` blocks; Windows
   gives up after 10 attempts / ~766 ms and returns an error. Under sustained
   reader contention a Windows `Delete`/`Unwatch` can fail where Linux would
   wait. Documented in the code, not measured under load. P6.1's stress campaign
   is the place.
5. **The drive-letter device-map question** (§4.3's named residual — whether an
   unprivileged same-user process can rebind an existing letter via
   `DefineDosDevice`) is still `[UNMEASURED]`; it is the anchor
   `openVolumeRootNoFollow` depends on.
6. **ReFS/Dev Drive, SMB, FAT32, OneDrive placeholders and antivirus
   distribution** remain the documented `MATRIX.EXCLUDED` set. The exclusions
   are recorded in code next to the tests they are not a substitute for, which
   is the right handling; P6.6 still owes the manual pass.
7. **I did not audit `internal/web`'s templates or the viewer's JS.** The
   sandbox/trust split (`allow-scripts` without `allow-same-origin` for card
   previews; same-origin for the viewer overlay) was out of the traced scope.
