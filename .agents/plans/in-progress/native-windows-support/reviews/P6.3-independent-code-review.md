# P6.3 Independent Code Review

## Verdict

**PASS WITH FINDINGS.**

One Medium, three Low, four Informational. Nothing I found is a containment
escape, and nothing blocks the beta on its own. The Medium is a
confidentiality/visibility bypass that the threat model predicted in §4.7(b)
and that a later audit checked only half of.

The mechanism layer holds up under a second, independent pass. I re-derived,
rather than accepted, the four claims that carry the most weight:

- **No handle leak.** I enumerated all 30 handle-acquisition sites in the five
  Windows production files plus `internal/watch` (`ntOpenAt` ×12,
  `windows.CreateFile` ×4, `dupHandle` ×2, `os.NewFile` ×8, and their callers)
  and traced every early return, `break`, `defer` and recursive call. Every
  acquisition is released on the success path and on every error path. Two
  transfer-of-ownership sites are correct and easy to get wrong:
  `openAnnotationFS` takes `rfs.root` without calling `rfs.close()`
  (`annotationfs_windows.go:53`) — correct, the other `rootedFS` fields are
  plain values — and `atomicWriteFileAt`'s `done` switch closes exactly once in
  both directions. `readDirFD` is the only site that checks `os.NewFile` for
  nil and closes on that path; the others cannot receive an invalid handle.
- **The six `FILE_OPEN_REPARSE_POINT` additions are complete and none changed a
  caller's control flow.** I grepped every create disposition in the package
  (`FILE_CREATE` ×3, `FILE_OPEN_IF` ×2, `FILE_OPEN` ×7) and confirmed all
  twelve now carry the flag, with no disposition missed and none added where it
  would be wrong. The side-effect question is real — an existing reparse point
  at a `FILE_CREATE` name now yields `STATUS_OBJECT_NAME_COLLISION` →
  `errExists` instead of a reparse status → `errExistsReparse` — but every
  consumer branches on `errors.Is(err, errExists)`, and `errExistsReparse`
  wraps `errExists` (`win32_windows.go:538`), so both statuses take the same
  branch in `Publish` (`store.go:769`), `Watch` (`store.go:868`),
  `openRealDir` (`storefs_windows.go:366`), `mkdirsAt` (`:713`) and
  `annotationFS.openDir` (`annotationfs_windows.go:304`). Watch's idempotence
  is unaffected. One site is *improved* by the change:
  `atomicWriteFileAt`'s temp-name retry loop keys on `isNameCollision`
  (`annotationfs_windows.go:557`), which the new status satisfies and the old
  one did not. Three doc comments are now wrong about it — F4.
- **`unsafe` and the ABI are sound on amd64 and arm64.** `attrTagInfo` = 8 B,
  `fileIDInfoRaw` = 24 B (u64 + [16]byte, align 8), `reparseHeader` = 8 B,
  `identity_windows.go`'s `fileIDInfo` = 24 B — identical on both arches, all
  four now carrying `structs.HostLayout`. The hand-rolled `FILE_RENAME_INFO`
  buffer's offsets (0/8/16/20) are right for a 64-bit `HANDLE`, and writing the
  class-10 `BOOLEAN ReplaceIfExists` as a 4-byte LE store is safe because bytes
  1–7 are padding. Both reparse encoders' layouts check out arithmetically
  (MOUNT_POINT fixed=8, path at 16; SYMLINK fixed=12, Flags at 16, path at 20;
  `ReparseDataLength` excludes the 8-byte header in both). `readLinkHandle`
  bounds every read against the FSCTL's *returned* byte count `n`, not the
  self-describing `ReparseDataLength` — the safe choice. `GOARCH=386` still
  fails the build on `win32_windows.go:45`, verified.
- **Error translation does not turn a refusal into a silent success.** Only
  four statuses reach `fs.ErrNotExist` (`STATUS_OBJECT_NAME_NOT_FOUND`,
  `STATUS_OBJECT_PATH_NOT_FOUND`, `ERROR_FILE_NOT_FOUND`,
  `ERROR_PATH_NOT_FOUND`), all genuine. Nothing permission- or reparse-shaped
  reaches it. The three predicates that act on `fs.ErrNotExist` all fail closed
  when a status is *not* mapped: the create-if-missing branches simply do not
  create, and `removeTreeAt`'s `return nil` is backstopped by the parent's own
  `rmdirAt` failing loudly on a non-empty directory.

`internal/store` and `internal/web` are **byte-identical** between `2d51cb3`
(where I began) and `de172f1` (HEAD) — verified with
`git diff --stat 2d51cb3..HEAD -- internal/store internal/web`, which is empty.

`internal/watch` and `cmd/scratchpad` moved three times while I read:
`185b37d`, `afc3a66`, `de172f1`. I re-read `internal/watch` at HEAD. Two
consequences for this review:

- **P4.7's P-5 is now fixed** (`afc3a66`), and it was worse than its own text
  said. Real Windows CI showed `filepath.EvalSymlinks` failing on any path
  *past* a junction component, so `desiredDirs` silently dropped everything
  nested inside a junction watch link. Because `symlinkAt` falls back to a
  junction whenever a directory symlink fails, and a junction is the **only**
  flavour a Developer-Mode-off user can create (`errNoLinkPrivilege`'s own

  link for the entire default-configuration Windows population. It is fixed by
  a handle-based `canonicalDir` platform pair. I am not re-reporting it, but it
  deserves to be on the record as the most severe *functional* defect this
  branch has had, and it was found only by running on real Windows.
- The fix introduces **F2**, below.

### F5, as actually implemented

I recommended "a ceiling around 10 000". That would have reintroduced M2 for
anything the store creates above it, so the shipped fix is P3.14's *first*
suggestion instead, which nobody had taken: **one constant bounds both halves**.
`maxArtifactTreeDepth` = 2048 bounds what `ValidateFilePath` will create and how
deep `removeTreeAt` will descend, so "the store never creates a tree it then
refuses to delete" is true by construction and checkable in one place rather
than emergent from two limits nobody compared.

2048 is derived rather than round: it is exactly Linux's path-nameability
ceiling (`PATH_MAX` 4096 / 2 bytes per minimal level), ~16× past Windows'
legacy `MAX_PATH` ceiling where Explorer and `rmdir /s` stop, ~20× the deepest
real tree anyone has, and — against the two ceilings §3.4 measured — 1500× under
the goroutine-stack cost and 256× under this host's `RLIMIT_NOFILE`.

The residual is stated in the constant's own comment rather than buried: a tree
deeper than this that arrived some *other* way (an external `cp -r`) is now
refused by `Delete`, where the unbounded version would have removed it. That is
a real capability regression and it is deliberately not M2 — M2 was the store
refusing to delete what the store itself created, at a depth one `publish` call
could reach. `errTreeTooDeep` names the tool that can remove it.

`walkAnnotationDir` is bounded in the same change. It had **no** bound at all on
either platform (P3.13 F-11, P6.2's R16 row) and is the identical unrecoverable
stack class, reached from `WalkNotes`' report rendering rather than from a
delete. It degrades like `List`/`sizeWalkAt` (stop walking) rather than
erroring, because under-reporting a note is recoverable and leaving content
behind is not.

### FD-3, decided per function

- **`rootedFS.verifyRoot`** — deleted. Wiring it would have been *actively
  wrong*, not merely redundant: ADR §4.1 says of a root replaced mid-operation
  that "an operation that began against a live root, holding a descriptor to
  it, completes against that object — that is F-b, not a defect", so the only
  thing the check could ever have done is fail an operation the ADR calls
  correct. R13's real mechanism, `checkRootIdentity`, is wired and tested.
- **`statLinkTarget`** — deleted on both platforms. A strictly weaker duplicate
  of `classifyEntry`, and its Linux doc comment claimed `classifyEntry` was
  "the only caller", which was false.
- **`StatEntryAt`** — deleted. Added speculatively for P4.6, which landed using
  its two siblings and never needed it; the same shape as the dead
  `serveMarkdown` that P3.14's L6 removed.

**Still open, for the ADR-accuracy task, not edited here:** the ADR lists all
three of those functions — §3.2's backend API table (`verifyRoot`,
`statLinkTarget`), §6.8 item 5 (`StatEntryAt`) — and §4.1 plus the §6 mutation
flows still say `verifyRoot` runs "before every mutation", which was never true
of the shipped code.

## Findings

### F1 — an 8.3 short-name alias defeats `Visible`'s `.annotations` reserved-name guard and every `defaultIgnores` rule, for any requester-supplied path segment. *(Medium — confidentiality; confirmed by reading, Windows half unexecuted)*

`internal/store/ignore.go:390` (the guard) — `internal/store/store.go:196-213`
(`visibleSegments`, the second producer) — `internal/store/names_windows.go:41`
(`checkLookupSegmentPlatform`, where the cheap fix belongs).

```go
// ignore.go:390 — the ONE enforcement point for both reserved names
if rel == "." && (nameEquals(name, AnnotationsDir) || nameEquals(name, lockFileName)) {
    return false
}
```

`nameEquals` is `strings.EqualFold` on Windows (`storefs_windows.go:183`), so
the **case**-folding half of this is closed (ADR §7.4, RW4). The **spelling**
half is not. NTFS stores an 8.3 alias alongside the long name whenever
generation is enabled — which spike `M6.enabled` measured as **on** for the
runner's `C:` volume, and which is the Windows default for the system volume,
where `~\.scratchpad` lives. `.annotations` is not a valid 8.3 name, so it gets
an alias (`ANNOTA~1`-shaped). `NtCreateFile` resolves that alias exactly like
the long name, including through an `OBJECT_ATTRIBUTES.RootDirectory`-relative
open.

Trace for `GET /p/ANNOTA~1`:

1. `VisiblePath` → `visibleSegments(root, ["ANNOTA~1"])` (`store.go:196`).
2. `validateSegment` passes: `checkLookupSegmentPlatform` refuses `:`, a
   trailing dot/space and reserved device basenames — not `~`.
3. `Visible(root, "ANNOTA~1", true)`: `rel == "."`, but
   `EqualFold("ANNOTA~1", ".annotations")` is false, so the reserved-name deny
   does not fire; no `defaultIgnores` rule matches either. Visible.
4. `ResolveFolder` → `openBrowsableDir(["ANNOTA~1"])` →
   `openRealDirAt(rootFD, "ANNOTA~1")` → the kernel resolves the alias and the
   annotations tree is browsable.

**Why P6.2 did not catch it.** P6.2 §1.2 examined this exact line and concluded
it is "not defeatable by spelling: I traced all eight call sites and every one
passes a `dir` built by `filepath.Join(Root(), …)` from the *same* `Root()`
string the `Rel` is taken against … The 8.3-alias and case hazards of threat
model §4.7 require the two operands to be spelled differently by different
producers; here they have one producer." That is correct **for the `dir`
operand and the `Rel` it feeds**. It does not cover the **`name` operand**,
which is the one the reserved-name comparison actually uses, and which *does*
have two producers: `os.DirEntry.Name()` from `List`/`Watches`/`desiredDirs`
(always the long name — those paths are safe) and a **requester-supplied URL
segment** from `visibleSegments`. P6.2's own stated precondition for the hazard
is met on the operand it did not check. Threat model §4.7(b) named `Visible`
explicitly; ADR §7.4 mitigated only the case half and states plainly that the
sound test "is **not implementable at `Visible`'s call site**" — which is true,
and is exactly why the check needs a second, post-open enforcement point rather
than a better string comparison.

**What a user or attacker experiences.** On a `LAN=1` (unauthenticated)
instance: the `.annotations` tree becomes browsable, disclosing every annotated
document path in the store; the `.scratchpad-lock` name likewise; and inside a
watched project tree, `defaultIgnores`' cost and credential entries
(`node_modules/`, `.git/`, `.ssh/`, `.aws/`, `.gnupg/`, `.env`) can be walked
by alias. I want the impact bounded honestly: this is **listing** disclosure,
not content. `/a/{path…}` serves a file only when `ResolvePath` finds an
ancestor directory holding an `.html` (`store.go:665-691`), and neither
`.annotations` nor a credential directory has one — note sidecars are
`<doc>.html.json`, which `dirHasHTMLFD`'s `HasSuffix(…, ".html")` correctly
does not match. `Delete` and `Unwatch` on an aliased path fail closed
(`rmdirAt` refuses a non-empty directory). The watcher is unaffected, since it
only ever sees `ReadDir` names.

**Fix**, in preference order:

1. Enforce the reserved names where a handle exists, not only where a string
   does: after `openBrowsableDir` opens a top-level child, compare
   `objectIDOf(childFD)` against the `.annotations` directory's own
   `objectID`. This is the test ADR §7.4 says is correct and calls
   unimplementable *at `Visible`* — it is implementable one layer down, and it
   closes case, 8.3 and any future aliasing at once.
2. Cheap and in keeping with existing precedent: have
   `checkLookupSegmentPlatform` (`names_windows.go:41`) refuse the 8.3 alias
   shape — `^[^.]{1,6}~[1-9][0-9]*(\.[^.]{1,3})?$`, case-insensitive — for the
   same stated reason it already refuses `:`: "the underlying Win32/NT open
   primitives interpret them dangerously rather than simply failing to find
   them". Cost: an entry a watched repo literally named `FOO~1.TXT` becomes
   unaddressable. Note this does *not* fix the ignore-rule half for a
   deliberately short-named directory.
3. If neither lands, record it as an accepted residual in the threat model's
   RR table alongside RR12, and say so in `docs/windows.md`. It is currently
   recorded nowhere.

### F2 — `internal/watch`'s duplicated `finalPathDOS` dropped the validator that makes the original safe; a UNC result becomes a malformed watch path and a fatal watcher failure. *(Low — availability; reasoned, not executed)*

`internal/watch/identity_windows.go:147-161` and its caller `:114-140`, against
the original at `internal/store/win32_windows.go:496-509`.

Both copies end identically:

```go
return strings.TrimPrefix(windows.UTF16ToString(buf), `\\?\`), nil
```

`GetFinalPathNameByHandleW(VOLUME_NAME_DOS)` returns `\\?\UNC\server\share\…`
for a path on a mapped network drive or a UNC share. Trimming only `\\?\`
leaves `UNC\server\share\…` — not a path at all.

In `internal/store` that is harmless because the single caller,
`canonicalizeWatchTarget`, immediately runs the result through
`validateAbsoluteWindowsPath` (`storefs_windows.go:564-566`), which refuses
anything without an `X:\` prefix, so `Watch` fails closed with an actionable
message. The package also has `stripNTPrefix` (`link_windows.go:195-200`),
which handles the `UNC\` form correctly — for reparse buffers.

The new `internal/watch` copy has **neither**. Its output goes straight into
`dirs[canonical]` and then into `w.backend.Add(...)` (`watch.go:216`), whose
failure `reconcile` returns as a hard error — which `newWatcher` treats as
fatal at startup and `Run` treats as fatal at runtime. So a `SCRATCHPAD_ROOT`
on a mapped network drive, which `openRootedFS`'s `validateAbsoluteWindowsPath`
*accepts* (`Z:\…` is drive-letter-rooted), makes `scratchpad-web` refuse to
start with a confusing "add watch" error. Before `afc3a66` the old
`EvalSymlinks`-based `canonicalDir` returned `Z:\store` and this worked.
`docs/windows.md:13` says local NTFS only, so this is a documented-unsupported
configuration — but turning it from "works" into "server will not boot" is a
regression, and the failure names the wrong thing.

**Fix.** Give the watcher's copy the same two lines the original's caller has:
handle the `\\?\UNC\` form the way `stripNTPrefix` does, and if the result is
not drive-letter-rooted return an error that `skipWalkError` recognises (so the
entry is *skipped and logged*, not fatal). Or export the store's
`finalPathDOS` + `stripNTPrefix` pair rather than duplicating a helper minus
its guard — the duplication rationale in the doc comment is reasonable for the
15 lines of mechanism, but it silently dropped the part that made those 15
lines correct.

I could not execute this: it needs a Windows host with a mapped drive. The
code-level defect — a duplicated helper with the caller-side guard omitted —
does not depend on which spelling the API returns.

### F3 — Windows `unlinkAt` refuses a file-shaped watch tag; Linux's does not. A file symlink in the store is undeletable through the tool on Windows only. *(Low — reasoned)*

`internal/store/link_windows.go:207-215` vs `internal/store/link_linux.go:41-43`.

```go
// windows
h, err := ntOpenAt(..., windows.FILE_OPEN,
    windows.FILE_OPEN_REPARSE_POINT|windows.FILE_DIRECTORY_FILE, ...)
// linux
return unix.Unlinkat(parent, name, 0)
```

`classifyHandle` (`storefs_windows.go:634`) sets `IsLink` for **any**
allow-listed tag, including `IO_REPARSE_TAG_SYMLINK` on a non-directory. Both
`Delete` (`store.go:1114-1118`) and `Unwatch` (`store.go:1072`) route an
`IsLink` entry to `unlinkAt`, which then fails with `STATUS_NOT_A_DIRECTORY` →
`errNotDir`. The entry cannot be removed by either verb; `Watches` also skips
it (`store.go:998`, `linkTargetIsDir`), so the UI never offers unwatch either.
The store never creates such a link, so this needs a user or an external tool
to plant one — low reachability, but the Linux twin handles it and the Windows
one does not, which is the kind of asymmetry this port is otherwise careful
about. `deleteEntryAt` (`annotationfs_windows.go:658`), which constrains
neither file-vs-directory flag, is the shape that is already right.

**Fix.** Drop `FILE_DIRECTORY_FILE` from `unlinkAt`'s options, matching
`deleteEntryAt`. `FILE_OPEN_REPARSE_POINT` is what provides the no-follow
guarantee; the directory constraint adds nothing to it.

### F4 — three doc comments now misdescribe what the `FILE_OPEN_REPARSE_POINT` additions do. *(Low — audit-surface accuracy; confirmed by reading)*

`annotationfs_windows.go:252-255`, `annotationfs_windows.go:158-165`,
`storefs_windows.go:731-742`.

`openLockFileAt`'s comment claims the flag combination "refuse[s] a reparse
point or a directory at this name **outright** rather than transparently
opening through it". Half right. `FILE_NON_DIRECTORY_FILE` does refuse a
directory-shaped reparse point (`STATUS_FILE_IS_A_DIRECTORY`). But
`FILE_OPEN_IF` + `FILE_OPEN_REPARSE_POINT` on a *file*-shaped reparse point
**opens it as itself** — that is precisely what the flag is for, and what Go's
own `Symlinkat` relies on. The security property the fix was bought for is
intact (the open never lands outside the store), and the outcome is fail-safe
either way (`LockFileEx` on such a handle either works, in which case every
process contends on the same object and the rendezvous still functions, or
fails and `lockFileHandleWithRetry` errors out loudly). But "refused outright"
is not what happens, and `openRendezvousLockFile` carries the same claim.

Separately, `writeFileAt`'s comment says a pre-planted link "is refused,
translated to `errExistsReparse`". Post-fix it is translated to `errExists`
via `STATUS_OBJECT_NAME_COLLISION`. Same refusal, different sentinel.

This matters more than a normal comment nit because `win32_windows.go`'s header
declares the file's whole premise to be "auditable, guarded ABI", and these
comments are the audit record a future reader will check the flags against.

**Fix.** Say what actually happens: "opened as the reparse point itself, never
traversed through" for the `FILE_OPEN_IF` pair, and `errExists` for
`writeFileAt`.

### F5 — `removeTreeAt`'s depth bound was not removed so much as relocated to the fd/handle ceiling, and *at* that ceiling the failure mode differs by platform. *(Informational — measured; see §3 for the full data)*

`annotationfs_windows.go:737-783`, `annotationfs_linux.go:228-268`,
`store.go:354-375`.

M2 is genuinely closed — I deleted a 520 000-level tree cleanly. The residual
is that the recursion holds one descriptor/handle per level, so the store still
has a depth past which it refuses to delete what it created; the bound moved
from 64 to ≈`RLIMIT_NOFILE`, roughly 8 000× further out and past anything
reachable in practice. Details, numbers and the Windows analysis are in §3,
because the coordinator asked for that specifically and it is longer than a
finding entry should be.

### F6 — `STATUS_DELETE_PENDING` aborts an entire tree removal. *(Informational)*

`win32_windows.go:617` maps it to `errDeletePending`, which
`removeTreeAt`'s triage (`annotationfs_windows.go:740-753`) recognises as
neither not-exist, nor a reparse refusal, nor `errNotDir` — so it propagates
and fails the whole `Delete`. A legacy (non-POSIX) delete of one entry by an
external tool, still completing, therefore aborts the removal of an entire
artifact. It is transient and the user can retry, and it is correctly *not* in
`retryableRenameStatuses`' scope. Linux has no equivalent state. Cheap
improvement: treat it like `fs.ErrNotExist` in that one triage, since a
delete-pending entry is on its way out of the namespace by definition.

### F7 — `internal/store` still fails to build on darwin/BSD with four `undefined:` errors. *(Informational — P3.14's structural note, unaddressed)*

Executed: `GOOS=darwin GOARCH=arm64 go build ./...` produces
`annotations.go:112:11: undefined: annotationFS` and nine more. A
`//go:build !linux && !windows` file with a single clear compile error would
save the next contributor ten minutes. Intentional, undeclared.

### F8 — P3.14's L7 is still open. *(Informational)*

`store.go:1144` still collapses every `Delete` failure into `artifact %s not
found`. P3.14 assigned it to P3.13/P4.7 rather than owning it; neither closed
it. `winError` carries the NTSTATUS for exactly this purpose and nothing
surfaces it. Flagging so it does not fall between three reviews.

## Parity notes (not findings)

- **The L1 fix is load-bearing on Windows, not merely defensive.**
  `ntOpenAt`'s new `.`/`..` rejection (`win32_windows.go:145`) sits under
  `openAbsoluteDirNoFollowWin` (`storefs_windows.go:470`), which splits a
  *link-target* string on `\` and feeds each component to the kernel.
  `validateAbsoluteWindowsPath` does not reject `..`, and `readlinkAt`'s target
  comes off an attacker-plantable reparse buffer. P3.14 called this "not
  currently reachable"; post-fix it is moot, but the reachability assessment
  was optimistic. **The Linux twin still has the gap**:
  `openAbsoluteDirNoFollow` (`storefs_linux.go:440`) splits on `/` and calls
  `openDirAt`, and `openat(fd, "..")` succeeds. There is no security
  consequence — a watch link may legitimately point anywhere absolute, so
  walking `..` reaches nothing new — but the two platforms now disagree, and
  the Windows comment explains a rule the Linux side does not follow.
- **`FILE_OPEN_FOR_BACKUP_INTENT` on every `ntOpenAt` is correct, not a
  privilege-escalation smell.** I checked against Go 1.27's own
  `internal/syscall/windows/at_windows.go:153`, which ORs it unconditionally
  into every `Openat`. Same choice, same reason.
- **P3.14's unverified item 4 (wildcards) traced.** `*`, `?`, `"`, `<`, `>`,
  `|` are still accepted by `validateSegment`/`checkLookupSegmentPlatform` and

  closed anyway (`classifyEntry` → `explore == false` → 404), so this is a
  message-quality issue, not a hole. Still unexecuted on Windows.
- **`namespaceRemovalHook`** (`annotationfs_windows.go:689`) is an
  unsynchronised package variable, same shape as the pre-existing
  `testStoreOpHook`. Correct for L5's purpose; noted because the race detector
  will eventually notice if a parallel test ever sets it mid-run.

## 3. `removeTreeAt`: what actually terminates it now — demonstrated

The coordinator asked for execution, not argument. Everything in this section
was run.

### 3.1 The claim under test

Both platforms' doc comments now assert: *"removeTreeAt never follows a link
either … so it carries none of that risk; a real directory tree cannot cycle
… the only bound that mattered — the filesystem's own — still applies."*

Two clauses. The first is a cycle claim. The second names the terminator. I
tested both.

### 3.2 The cycle claim: I could not construct a counterexample, on either platform

- **Windows.** No mechanism exists. NTFS forbids directory hardlinks; every
  mount point is `IO_REPARSE_TAG_MOUNT_POINT`, which `openRealDirAt`'s strict
  open refuses on the tag before any descent. The claim holds by construction.
- **Linux.** The obvious counterexample is a bind mount of an ancestor into a
  descendant, which `O_NOFOLLOW` does not see. I built one:

  ```
  unshare -Ur -m sh -c 'mount --bind …/cyc/a …/cyc/a/sub && ls …/cyc/a/sub/sub/sub/sub'
  → ls: cannot access …: No such file or directory
  ```

  A bind mount is attached to a (parent-mount, dentry) pair, so reaching the
  same dentry through the bind does not re-trigger it: `a/sub/sub` is the
  underlying empty directory, and the recursion terminates. `mount --rbind` of
  an ancestor onto its own descendant is refused by `do_loopback` with
  `-ELOOP`. Directory hardlinks are forbidden here too.

**So the comment's cycle claim survives adversarial attempt on both
platforms.** I am recording the attempt because the claim is load-bearing for
the whole decision and had not previously been tested.

### 3.3 The terminator: measured

A structural replica of `annotationfs_linux.go`'s `removeTreeAt` — same
`openat(O_DIRECTORY|O_NOFOLLOW)`, same `readDirFD` dup-and-rewind, same
`Fstatat`-then-recurse triage — run against trees built handle-relative (so
`PATH_MAX` does not bound the construction, exactly as `mkdirsAt` does not).
Host: `RLIMIT_NOFILE` 524 288 (Go raises the soft limit to the hard limit at
startup), `fs.nr_open` 1 073 741 816.

| depth built | result | tree afterwards |
|---|---|---|
| 1 000 | `err=<nil>` | 0 levels — fully removed |
| 10 000 | `err=<nil>` | 0 levels |
| 100 000 | `err=<nil>` | 0 levels |
| 200 000 | `err=<nil>` | 0 levels |
| 400 000 | `err=<nil>` | 0 levels |
| 520 000 | `err=<nil>` | 0 levels |
| **540 000** (> `RLIMIT_NOFILE`) | **`too many open files`** | **540 000 of 540 000 intact** |

So: **the terminator is the descriptor ceiling, and it fails closed.** The
recursion errors on the way *down*, before any removal, so there is no partial
destruction — I verified the count, not just the error. The process exits
normally (rc 0); nothing crashes.

M2 is therefore closed: a tree 8 000× deeper than the old bound of 64 deletes
cleanly. The residual is that the *shape* of M2 still exists past the ceiling —
the store can create a tree it will then refuse to delete. Two observations
about that residual:

- **It is not reachable through any supported path.** `publish -dir` walks its
  source with `fs.WalkDir`, which is path-based and dies at `PATH_MAX` long
  before; `.annotations` mirrors doc paths, bounded by URL length; a watched
  tree is never removed by the store.
- **A manual remedy exists on Linux and is worse on Windows.** `os.RemoveAll`
  could **not** clear the stuck 540 000-level tree (measured — it is the same
  recursive shape). `rm -rf` **could** (measured, rc 0), because coreutils'
  `fts` walks with `FTS_CWDFD` and holds a bounded number of descriptors. The
  Windows equivalents are path-based: `rmdir /s` and Explorer cannot address a
  tree the store built through `RootDirectory`-relative `NtCreateFile`, which
  never consults `MAX_PATH`. `robocopy /MIR` from an empty directory is the
  only common Windows remedy.

### 3.4 Stack depth: measured, and what happens at the limit

Per-level stack cost, read out of the compiler for the **real** functions:

```
GOOS=linux   GOARCH=amd64  store.removeTreeAt  args=0x18 locals=0x138  (312 B)
GOOS=windows GOARCH=amd64  store.removeTreeAt  args=0x18 locals=0x80   (128 B)
GOOS=windows GOARCH=arm64  store.removeTreeAt  args=0x18 locals=0x88   (136 B)
```

Calibration: my replica reports `locals=0x160` (352 B), and I found its real
per-level cost by capping the stack and bisecting the depth at which it dies —
clean at 11 000, `fatal error: stack overflow` at 12 500, with a 4 194 304-byte
cap. That is **357 B/level measured** against **360 B/level predicted**
(`locals` + 8 for the return address). The compiler numbers are trustworthy.

Applying that to the real functions, against Go's default 1 GB
`maxstacksize`:

| target | B/level | stack-limit depth | competing ceiling |
|---|---|---|---|
| linux/amd64 | 320 | ≈ 3.12 M | `RLIMIT_NOFILE` — **524 288 here**, so fd wins by 6× |
| windows/amd64 | 136 | ≈ **7.35 M** | per-process handle limit ≈ 16.7 M — **stack wins** |
| windows/arm64 | 152 | ≈ 6.58 M | same — **stack wins** |

The Windows frame is *smaller* than Linux's (128 vs 312 bytes) because the
Linux twin holds a `unix.Stat_t` (144 B) in its own frame for the
classify-then-open triage, while the Windows twin delegates to
`openRealDirAt`/`deleteEntryAt`, whose frames are transient. So the answer to
"does the same reasoning hold on Windows, where the per-frame cost differs" is:
**the frame is cheaper, which makes the stack ceiling reachable at a shallower
depth relative to the handle ceiling, and therefore makes the stack the binding
limit on Windows where it is not on Linux.**

That matters because the two ceilings fail differently. I ran the stack ceiling
deliberately (`debug.SetMaxStack(4 MiB)`, depth 14 000):

```
runtime: goroutine stack exceeds 4194304-byte limit
runtime: sp=0x2633d2f60368 stack=[0x2633d2f60000, 0x2633d3360000]
fatal error: stack overflow
                                         → exit status 2
                                         → 14 000 of 14 000 levels still on disk
```

Go's stack overflow is a `runtime.throw`, not a panic: **`recover()` cannot
catch it and the process dies.** In `scratchpad-web` that is the HTTP server
terminating for every user because one `DELETE` handler recursed too far.
Contrast the descriptor ceiling, which returns `EMFILE` up the stack and leaves
the server running.

The same is true on Linux if `RLIMIT_NOFILE` exceeds ≈3.1 M. It does not here
(524 288), and the project's installers set no `LimitNOFILE`, so a systemd
`--user` install inherits the manager default. But `LimitNOFILE=infinity`
resolves to `fs.nr_open` — 1 073 741 816 on this host — and would put Linux in
the fatal regime too.

### 3.5 Judgement

**The change is correct and I would keep it.** The depth bound was strictly
harmful: it protected against a cycle risk I could not construct, while
guaranteeing that a tree past depth 64 was permanently undeletable, which is a
defect a user can actually hit. Removing it is the right call and P3.14's
reasoning for it holds up under testing.

What I would add — as an Informational, not a blocker — is that the fix took
half of P3.14's own recommendation. P3.14 proposed "keep descending but stop
*only* if the walk fails to make progress"; the implementation kept the
"unbounded" and dropped the progress guard, leaving an implicit ceiling that is
(a) invisible, (b) different on each platform, and (c) fatal rather than
graceful on Windows. A single explicit ceiling — 10 000, say, which is 150×
the old bound and 50× anything constructible through a supported path —
returning an actionable error would restore a graceful failure on both
platforms, keep M2 closed by any practical measure, and stop a deep delete
transiently draining a long-running server's descriptor table. If the ceiling
stays implicit, the doc comments should at least say what it is, because
"the only bound that mattered — the filesystem's own — still applies" is not
what I measured: the filesystem imposed no bound at all, the process's
descriptor table did.
